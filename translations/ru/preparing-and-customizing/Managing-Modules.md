# Управление модулями

Менеджер модулей MiniOS — это графическое приложение для просмотра, создания и управления модулями MiniOS `.sb`. В нём есть две рабочие области: **Модули** для составления системы и **Создать** для создания новых модулей.

Запустить его можно из меню приложений или командой:

```bash
minios-module-manager
```

Само приложение работает от имени вашего пользователя в системе. Запрос на аутентификацию администратора появляется только при выполнении операций, требующих повышенных прав.

## Текущее выполнение и следующая загрузка

Рабочее пространство Модули предоставляет два отдельных представления:

- **Текущее выполнение** — это упорядоченный набор модулей, который сейчас формирует рабочую систему.
- **Следующая загрузка** — это упорядоченный набор, выбранный текущими правилами загрузки MiniOS.

Изменение одного представления не приводит к незаметному изменению другого. Например, действие **Активировать для этой сессии** влияет только на работающую систему, а **Добавить в следующую загрузку** копирует модуль в постоянное хранилище модулей без немедленной активации.

Актуальные правила загрузки, включая уровни-источники кандидатов, замену по точному имени файла, числовую сортировку и фильтрацию по `load=`, `noload=` и `bext=`, описаны в разделе [Загрузка модулей Initrd](/reference/boot-process/Module-Loading). В этом руководстве также объясняется, почему Текущее выполнение и Следующая загрузка могут различаться.

Активация и деактивация модулей во время работы доступны только если корневая файловая система использует AUFS. Они недоступны на корне OverlayFS, даже если ядро поддерживает AUFS. Базовые модули нельзя деактивировать через приложение.

Изменения для следующей загрузки доступны только если MiniOS находит подходящее постоянное и доступное для записи хранилище модулей. Базовые модули и модули на только для чтения или временных носителях нельзя удалить. Фильтры загрузки, такие как `load`, `noload` и `bext`, по-прежнему определяют, какие модули будут выбраны.

## Просмотр модуля

Выберите модуль, чтобы увидеть его источник, сжатый размер и содержимое файловой системы. Если исходный файл доступен, функция **Извлечь в папку** создаст новую директорию с файлами модуля.

Для просмотра и обычного извлечения не требуются права администратора. Извлечение никогда не заменяет существующую папку назначения.

Вы также можете открыть локальный файл `.sb` из файлового менеджера. Открытие файла только позволяет его просмотреть; это не активирует модуль и не добавляет его в список для следующей загрузки.

## Создание модуля

Рабочая область «Создать» использует последовательность **Настройка**, **Проверка**, **Выполнение** и **Результат**. Успешно созданный модуль остаётся файлом по выбранному пути. Он не активируется и не добавляется в следующую загрузку автоматически.

Доступные методы:

- **Пакеты** устанавливает пакеты из репозитория и выбранные локальные файлы `.deb` вместе с их зависимостями в изолированной среде сборки MiniOS. Для установки пакетов требуется аутентификация администратора.
- **Скрипт установки** выполняет проверенный скрипт без интерактивного терминала. Необязательная папка с исходными файлами может быть использована для начального наполнения. Скрипт выполняется с правами администратора, но не сохраняется в итоговом модуле.
- **Интерактивный chroot** открывает временную root-оболочку во встроенном терминале. Введите `exit` после завершения работы, затем создайте модуль, снова откройте оболочку или отмените изменения. Закрытие или отмена сессии не влияет на текущую систему.
- **Папка** упаковывает содержимое существующего каталога. Сам исходный каталог не вкладывается внутрь модуля. Обычное преобразование папки не требует root-прав, не изменяет исходные данные и нормализует владельца файлов в модуле до root.
- **Изменения текущей сессии** фиксирует допустимые файлы и удаления из текущего слоя с возможностью записи. Используется стандартная политика MiniOS `savechanges`, которая исключает журналы, кэш, загрузочные данные и временные пути. Для чтения полного слоя с возможностью записи требуются права администратора.

Для каждого сценария выберите новый путь для сохранения результата. Существующие файлы никогда не перезаписываются. Ход выполнения и диагностические сообщения backend отображаются во время работы, а захват изменений текущей сессии можно отменить.

Изменения текущей сессии предназначены для стандартного быстрого захвата, а не для детального просмотра каждого включённого пути. Живой слой с возможностью записи может содержать личные или конфиденциальные данные. Для явных политик приватности по `exact`, `clean` или выбору путей используйте командную строку с `savechanges`, как описано в разделе [Создание модулей](/preparing-and-customizing/Managing-Modules).

## Drag and drop

Перетаскивание используется только для заполнения поля ввода или открытия просмотра:

- Модуль открывает его детали.
- Файлы `.deb` добавляются в раздел «Пакеты».
- Каталог выбирается для режима «Папка».
- Другой обычный файл выбирается как скрипт установки.

Перетаскивание не выполняет код и не изменяет списки «Запущено сейчас» или «Следующая загрузка».

## Создание модулей

MiniOS модули — это доступные только для чтения образы файловой системы SquashFS, которые обычно имеют расширение `.sb`. При загрузке MiniOS выстраивает выбранные модули в слоистую корневую файловую систему. Файлы в слое с более высоким приоритетом могут дополнять или скрывать файлы из нижележащих слоёв. Эта модульная live-система является частью архитектуры MiniOS, описанной в разделе [О MiniOS](/getting-started/About-MiniOS) и [Режимы загрузки](/using-minios/Boot-Modes). После нативного преобразования слоистый корень `.sb` заменяется обычной записываемой файловой системой Debian. Программное обеспечение управления модулями MiniOS удаляется, так как сценарии работы с модулями больше не применяются, а выбранная рабочая среда и обычные приложения остаются установленными как стандартные пакеты.

В этом руководстве описаны актуальные сценарии работы с командной строкой MiniOS Tools. Для графического приложения см. [Менеджер модулей MiniOS](/preparing-and-customizing/Managing-Modules). Полный процесс сборки образа и архитектуру системы см. в разделе [Сборка MiniOS](/development/Building-MiniOS). Списки пакетов, используемые при сборке MiniOS, описаны в [документации CondinAPT](/development/CondinAPT).

### Безопасность и границы привилегий

Не все операции с модулями требуют root-прав:

| Операция | Привилегии |
|---|---|
| Просмотр «Запущено сейчас» или «Следующая загрузка» с помощью `sb` | Без root |
| Просмотр модуля с помощью `sb inspect` | Без root |
| Обычное преобразование `dir2sb` и `sb2dir` | Без root |
| Сохранить владельца или разрешить спецфайлы при конвертации | Root |
| Сборка с `apt2sb`, `script2sb` или `chroot2sb` | Root |
| Захват сессии с помощью `savechanges` | Root |
| Активация, деактивация, добавление в следующую загрузку или удаление из неё | Root |

Сборщики используют изолированный union и не устанавливают пакеты или скриптовые изменения в рабочую корневую систему. Создание модуля также не активирует результат и не выбирает его для следующей загрузки.

Текущие конвертеры и сборщики используют публикацию без замены: если цель уже существует (включая символическую ссылку), она не будет перезаписана. Выберите новый путь для результата или вручную удалите старый файл.

Используйте вывод `--help` каждой команды как ссылку на установленную версию. Стандартные параметры сжатия для сборщика: `zstd` (по умолчанию), `gzip`, `lzo` и `xz`; `dir2sb` также поддерживает `lz4`.

### Имена модулей и уровни фильтрации

Имена часто начинаются с числа, например `06-browser.sb`, потому что порядок слоёв влияет на разрешение конфликтов. Модуль должен содержать пути относительно корня системы, такие как `usr/bin/example`, а не дополнительную директорию с этим деревом.

Для точных уровней-источников кандидатов, поведения при совпадении имён, числовой сортировки и семантики `bext=`, `load=` и `noload=` см. [Загрузка модулей Initrd](/reference/boot-process/Module-Loading). Особенно важно использовать уникальное имя файла, если только модуль не предназначен для замены одноимённого слота из предыдущего уровня-источника.

Опция `--level LEVEL` на `apt2sb`, `script2sb` и `chroot2sb` ограничивает базовые слои, используемые для построения объединённого слоя. С `--level 3` используются пронумерованные слои до `03`, а слои с более высокими номерами отфильтровываются. Это может сделать модуль менее зависимым от необязательных верхних слоёв, но увеличивает количество зависимостей в результате.

### Создание модуля из пакетов

`apt2sb` устанавливает пакеты из репозитория или читаемые локальные файлы `.deb` во временное объединение и сохраняет результат. Требуется поддерживаемая живая сессия MiniOS и root-права.

```bash
sudo apt2sb install chromium chromium-sandbox
sudo apt2sb install -y --level 3 -n 06-browser.sb chromium chromium-sandbox
sudo apt2sb install -y --no-install-recommends ./example_amd64.deb -n 06-example.sb
```

Без `--name` имя результата формируется на основе первого пакета. Полезные параметры APT: `--install-recommends`, `--no-install-recommends`, `--install-suggests`, `--no-install-suggests`, `--allow-downgrades` и `--target-release RELEASE`. Опция target-release применяется только к `install`.

Чтобы зафиксировать обновления уже установленных пакетов:

```bash
sudo apt2sb upgrade -y -n upgrades.sb
```

### Создание модуля из скрипта

`script2sb` копирует скрипт установки во временный chroot, делает его исполняемым, запускает от root без интерактивного терминала, удаляет его и сохраняет изменения файловой системы. Если скрипт завершился с ошибкой, модуль не создаётся.

```bash
sudo script2sb --script ./install-example.sh -n 06-example.sb
sudo script2sb --script ./install-example.sh --directory ./seed-root --level 3 -n 06-example.sb
```

Необязательный параметр `--directory DIR` копирует всё содержимое исходной папки, включая скрытые файлы, в корень модуля до запуска скрипта. Организуйте seed-директорию как дерево файловой системы:

```text
seed-root/
`-- usr/
    `-- share/
        `-- applications/
            `-- example.desktop
```

Перед запуском обязательно проверьте скрипт. Он выполняется с правами администратора и может запускать любые команды. Используйте `chroot2sb`, если для установки требуются вопросы или ручные действия.

### Интерактивное создание модуля

`chroot2sb` создаёт временное объединение и открывает в нём оболочку root. Установите пакеты или измените файлы, затем завершите работу в оболочке для сохранения изменений:

```bash
sudo chroot2sb --level 3 -n 06-custom.sb
sudo chroot2sb --directory ./seed-root -c xz -n 06-custom.sb
```

Введённые в оболочке команды не будут повторяться при загрузке модуля; модуль — это снимок итогового состояния файловой системы. История команд оболочки не сохраняется в результате. Если имя не указано, оно формируется по текущей дате и времени.

Разделённый жизненный цикл `prepare`, `shell`, `finish` и `cancel` применяется для защищённых графических интерфейсов. Для обычного терминала используйте единую интерактивную команду, приведённую выше.

### Создание модуля из каталога

`dir2sb` упаковывает содержимое подготовленного каталога в новый модуль. Оба параметра обязательны:

```bash
dir2sb my-app-root 06-my-app.sb
dir2sb --comp xz my-app-root 06-my-app-xz.sb
```

Обычное преобразование не требует root-прав. Исходные данные не изменяются, внутри модуля все файлы принадлежат root, устройства, сокеты и FIFO-файлы отклоняются, цель никогда не перезаписывается. Используйте `--keep-ownership` или `--allow-special` только при необходимости этих привилегированных режимов.

### Захват изменений текущей сессии

`savechanges` читает основной слой с возможностью записи в работающей сессии MiniOS. Требуются root-права, так как слой может содержать файлы, доступные только root. По умолчанию место хранения изменений определяется автоматически:

```bash
sudo savechanges session-changes.sb
sudo savechanges --comp xz session-changes-xz.sb
```

Без `--profile` историческая политика MiniOS исключает пустые каталоги, кэш, журналы, загрузочные данные, временные пути, псевдофайловые системы и отдельные файлы сессии и системы. Это удобно для традиционного создания модулей, но не гарантирует приватность.

Доступные профили:

- `exact` сохраняет все представимые изменения, включая пользовательские данные, журналы, кэш, идентификаторы, учётные данные и поддерживаемые метаданные об удалениях. Не поддерживаемые объекты файловой системы отклоняются, а не теряются молча.
- `clean` использует узкий список разрешённых путей, ориентированный на ПО. Исключаются данные пользователей и root, журналы, кэш, идентификаторы, сетевые настройки, учётные данные, произвольные системные настройки и `/usr/local`. Это снижает риск раскрытия приватных данных, но не гарантирует, что разрешённый файл не содержит секретов.
- `selected` включает только явно выбранные относительные пути из файла инвентаризации и выбора. Явные исключения имеют приоритет. Этот профиль подходит, если модуль должен содержать строго определённый набор изменений.

Примеры:

```bash
sudo savechanges --profile exact exact-session.sb
sudo savechanges --profile clean --comp xz software-session.sb
sudo savechanges --inventory-json session-inventory.json
sudo savechanges --profile selected --selection selection.json selected-session.sb
```

Файл выбора должен иметь строгую JSON-структуру:

```json
{
  "product_kind": "minios-session-selection",
  "schema_version": 1,
  "include_paths": ["etc/default", "opt/my-app"],
  "exclude_paths": ["opt/my-app/private"]
}
```

Пути нормализуются, не пустые и задаются относительно корня изменений. Сначала сгенерируйте и проверьте инвентарь; каждый включённый путь должен соответствовать данным инвентаря. Инвентарь содержит метаданные (путь, тип, категория, чувствительность, размер), но не читает и не выводит содержимое файлов, цели символических ссылок или секретные значения. Модули с явным профилем и инвентари имеют режим `0600`; модули по старой политике — режим `0644`.

Захват сессии может сохранять поддерживаемые удаления файлов и непрозрачность каталогов для активного backend AUFS или OverlayFS. Исключаются монтирования во время работы, вложенные файловые системы, служебные файлы объединения и сам результат. Существующая цель никогда не заменяется.

### Просмотр и извлечение модулей

Просмотреть модуль без монтирования или извлечения:

```bash
sb inspect 06-example.sb
sb inspect 06-example.sb --json
```

Просмотр не требует root-прав и работает вне сессии MiniOS.

Извлечь модуль в новую папку:

```bash
sb2dir 06-example.sb example-root
```

Обычное извлечение не требует root-прав и не изменяет исходный файл. Целевая папка не должна существовать. Специальные файлы отклоняются, если не указан `--allow-special` и нет соответствующих прав.

Каталоги, созданные текущей `sb2dir`, — это обычные папки. `rmsbdir`, `sb rm` и `sb rmdir` — устаревшие команды совместимости, которые всегда отказываются от удаления; они не размонтируют и не удаляют рекурсивно ничего. Перед удалением извлечённого пути и его содержимого проверьте их стандартными средствами файловой системы.

### Управление модулями текущей и следующей загрузки

Текущее выполнение и Следующая загрузка — это независимые композиции. См. [Построение объединённого слоя и активация во время работы](/reference/boot-process/Module-Loading) для информации о границе загрузки/выполнения и причинах различий между этими списками.

Вывести список модулей, фактически составляющих текущий корень AUFS или OverlayFS, от низшего к высшему приоритету:

```bash
sb list
sb list --json
```

Вывести список модулей, выбранных текущими правилами загрузки:

```bash
sb next-boot
sb next-boot --json
```

Эти запросы не требуют прав суперпользователя. Канонические [правила уровней-кандидатов и замены](/reference/boot-process/Module-Loading) определяют, какой источник предоставляет каждый файл для Следующей загрузки.

Чтобы сделать пользовательский модуль доступным при следующей загрузке:

```bash
sudo sb next-boot add 50-extra.sb
```

MiniOS использует подходящее постоянное доступное для записи хранилище, подготавливает и проверяет копию, а затем публикует её атомарно, не заменяя существующий модуль. Имя файла должно соответствовать текущим фильтрам загрузки. Для удаления выбранного пользовательского модуля по его точному имени:

```bash
sudo sb next-boot remove 50-extra.sb
```

Удаление невозможно для базовых модулей и модулей на носителях только для чтения или временных источниках.

Активация во время работы — это отдельная операция, действующая только в текущей сессии:

```bash
sudo sb activate 50-extra.sb
sudo sb deactivate 50-extra.sb
```

Активация и деактивация работают только если `/` в данный момент является объединённым слоем AUFS. Они недоступны на OverlayFS, и одной поддержки ядра AUFS недостаточно. Ни одна из этих команд не изменяет список Следующей загрузки.

Диспетчер преобразования совместимости требует оба операнда:

```bash
sudo sb conv my-app-root 06-my-app.sb
sudo sb conv 06-my-app.sb example-root
```

Прямое использование `dir2sb` и `sb2dir` предпочтительнее, так как обычное преобразование можно выполнять без прав суперпользователя.
