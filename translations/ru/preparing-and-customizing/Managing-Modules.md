# Управление модулями

Менеджер модулей MiniOS — это графическое приложение для просмотра, создания и управления модулями MiniOS`.sb` . В нём есть два рабочих пространства: **Модули** для компоновки системы и **Создать** для создания новых модулей.

Запустить его можно из меню приложений или командой:

```bash
minios-module-manager
```

Само приложение работает от имени вашего пользователя. Запрос на аутентификацию администратора появляется только при необходимости выполнить действие, требующее повышенных прав.

## Текущий запуск и следующий запуск

В рабочем пространстве «Модули» доступны два отдельных представления:

- **Текущий запуск** — это упорядоченный набор модулей, формирующий активную систему.
- **Следующий запуск** — это упорядоченный набор, выбранный по текущим правилам загрузки MiniOS.

Изменение одного представления не приводит к незаметному изменению другого. Например, **Активировать для этой сессии** влияет только на текущую систему, а **Добавить в следующий запуск** копирует модуль в постоянное хранилище модулей без его активации прямо сейчас.

Правила загрузки, включая уровни источников, замену по имени, числовую сортировку`load=`, `noload=` и `bext=` фильтрацию, описаны в разделе [Загрузка модулей initrd](/reference/boot-process/Module-Loading). Там же объясняется, почему «Текущий запуск» и «Следующий запуск» могут отличаться.

Активация и деактивация модулей во время работы доступны только если корневая файловая система использует AUFS. На OverlayFS это недоступно, даже если ядро поддерживает AUFS. Базовые модули нельзя деактивировать через приложение.

Изменения для следующей загрузки возможны только если MiniOS находит подходящее постоянное и доступное для записи хранилище модулей. Базовые модули и модули на только для чтения или временных носителях удалить нельзя. Фильтры загрузки, такие как `load`, `noload` и `bext` по-прежнему определяют, какие модули будут выбраны.

## Просмотр модуля

Выберите модуль, чтобы увидеть его источник, сжатый размер и содержимое файловой системы. Если исходный файл доступен,**Извлечь в папку** создаст новую директорию с файлами модуля.

Для просмотра и обычного извлечения не требуются права администратора. Извлечение никогда не заменяет уже существующую папку назначения.

Вы также можете открыть локальный`.sb` файл через файловый менеджер. Открытие файла только позволяет просмотреть его, но не активирует и не добавляет в следующий запуск.

## Создание модуля

В рабочем пространстве «Создать» используется последовательность этапов:**Настройка**, **Проверка**, **Выполнить**, и **Результат**. Успешно созданный модуль сохраняется как файл по указанному пути. Он не активируется и не добавляется в следующий запуск автоматически.

Доступные методы:

- **Пакеты** устанавливает пакеты из репозитория и выбранные локальные`.deb` файлы вместе с зависимостями в изолированной среде сборки MiniOS. Для установки пакетов требуется аутентификация администратора.
- **Скрипт установки** выполняет проверенный скрипт без интерактивного терминала. Необязательная папка-источник может содержать исходные файлы. Скрипт запускается с правами администратора, но не сохраняется в итоговом модуле.
- **Интерактивный chroot** открывает временную root-оболочку в терминале приложения. После завершения работы введите`exit` , затем создайте модуль, снова откройте оболочку или отмените изменения. Закрытие или отмена сессии не влияет на работающую систему.
- **Папка** упаковывает содержимое существующего каталога. Сам исходный каталог не вкладывается внутрь модуля. Обычное преобразование папки не требует root-прав, не изменяет исходные данные и нормализует владельца файлов в модуле до root.
- **Изменения текущей сессии** сохраняет подходящие файлы и удаления из текущего слоя сессии с возможностью записи. Используется стандартная политика MiniOS`savechanges`, которая исключает журналы, кэш, загрузочные данные и временные пути. Для чтения всего слоя с возможностью записи требуется аутентификация администратора.

Для каждого сценария выберите новый путь для вывода. Существующие файлы никогда не перезаписываются. Пока операция выполняется, отображается прогресс и диагностические сообщения, а захват изменений текущей сессии можно отменить.

Функция «Изменения текущей сессии» предназначена для стандартного захвата, а не для детального просмотра всех путей. В рабочем writable-слое могут находиться личные или конфиденциальные данные. Для явного`exact`, `clean` или политики приватности с выбором путей используйте командную строку`savechanges` , как описано в разделе [Создание модулей](/preparing-and-customizing/Managing-Modules).

## Перетаскивание

Перетаскивание только заполняет поле ввода или открывает просмотр:

- Модуль открывается для просмотра подробностей.
- `.deb` файлы добавляются в «Пакеты».
- Каталог выбирается для режима «Папка».
- Другой обычный файл выбирается как скрипт установки.

Перетаскивание не выполняет код и не изменяет списки «Текущий запуск» и «Следующий запуск».

## Создание модулей

Модули MiniOS — это только для чтения образы файловой системы SquashFS, обычно с расширением`.sb` . При загрузке MiniOS собирает выбранные модули в слоистую корневую файловую систему. Файлы в слое с более высоким приоритетом могут дополнять или скрывать файлы из нижних слоёв. Эта модульная живая схема — часть архитектуры MiniOS, описанной в разделе[О программе MiniOS](/getting-started/About-MiniOS) и [Режимы загрузки](/using-minios/Boot-Modes). После нативного преобразования слоистый`.sb` root заменяется обычной writable-файловой системой Debian. Программное обеспечение для управления модулями MiniOS удаляется, так как модульные сценарии больше не применяются, а выбранная среда рабочего стола и приложения остаются установленными как обычные пакеты.

В этом руководстве описаны актуальные командные сценарии работы с MiniOS Tools. Для работы с графическим приложением см.[Менеджер модулей MiniOS](/preparing-and-customizing/Managing-Modules) . Для полного процесса сборки образа и архитектуры системы см.[Сборка MiniOS](/development/Building-MiniOS). Списки пакетов, используемые при сборке MiniOS, описаны в разделе[Документация CondinAPT](/development/CondinAPT).

### Безопасность и границы привилегий

Не все операции с модулями требуют root-прав:

| Операция | Привилегии |
|---|---|
| Просмотр «Текущий запуск» или «Следующий запуск» с помощью`sb` | Без root |
| Просмотр модуля с помощью`sb inspect` | Без root |
| Обычное`dir2sb` и `sb2dir` преобразование | Без root |
| Сохранение владельца или разрешение спецфайлов при преобразовании | Root |
| Сборка с помощью`apt2sb`, `script2sb` или `chroot2sb` | Root |
| Сохранение сессии с помощью`savechanges` | Root |
| Активация, деактивация, добавление в следующий запуск или удаление из следующего запуска | Root |

Сборщики используют изолированный union и не устанавливают пакеты или изменения скриптов в рабочую систему. Создание также не активирует результат и не выбирает его для следующей загрузки.

Текущие конвертеры и сборщики используют публикацию без перезаписи. Уже существующая цель, включая символическую ссылку, не перезаписывается. Выберите новый путь для вывода или вручную удалите старый результат.

Используйте команду`--help` для получения информации об установленной версии. Стандартные варианты сжатия для сборщика:`zstd` (по умолчанию), `gzip`, `lzo` и `xz`; `dir2sb` также поддерживает `lz4`.

### Имена модулей и уровни фильтрации

Имена часто начинаются с числа, например`06-browser.sb`, так как порядок слоёв влияет на разрешение конфликтов. Модуль должен содержать пути относительно корня системы, например`usr/bin/example`, а не дополнительную папку с этим деревом.

Для точных уровней источников, поведения при совпадении имён, числовой сортировки`bext=`, `load=` и `noload=` семантики см.[Загрузка модулей initrd](/reference/boot-process/Module-Loading). В частности, используйте уникальное имя файла, если только модуль не предназначен для замены одноимённого слота из предыдущего уровня.

Параметр`--level LEVEL` на`apt2sb`, `script2sb` и `chroot2sb` ограничивает базовые слои, используемые для сборки union. При использовании`--level 3`, слои с номерами до`03` включительно используются, а более высокие фильтруются. Это может сделать модуль менее зависимым от дополнительных слоёв, но увеличит число зависимостей в результате.

### Создание модуля из пакетов

`apt2sb` устанавливает пакеты из репозитория или доступные локальные`.deb` файлы в приватный union для сборки и сохраняет результат. Требуется поддерживаемая живая сессия MiniOS и root-права.

```bash
sudo apt2sb install chromium chromium-sandbox
sudo apt2sb install -y --level 3 -n 06-browser.sb chromium chromium-sandbox
sudo apt2sb install -y --no-install-recommends ./example_amd64.deb -n 06-example.sb
```

Без`--name`, имя результата формируется по первому пакету. Полезные параметры APT:`--install-recommends`, `--no-install-recommends`, `--install-suggests`, `--no-install-suggests`, `--allow-downgrades` и `--target-release RELEASE`. Параметр target-release применяется только к`install`.

Для захвата обновлений уже установленных пакетов:

```bash
sudo apt2sb upgrade -y -n upgrades.sb
```

### Создание модуля из скрипта

`script2sb` копирует установочный скрипт в приватный chroot, делает его исполняемым, запускает от имени root без интерактивного терминала, удаляет его и фиксирует изменения файловой системы. Если скрипт завершился с ошибкой, модуль не создаётся.

```bash
sudo script2sb --script ./install-example.sh -n 06-example.sb
sudo script2sb --script ./install-example.sh --directory ./seed-root --level 3 -n 06-example.sb
```

Необязательный параметр `--directory DIR` копирует все исходные файлы, включая скрытые (dotfiles), в корень модуля до запуска скрипта. Подготовьте seed-директорию как дерево файловой системы:

```text
seed-root/
`-- usr/
    `-- share/
        `-- applications/
            `-- example.desktop
```

Перед запуском обязательно проверьте скрипт. Он выполняется с правами администратора и может запускать любые команды. Используйте `chroot2sb`, если для установки требуются вопросы или ручные действия.

### Интерактивное создание модуля

`chroot2sb` создаёт приватный build union и открывает root-оболочку внутри него. Установите пакеты или отредактируйте файлы, затем выйдите из оболочки, чтобы зафиксировать изменения:

```bash
sudo chroot2sb --level 3 -n 06-custom.sb
sudo chroot2sb --directory ./seed-root -c xz -n 06-custom.sb
```

Введённые в оболочке команды не воспроизводятся при загрузке модуля; модуль — это снимок итогового состояния файловой системы. История команд оболочки из результата удаляется. Если имя не указано, оно будет сгенерировано по текущей дате и времени.

Разделённый жизненный цикл `prepare`, `shell`, `finish` и `cancel` используется для защищённых графических интерфейсов. Для обычного использования в терминале применяйте единую интерактивную команду, показанную выше.

### Создание модуля из директории

`dir2sb` упаковывает содержимое подготовленной директории в новый модуль. Оба аргумента обязательны:

```bash
dir2sb my-app-root 06-my-app.sb
dir2sb --comp xz my-app-root 06-my-app-xz.sb
```

Обычное преобразование не требует root-прав. Исходная директория не изменяется, права собственности внутри модуля нормализуются на root, устройства, сокеты и FIFO-файлы отклоняются, целевой файл никогда не перезаписывается. Используйте `--keep-ownership` или `--allow-special` только если действительно необходимы привилегированные действия.

### Фиксация изменений текущей сессии

`savechanges` читает основной записываемый слой работающей сессии MiniOS. Требуются root-права, так как этот слой может содержать файлы, доступные только root. Местоположение изменений определяется автоматически:

```bash
sudo savechanges session-changes.sb
sudo savechanges --comp xz session-changes-xz.sb
```

Без `--profile` историческая политика MiniOS исключает пустые директории, кэши, логи, загрузочные данные, временные пути, псевдофайловые системы, а также отдельные файлы сессии и системы. Это удобно для традиционного создания модулей, но не является явной гарантией приватности.

Явные профили:

- `exact` сохраняет все представимые изменения, включая пользовательские данные, логи, кэши, идентификационные файлы, учётные данные и поддерживаемые метаданные об удалениях. Неподдерживаемые объекты файловой системы отклоняются, а не теряются без предупреждения.
- `clean` использует ограниченный список путей, ориентированный на программное обеспечение. Исключаются домашние и root-данные, логи, кэши, идентификаторы, сетевые настройки, учётные данные, произвольные системные настройки и `/usr/local`. Это снижает риск раскрытия приватных данных, но не гарантирует, что разрешённый файл не содержит секретной информации.
- `selected` включает только проверенные относительные пути из инвентарного и выборочного файла. Явные исключения имеют приоритет. Этот профиль подходит, если модуль должен содержать строго определённый набор изменений сессии.

Примеры:

```bash
sudo savechanges --profile exact exact-session.sb
sudo savechanges --profile clean --comp xz software-session.sb
sudo savechanges --inventory-json session-inventory.json
sudo savechanges --profile selected --selection selection.json selected-session.sb
```

Файл выбора имеет строгую структуру JSON:

```json
{
  "product_kind": "minios-session-selection",
  "schema_version": 1,
  "include_paths": ["etc/default", "opt/my-app"],
  "exclude_paths": ["opt/my-app/private"]
}
```

Пути должны быть нормализованными, непустыми и относительными к корню изменений. Сначала сгенерируйте и проверьте инвентарь; каждый включаемый путь должен совпадать с данными инвентаря. Инвентарь фиксирует метаданные (путь, тип, категорию, чувствительность, размер), но не читает и не выводит содержимое файлов, цели символьных ссылок или секретные значения. Выводы явных профилей и инвентари создаются в режиме `0600`; модули с устаревшей политикой — в режиме `0644`.

Фиксация сессии может сохранять поддерживаемые удаления файлов и непрозрачность директорий для активного бэкенда AUFS или OverlayFS. Исключаются временные монтирования, вложенные файловые системы, служебные данные union и сам вывод. Существующий целевой файл никогда не заменяется.

### Просмотр и извлечение модулей

Просмотреть модуль без монтирования или извлечения:

```bash
sb inspect 06-example.sb
sb inspect 06-example.sb --json
```

Просмотр не требует root-прав и работает также вне запущенной сессии MiniOS.

Извлечь модуль в новую директорию:

```bash
sb2dir 06-example.sb example-root
```

Обычное извлечение не требует root-прав и не изменяет исходный файл. Целевая директория не должна существовать. Специальные файлы отклоняются, если только не запрошен `--allow-special` с достаточными правами.

Директории, созданные текущей `sb2dir`, являются обычными директориями. `rmsbdir`, `sb rm` и `sb rmdir` — устаревшие команды совместимости, которые всегда отказываются от удаления; они не размонтируют и не удаляют ничего рекурсивно. Перед удалением извлечённого пути и его содержимого используйте стандартные инструменты файловой системы для проверки.

### Управление текущими и загружаемыми модулями

Списки Running Now и Next Boot независимы друг от друга. Подробнее см. [конструирование union и активация во время выполнения](/reference/boot-process/Module-Loading) — о границе между загрузкой и рабочим режимом и о причинах, по которым эти списки могут отличаться.

Показать модули, реально формирующие текущий корень AUFS или OverlayFS, от низшего к высшему приоритету:

```bash
sb list
sb list --json
```

Показать модули, выбранные текущими правилами загрузки:

```bash
sb next-boot
sb next-boot --json
```

Оба запроса не требуют root-прав. Канонические [правила кандидатов и замещения](/reference/boot-process/Module-Loading) определяют, из какого источника берётся имя для Next Boot.

Чтобы сделать пользовательский модуль доступным при следующей загрузке:

```bash
sudo sb next-boot add 50-extra.sb
```

MiniOS использует подходящее надёжное хранилище с возможностью записи, подготавливает и проверяет копию, публикует её атомарно, не заменяя существующий модуль. Имя файла должно соответствовать текущим фильтрам загрузки. Для удаления выбранного пользовательского модуля используйте его точное имя:

```bash
sudo sb next-boot remove 50-extra.sb
```

Удаление невозможно для базовых модулей и модулей на только для чтения или временных источниках.

Активация во время выполнения — отдельная операция только для текущей сессии:

```bash
sudo sb activate 50-extra.sb
sudo sb deactivate 50-extra.sb
```

Активация и деактивация работают только если `/` сейчас является union AUFS. Они недоступны на OverlayFS, и одной поддержки ядра AUFS недостаточно. Ни одна из этих команд не изменяет Next Boot.

Диспетчер конвертации совместимости требует оба аргумента:

```bash
sudo sb conv my-app-root 06-my-app.sb
sudo sb conv 06-my-app.sb example-root
```

Для обычного преобразования предпочтительнее использовать `dir2sb` и `sb2dir`, так как оно может выполняться без root-прав.
