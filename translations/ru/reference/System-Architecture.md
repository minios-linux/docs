# Архитектура системы

MiniOS загружает операционную систему только для чтения, собранную из модулей SquashFS, и добавляет одну записываемую прослойку для текущей сессии. Initramfs отвечает за поиск носителя, выбор модулей и персистентности, создание корневой файловой системы, применение ранних настроек и передачу управления установленной системе инициализации.

## Обнаружение загрузки

Загрузчик BIOS или UEFI загружает ядро Linux и initramfs MiniOS из `minios/boot/`. Затем initramfs обнаруживает дерево данных MiniOS, содержащее live-модули. Источник может быть локальным, выбранным интерактивно или предоставленным по поддерживаемому сетевому пути; локальный ISO подключается через loop до использования его дерева данных. Точный порядок приоритетов и допустимые `from=` формы описаны в [Обнаружение системы initrd](/reference/boot-process/System-Discovery).

На этом же этапе обнаружения поддерживаются ISO по HTTP и PXE-источники. Дополнительная сеть на ранней загрузке предназначена только для **загрузки MiniOS по сети** (PXE / HTTP ISO). Это не постоянная сетевая конфигурация для сессии. Подробнее см. [Сетевая загрузка](/reference/boot-process/Network-Boot).

После обнаружения MiniOS может при необходимости подготовить копию RAM. Необходимость исходного источника зависит от режима копирования, персистентности и успешного отсоединения. Подробнее см. [Режимы загрузки](/using-minios/Boot-Modes) для описания модели работы.

## Состав модулей

Каждый `.sb` файл представляет собой файловую систему только для чтения SquashFS. Встроенные модули размещаются непосредственно в `minios/`; дополнительные расположения модулей могут добавлять свои слои в итоговую последовательность. Initramfs выбирает, упорядочивает и монтирует получившиеся слои только для чтения. Кандидаты на слои, замена базовых имён, фильтры, пользовательские расширения пакетов и координация с работающим ядром определяются в [Загрузка модулей initrd](/reference/boot-process/Module-Loading).

Обычный образ Xfce содержит следующие роли в определённом порядке, хотя точные имена и количество зависят от сборки и модулей, исключённых для данной цели:

```text
00-core-<arch>.sb
01-kernel-<version>.sb
02-firmware-<arch>.sb
03-gui-base-<arch>.sb
04-xfce-desktop-<arch>.sb
05-apps-<arch>.sb or the next applicable module
```

Позднее подключённые модули имеют больший приоритет и могут заменять пути, предоставленные более ранними модулями. Модуль может зависеть от файлов во всех модулях с меньшим номером, поэтому набор файлов модулей — это упорядоченная композиция, а не просто набор независимых пакетов.

## AUFS и OverlayFS

MiniOS использует union-файловую систему для объединения модулей и записываемого слоя в единую корневую файловую систему. При поддержке работающим ядром выбирается AUFS, в противном случае используется OverlayFS. `union=aufs` запрашивает AUFS, но также переходит на OverlayFS, если AUFS недоступен; `union=overlayfs` выбирает OverlayFS. При UEFI Secure Boot initrd не загружает неподписанный `aufs-ng` модуль и использует OverlayFS, если только не обнаружена другая подходящая реализация AUFS.

Две реализации отличаются важным аспектом работы:

- AUFS начинает с записываемой ветки и добавляет смонтированные модули как ветки только для чтения. MiniOS может активировать или деактивировать модуль в работающем корне, если монтирование AUFS поддерживает такую операцию.
- OverlayFS получает свой полный упорядоченный `lowerdir` список при монтировании корня, а также `upperdir` и `workdir`. Его набор нижних модулей нельзя изменить на лету с помощью **Менеджер модулей MiniOS**.

**Менеджер модулей MiniOS** таким образом разделяет **Текущий запуск**, набор смонтированных модулей, и **Следующая загрузка**, модули, выбранные текущим носителем и правилами загрузки. Добавление или удаление постоянного модуля обычно влияет только на следующую загрузку. Создание или открытие модуля не активирует его. Активация и деактивация во время работы доступны только с AUFS.

После сборки корня и завершения ранней инициализации initrd LiveKit использует `pivot_root`, сохраняет старый initrd для завершения работы и запускает init нового корня. В dracut итоговый корень готовится аналогично, но финальная `switch_root` передается dracut. Подробнее см. [Загрузка модулей initrd](/reference/boot-process/Module-Loading) для описания границы передачи управления.

## Записываемый слой и сессии

Без постоянства записываемый слой хранится в памяти и исчезает при завершении работы. Включение постоянства позволяет активировать пронумерованную сессию с поддерживаемым хранилищем. При выборе бэкенда плагина постоянства Ventoy вместо пронумерованных сессий MiniOS использует одну прямую среду ext4 с постоянством. Выбор, совместимость, ошибки активации, полномочия текущей загрузки и надежность описаны в [Постоянство initrd](/reference/boot-process/Persistence-Internals).

| Режим | Записываемое хранилище | Примечания |
|------|------------------|-------|
| `native` | Файлы сохраняются непосредственно в каталоге сессии | Требуется записываемая файловая система POSIX с сохранением метаданных Linux. |
| `dynfilefs` | Расширяемая файловая система ext4, разбитая на резервные файлы | Поддерживаются файловые системы POSIX, а также носители FAT32, NTFS или exFAT. |
| `dynblk` | Тонкая файловая система ext4 на блочном устройстве ядра, поддерживаемом `volumeNNN.db` файлами | Требуются userspace, ядро и поддержка initrd для DynBlk. |
| `vmdk` | Разделённое разрежённое `volume.vmdk` / `volume-sNNN.vmdk` хранилище, представленное как блочное устройство драйвером DynBlk | Требуется `vmdk-session-v1` поддержка DynBlk/initrd; без сжатия на стороне бэкенда. |
| `raw` | Фиксированный размер `changes.img` с ext4 | Поддерживаются файловые системы POSIX, а также носители FAT32, NTFS или exFAT. |
| `squashfs` | Сжатый `changes.sb` снимок | Распаковывается в RAM для использования; при сохранении пересобирается и атомарно заменяет снимок. Файловая система для постоянства должна сохранять метаданные Linux при сохранении. |

Raw, DynFileFS, DynBlk и VMDK могут опционально содержать слой LUKS2. Метаданные отдельно фиксируют бэкенд хранилища и шифрование. При завершении работы освобождаются ext4, mapper, все занятые loop-устройства и бэкенд в порядке зависимости.

Активная сессия, выбранная для будущего возобновления, и реально разрешённый для текущей загрузки записываемый слой — это связанные, но разные состояния. Изменение будущего выбора не заменяет работающий записываемый слой.

См. [Управление сессиями](/using-minios/Sessions-and-Persistence) для команд создания, выбора, изменения размера, шифрования, конвертации, экспорта и восстановления.

## Приоритеты конфигурации

Конфигурация носителя хранится в `minios/config.conf`, с дополнительными фрагментами в `minios/config.conf.d/`. Копии для работы системы размещаются в `/etc/live/config.conf` и `/etc/live/config.conf.d/` в собранном корне.

При загрузке MiniOS сравнивает время изменения и копирует более новый файл с носителя в рабочий корень. Если носитель доступен для записи, а рабочая копия новее, она копируется обратно на носитель. Фрагменты синхронизируются по имени файла в обоих направлениях. Если время системы было переведено назад после предыдущей синхронизации, MiniOS избегает замены меток времени и только дополняет отсутствующие файлы.

Параметры командной строки ядра перекрывают соответствующие значения, считанные из рабочей конфигурации для этой загрузки. Таким образом, итоговый порядок для явно поддерживаемой настройки: сначала параметр загрузки, затем синхронизированная рабочая/носитель-конфигурация, затем встроенное значение по умолчанию. Постоянные изменения в рабочей конфигурации могут стать конфигурацией носителя, если источник доступен для записи; ISO-носитель только для чтения не может быть обновлён.

Подробнее см. [Файл конфигурации](/reference/configuration/config.conf) и [live-config](/reference/configuration/live-config) для поддерживаемых параметров.

## Завершение работы и жизненный цикл сохранения

При штатном завершении работы системе предоставляется возможность сбросить данные сервисов и сессии. Сессия SquashFS с включённым сохранением при завершении пересобирается и проверяется до размонтирования файловой системы. Бэкенд сохранения записывает маркер завершения именно для текущей сессии; initramfs завершения работы проверяет этот маркер и помечает сессию как «грязную», если обязательное сохранение не удалось.

Далее initramfs завершения работы отсоединяет неиспользуемые loop-устройства, размонтирует старый корень и записываемый слой, отмечает успешную сессию как «чистую», размонтирует носитель и закрывает LUKS-мэппинг, принадлежащий MiniOS. После этого оптический носитель можно извлечь до выключения или перезагрузки. Ручное и периодическое сохранение SquashFS использует тот же механизм снимков, но только настроенная политика завершения блокирует финализацию при отсутствии сохранения на этапе завершения работы.

## Дерево носителя

Текущий образ организован следующим образом. Необязательные каталоги появляются только при наличии соответствующего содержимого.

```text
/
|-- .disk/                         ISO metadata
|-- EFI/                           UEFI boot files
`-- minios/
    |-- 00-core-<arch>.sb          base userspace
    |-- 01-kernel-<version>.sb
    |-- 02-firmware-<arch>.sb
    |-- NN-<name>-<arch>.sb        ordered system modules
    |-- boot/                      kernels, initramfs, GRUB, and Syslinux data
    |-- changes/                   session metadata and numbered sessions
    |-- modules/                   additional next-boot modules
    |-- config.conf                main media configuration
    |-- config.conf.d/             optional configuration fragments
    |-- kernels/                   optional inactive kernel repository
    |-- userdata/                  optional linked or bound user directories
    `-- log/                       optional exported boot logs
```

Загруженные пути в `/run/initramfs/memory/` — это монтирования, реализованные на уровне системы, а не вторая постоянная копия этого дерева.
