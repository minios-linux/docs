# Архитектура системы

MiniOS загружает операционную систему только для чтения, собранную из модулей SquashFS, и добавляет один слой с возможностью записи для текущей сессии. За поиск носителя, выбор модулей и персистентности, построение корневой файловой системы, применение ранней конфигурации и передачу управления установленной init-системе отвечает initramfs.

## Обнаружение загрузки

Загрузчик BIOS или UEFI загружает ядро Linux и initramfs MiniOS из `minios/boot/`. Затем initramfs обнаруживает дерево данных MiniOS, содержащее live-модули. Источник может быть локальным, выбранным интерактивно, либо предоставленным по поддерживаемому сетевому пути; локальный ISO монтируется в режиме loop перед использованием его дерева данных. Точная приоритетность и поддерживаемые форматы `from=` описаны в разделе [Обнаружение системы Initrd](/reference/boot-process/System-Discovery).

На этом же этапе обнаружения поддерживаются источники HTTP ISO и PXE. Необязательная сетевая загрузка на раннем этапе используется только для **загрузки MiniOS по сети** (PXE / HTTP ISO). Это не постоянная настройка сети для сессии. Подробнее см. [Сетевая загрузка](/reference/boot-process/Network-Boot).

После обнаружения MiniOS может при необходимости подготовить копию RAM. Необходимость исходного источника зависит от режима копирования, персистентности и успешного отсоединения. Операционная модель описана в разделе [Режимы загрузки](/using-minios/Boot-Modes).

## Композиция модулей

Каждый файл `.sb` — это файловая система только для чтения SquashFS. Встроенные модули хранятся непосредственно в `minios/`; дополнительные расположения модулей могут участвовать в формировании упорядоченной композиции. Initramfs выбирает, упорядочивает и монтирует получившиеся слои только для чтения. Кандидаты уровней, замена базовых имён, фильтры, расширения пользовательских бандлов и координация с работающим ядром описаны в разделе [Загрузка модулей Initrd](/reference/boot-process/Module-Loading).

Обычный образ Xfce содержит следующие роли в указанном порядке, однако точные имена и количество зависят от сборки и модулей, исключённых для данной цели:

```text
00-core-<arch>.sb
01-kernel-<version>-<arch>.sb
02-firmware-<arch>.sb
03-gui-base-<arch>.sb
04-xfce-desktop-<arch>.sb
05-apps-<arch>.sb or the next applicable module
```

Поздние модули имеют больший приоритет и могут заменять пути, предоставленные более ранними модулями. Модуль может зависеть от файлов в каждом модуле с меньшим номером, поэтому набор файлов модулей — это упорядоченная композиция, а не просто коллекция независимых пакетов.

## AUFS и OverlayFS

MiniOS использует union-файловую систему для объединения модулей и слоя с возможностью записи в единое корневое файловое пространство. При поддержке работающим ядром выбирается AUFS, в противном случае используется OverlayFS. `union=aufs` запрашивает AUFS, но при отсутствии AUFS также возвращается к OverlayFS; `union=overlayfs` выбирает OverlayFS.

У этих двух реализаций есть важное различие в работе:

- AUFS начинает с ветки с возможностью записи и добавляет смонтированные модули как ветки только для чтения. MiniOS может активировать или деактивировать модуль в текущем корневом разделе, если монтирование AUFS поддерживает такую операцию.
- OverlayFS получает полный упорядоченный список `lowerdir` при монтировании корня, а также `upperdir` и `workdir`. Набор нижележащих модулей не может быть изменён на лету через **Менеджер модулей MiniOS**.

**Менеджер модулей MiniOS** поэтому разделяет **Сейчас запущено** (текущий набор смонтированных модулей) и **Следующая загрузка** (модули, выбранные текущими носителями и правилами загрузки). Добавление или удаление постоянного модуля обычно влияет только на следующую загрузку. Создание или открытие модуля не активирует его. Активация и деактивация модулей во время работы доступны только с AUFS.

После сборки корня и завершения ранней инициализации initrd LiveKit использует `pivot_root`, сохраняет старый initrd для завершения работы системы и запускает init нового корня. В случае с dracut подготавливается тот же собранный корень, но финальный `switch_root` выполняет dracut. Подробнее о границе передачи см. в разделе [Загрузка модулей в initrd](/reference/boot-process/Module-Loading).

## Слой с возможностью записи и сессии

Без персистентности слой с возможностью записи размещается в памяти и исчезает при выключении. Персистентность может активировать пронумерованную сессию с поддерживаемым хранилищем. Выбор, совместимость, ошибки активации, полномочия текущей загрузки и долговечность описаны в разделе [Персистентность Initrd](/reference/boot-process/Persistence-Internals).

| Режим | Хранилище для записи | Примечания |
|------|---------------------|------------|
| `native` | Файлы, хранящиеся непосредственно в каталоге сессии | Требуется файловая система POSIX с поддержкой сохранения метаданных Linux. |
| `dynfilefs` | Расширяемая файловая система ext4, разбитая на резервные файлы | Поддерживаются файловые системы POSIX, а также носители FAT32, NTFS или exFAT. |
| `raw` | Фиксированный размер `changes.img` с ext4 | Поддерживаются файловые системы POSIX, а также FAT32, NTFS или exFAT. |
| `luks` | LUKS2 `changes.luks` с ext4 | Требуется cryptsetup и initramfs с поддержкой шифрования MiniOS. Пароль запрашивается при загрузке. |
| `squashfs` | Сжатый снимок `changes.sb` | Распаковывается в RAM для использования; при сохранении снимок пересобирается и заменяется атомарно. Файловая система для персистентности должна сохранять метаданные Linux при сохранении. |

Активная сессия, выбранная для будущего возобновления, и слой для записи, фактически разрешённый для текущей загрузки, — это связанные, но разные состояния. Изменение будущего выбора не заменяет работающий слой для записи.

См. [Управление сессиями](/using-minios/Sessions-and-Persistence) для команд создания, выбора, изменения размера, шифрования, конвертации, экспорта и восстановления.

## Приоритет конфигураций

Конфигурация носителя — это `minios/config.conf`, с дополнительными фрагментами в `minios/config.conf.d/`. Копии для выполнения — это `/etc/live/config.conf` и `/etc/live/config.conf.d/` в собранном корне.

При загрузке MiniOS сравнивает время изменения и копирует более новый файл с носителя в рабочий корень. Если носитель доступен для записи и рабочая копия новее, она копируется обратно на носитель. Файлы-фрагменты синхронизируются по имени в обоих направлениях. Если часы были переведены назад после предыдущей синхронизации, MiniOS избегает замены временных меток и только заполняет отсутствующие назначения.

Параметры командной строки ядра перекрывают соответствующие значения, прочитанные из рабочей конфигурации для этой загрузки. Это значит, что итоговый порядок для явно поддерживаемой настройки — параметр загрузки, затем синхронизированная рабочая/медийная конфигурация, затем встроенное значение по умолчанию. Постоянные изменения в рабочей конфигурации могут стать конфигурацией носителя, если источник доступен для записи; носители ISO только для чтения не могут быть обновлены.

См. [Файл конфигурации](/reference/configuration/config.conf) и [live-config](/reference/configuration/live-config) для поддерживаемых параметров.

## Завершение работы и жизненный цикл сохранения

При обычном завершении работы работающая система получает возможность сбросить сервисы и данные сессии. Сессия SquashFS с включённым сохранением при завершении пересобирается и проверяется перед размонтированием файловой системы. Бэкенд сохранения записывает маркер завершения именно для текущей сессии; initramfs завершения проверяет этот маркер и помечает сессию как "грязную", если обязательное сохранение не удалось.

Далее initramfs завершения отсоединяет неиспользуемые loop-устройства, размонтирует старый корень и слой для записи, отмечает успешную сессию как чистую, размонтирует носитель и закрывает LUKS-маппинг, принадлежащий MiniOS. После этого оптический носитель можно извлечь перед выключением или перезагрузкой. Ручные и периодические сохранения SquashFS используют тот же бэкенд снимков, но только настроенная политика завершения блокирует чистое завершение при отсутствии сохранения при выключении.

## Дерево носителя

Актуальный образ организован следующим образом. Необязательные каталоги появляются только при наличии соответствующего контента.

```text
/
|-- .disk/                         ISO metadata
|-- EFI/                           UEFI boot files
`-- minios/
    |-- 00-core-<arch>.sb          base userspace
    |-- 01-kernel-<version>-<arch>.sb
    |-- 02-firmware-<arch>.sb
    |-- NN-<name>-<arch>.sb        ordered system modules
    |-- boot/                      kernels, initramfs, GRUB, and Syslinux data
    |-- changes/                   session metadata and numbered sessions
    |-- modules/                   additional next-boot modules
    |-- config.conf                main media configuration
    |-- config.conf.d/             optional configuration fragments
    |-- kernels/                   optional inactive kernel repository
    |-- userdata/                  optional linked or bound user directories
    `-- log/                       optional exported boot logs
```

Загруженные пути под `/run/initramfs/memory/` — это точки монтирования реализации, а не вторая постоянная копия этого дерева.
