# Загрузка модулей

На этой странице объясняется, что изменяют параметры загрузки `load`, `noload`, `bext`, `union` и `toram=trim`. Это расширенные настройки. При обычной загрузке автоматически подгружается набор модулей, предоставляемый выбранным образом MiniOS.

MiniOS выбирает и монтирует свой набор модулей в initrd до передачи объединённого корня установленной системе инициализации. Используйте эту страницу, если модуль с загрузочного носителя не появляется в работающей системе или если фильтр неожиданно изменяет запуск.

## Простыми словами

MiniOS собирается из пронумерованных модулей `.sb` только для чтения. Сначала загружаются модули с меньшими номерами; более высокие номера могут заменять файлы из модулей с меньшими номерами. Если активна записываемая сессия, она располагается выше всех модулей только для чтения.

Параметры `load=` и `noload=` фильтруют пути к модулям до их сборки. Они используют сопоставление с регулярными выражениями, а не безопасный список точных имён, поэтому слишком широкий фильтр может исключить необходимые системные или ядровые модули из набора для загрузки.

## Пояснение параметров

| Параметр | Что сообщает MiniOS | Основной риск |
|---|---|---|
| `load=PATTERN` | Оставляет только те кандидаты на модули, чьи пути соответствуют шаблону. | Неполный шаблон может исключить необходимые модули. |
| `noload=PATTERN` | Исключает подходящих кандидатов после применения `load=`. | Важные системные, ядровые, прошивочные или десктопные модули могут быть исключены из запуска. |
| `bext=EXTENSION` | Обрабатывает другое расширение файла как суффикс кандидата на модуль. | Не конвертирует файлы и не обеспечивает полную совместимость с ядровыми модулями. |
| `union=aufs` или `union=overlayfs` | Запрашивает файловую систему для объединения модулей с записываемым слоем. | Активация модулей во время работы различается между AUFS и OverlayFS. |
| `toram=trim` | Копирует только выбранные модули и ограниченные необходимые данные в RAM. | Пропущенные модули и каталоги будут недоступны после отсоединения источника. |

Перед изменением фильтров запишите текущую командную строку и набор модулей. Тестируйте по одному изменению за раз и держите под рукой рабочий вариант загрузки.

## Уровни кандидатов

После определения каталога данных MiniOS, обычно `minios/`, initrd сканирует кандидатов на модули в следующем порядке:

1. Записи непосредственно внутри `minios/`. Этот скан не рекурсивный.
2. Записи рекурсивно ниже `minios/modules/`.
3. Записи рекурсивно ниже `minios/modules/` на источнике постоянства, зафиксированном initrd.

Третий уровень отделён от каталога `minios/modules/` в выбранном дереве данных только для чтения. Это позволяет долговременным пользовательским модулям переопределять файлы из ISO или другого источника только для чтения. Доступен только при обнаружении постоянства с опубликованным записываемым корнем, содержащим этот каталог.

Пути кандидатов при монтировании сводятся к их точному базовому имени. Например, `modules/work/50-extra.sb` и `modules/test/50-extra.sb` используют точку монтирования с именем `50-extra.sb`. Они не становятся двумя независимыми слоями. Кандидат с тем же базовым именем на более позднем уровне монтируется в ту же точку и заменяет предыдущего кандидата, видимого для объединения. Поэтому одно и то же базовое имя следует рассматривать как одну позицию для замены, а не как способ загрузить несколько модулей из разных каталогов.

Обычный формат модуля — это стандартный образ файловой системы SquashFS. Сам сканер initrd ориентируется на имя файла: выбирает пути с заданным расширением и не проверяет заранее, что путь указывает на обычный файл или валидный SquashFS. Рекурсивные сканы могут встретить другой тип объекта файловой системы с совпадающим именем. Неудачная попытка монтирования через loop или SquashFS будет зафиксирована `mount`, но сама по себе такая ошибка не приводит к фатальному сбою — загрузка может продолжиться с пропущенным слоем. Проверяйте сомнительные файлы с помощью инструкции по инспекции в разделе [Создание модулей](/preparing-and-customizing/Managing-Modules).

## Порядок и приоритеты

В процессе обнаружения пути сортируются по числовому значению базового имени. В именах, таких как `00-core.sb`, `01-kernel-VERSION.sb` и `50-extra.sb`, ведущий номер определяет порядок модуля. Имя без ведущего числа сортируется как ноль.
Используйте явные, уникальные числовые префиксы вместо надежды на порядок при совпадении.

В итоговом объединении более поздние, с большим номером, модули имеют приоритет над более ранними, с меньшим номером. Если два выбранных модуля содержат один и тот же путь относительно корня, будет виден файл из модуля с более высоким приоритетом. Записываемый слой изменений имеет приоритет над всеми модулями только для чтения.

Замещение между уровнями происходит до применения итогового порядка модулей. Кандидат `50-extra.sb` с более позднего уровня заменяет файл с тем же базовым именем с более раннего уровня, затем его префикс `50` определяет, где эта точка монтирования окажется в объединении.

## Расширение пакета

Параметр загрузки `bext=` определяет расширение файла, используемое для поиска данных, фильтрации кандидатов и монтирования модулей. По умолчанию это `sb`, поэтому обычный суффикс кандидата — `.sb`:

```text
bext=sb
```

Изменение `bext` меняет выбранный суффикс имени файла; оно не конвертирует файл и не проверяет его файловую систему. Координация с ядром — исключение: всегда ищется `01-kernel-VERSION.sb`. При пользовательском расширении стандартный поиск кандидатов не выбирает эти ядровые модули `.sb`.

## Фильтры load и noload

`load=` и `noload=` — это незафиксированные расширенные регулярные выражения, применяемые к строкам путей кандидатов, полученным на каждом уровне. Это не списки точных имён. Простое значение, например `kernel`, совпадает с этим текстом в любом месте пути, а якоря нужно указывать явно, если требуется точная позиция.
Пути различаются по уровню: кандидаты верхнего уровня — это базовые имена, кандидаты из рекурсивных данных включают `modules/`, а кандидаты из постоянства — абсолютные пути.

Запятые преобразуются в чередование для регулярных выражений. Например:

```text
load=core,kernel,firmware
```

интерпретируется как `core|kernel|firmware`. Другие символы регулярных выражений не экранируются.

Числовой диапазон разворачивается только если весь фильтр — это один возрастающий диапазон, совпадающий с `^[0-9]+-[0-9]+$`. Например, `load=04-06` превращается в альтернативы `04|05|06`, при этом каждое значение дополняется до как минимум двух цифр. Диапазон внутри списка через запятую или другого выражения не разворачивается и сохраняет обычное значение ERE.

Если заданы оба параметра, initrd сначала применяет `load=`, а затем исключает совпадения по `noload=`. Таким образом, `noload=` имеет приоритет. Нет защищённого набора системных или ядровых модулей: фильтры могут исключить `00-core`, согласованные `01-kernel` или любой другой кандидат. Такой выбор может привести к неполному корню или невозможности загрузки.

## Координация с работающим ядром

Версия работающего ядра берётся из токена `vmlinuz-VERSION` в командной строке ядра, если он доступен, либо используется `uname -r` по умолчанию. Перед монтированием модулей initrd координирует эту верхнеуровневую тройку:

```text
minios/01-kernel-VERSION.sb
minios/boot/vmlinuz-VERSION
minios/boot/initrfs-VERSION.img
```

Если какой-либо элемент отсутствует, initrd ищет все три файла в:

```text
minios/kernels/VERSION/
```

Когда тройка из репозитория полная, модуль копируется в `minios/`, а файлы загрузки — в `minios/boot/`. Частичная копия удаляется. Если тройка не полная, настройка ядра возвращает ошибку, но процесс продолжается до этапа обычного монтирования модулей. В результате система может позже не загрузиться, так как корневая файловая система не содержит поддерживающих файлов для работающего ядра.

Другие верхнеуровневые файлы, совпадающие с `01-kernel-*.sb`, считаются неактивными. Initrd пытается переместить каждый неактивный модуль и соответствующие ему файлы `vmlinuz` и `initrfs` в `minios/kernels/VERSION/`. Эти операции отката и перемещения требуют записываемого дерева данных; отдельные неудачи перемещения не считаются фатальными. Они всегда используют `.sb`, независимо от `bext=`. Подробнее о поддерживаемых сценариях установки и активации ядер — см. [Управление ядрами](/preparing-and-customizing/Managing-Kernels).

## Конструкция union

MiniOS выбирает `AUFS`, если запущенное ядро его поддерживает, в противном случае используется OverlayFS. `union=overlayfs` выбирает OverlayFS. `union=aufs` запрашивает `AUFS`, но при отсутствии `AUFS` возвращается к OverlayFS.

С помощью `AUFS` initrd сначала монтирует пустой union с веткой для записи изменений, затем добавляет каждый смонтированный модуль как ветку только для чтения. Ошибка при создании union является фатальной. Ошибка при добавлении отдельной ветки `AUFS` обрабатывается по принципу best effort: загрузка продолжается с уже добавленными ветками, а MiniOS не отмечает постоянство как активное для неполного union.

С OverlayFS полный набор модулей передаётся как один перевёрнутый список `lowerdir` при монтировании union. Записываемый слой предоставляет свои `upperdir` и `workdir`. Ошибка монтирования этого union является фатальной. Порядок нижних веток слева направо и порядок вставки `AUFS` реализуют одно и то же правило: более поздние, с большим номером модули скрывают конфликтующие пути предыдущих модулей.

Эта композиция во время загрузки отличается от активации во время работы. После запуска `sb activate` и `sb deactivate` могут изменять только корень, который в данный момент смонтирован как `AUFS`. Нижние слои OverlayFS нельзя изменить на лету. Активация во время работы не влияет на выбор Next Boot, а добавление модуля Next Boot не активирует его в текущем корне. Подробнее см. [Менеджер модулей MiniOS](/preparing-and-customizing/Managing-Modules).

## Toram trim

`toram=trim` создаёт дерево данных RAM до этапов постоянства и координации ядра.
Он копирует только следующие элементы из выбранного дерева данных MiniOS:

- `config.conf`, который необходим для этого пути копирования.
- `authorized_keys`, если он существует как обычный файл.
- Кандидаты верхнего уровня с совпадающим расширением, выбранные `load=` и `noload=`.
- Выбранные кандидаты с совпадающим расширением рекурсивно ниже `modules/`, с сохранением их относительных директорий.
- Полное дерево `changes/`, если командная строка запрашивает постоянство.

Не копируются `boot/`, `kernels/`, `rootcopy/`, `config.conf.d/`, логи, другие несистемные данные, невыбранные модули и отдельный уровень модулей постоянства. В частности, откат из репозитория невозможен, если каталог `kernels/` отсутствует в обрезанном дереве RAM. Копируемый набор модулей фильтруется до обнаружения уровня модулей постоянства.

Проверки на вместимость RAM нет. Ошибка копирования `config.conf` или запрошенного `changes/` завершает выполнение функции копирования, но вызывающие её процессы не всегда корректно останавливают загрузку. Ошибка копирования `authorized_keys` фиксируется, но не останавливает копирование. Модули копируются через конвейер; ошибка копирования отдельного модуля фиксируется, но её статус не всегда приводит к остановке внешнего процесса загрузки. Отката транзакции при частично заполненном дереве RAM нет.

После копирования initrd пытается размонтировать исходный монт, удалить старый путь данных и переместить дерево RAM в этот путь. Только успех всей цепочки означает отсоединение источника. Если цепочка неудачна, загрузка продолжается с использованием временного пути RAM. Связанные операции отсоединения ISO и Ventoy выполняются по возможности.
Следовательно, `toram=trim` не является доказательством того, что загрузочное устройство можно извлечь. Не отключайте его, пока диагностика не подтвердит, что его файловая система, loop-устройство и маппинги device-mapper больше не смонтированы и не используются.

## Rootcopy и передача корня

После монтирования модулей и построения union initrd копирует видимое содержимое `minios/rootcopy/` непосредственно в собранный union. Шаблон оболочки `*` исключает записи с точкой в начале, находящиеся непосредственно в `rootcopy/`, хотя скрытые файлы внутри копируемого каталога остаются частью этой копии. Это копирование файлов в записываемое представление, а не ещё один слой только для чтения, поэтому оно может переопределять пути, предоставленные модулями. Ошибки копирования не считаются фатальными для этой функции.

Далее MiniOS выполняет свою раннюю инициализацию, записывает `fstab` нового корня и при наличии запускает `rootcopy/run/preinit.sh`, передавая путь union в качестве первого аргумента. Этот скрипт выполняется в окружении initrd до передачи корня и должен рассматриваться как привилегированный загрузочный код.

На финальном этапе initrd LiveKit переключает собранный union на `/`, оставляет старый initrd под `/run/initramfs` для задач завершения работы и запускает `init` нового корня. Путь Dracut готовит тот же union и позволяет Dracut выполнить финальную `switch_root`. После этого этапа обычная загрузка продолжается внутри собранного корня; изменение файлов на загрузочном носителе больше не перестраивает выбранный набор нижних слоёв для этой загрузки.

## Безопасная диагностика

Предпочитайте просмотр только для чтения и фиксируйте исходную командную строку перед изменением фильтров:

```bash
cat /proc/cmdline
sb next-boot
sb list
findmnt -no FSTYPE,OPTIONS /
findmnt -R /run/initramfs 2>/dev/null
```

`sb next-boot` показывает текущий выбор по правилам, а `sb list` — слои, реально составляющие работающий корень. Различие между ними может указывать на ошибку монтирования, замену по базовому имени, изменение `AUFS` во время работы или изменение источника выбора после загрузки.

Для диагностики ранних сбоев добавьте `debug` для вывода трассировки shell, `timing` для замеров времени этапов или `rd.break` для открытия shell после настройки initrd и до передачи финального корня. В этом shell проверьте `/memory/data`, `/memory/bundles`, точки монтирования и `/proc/cmdline`; не выполняйте ремонт файловых систем и не извлекайте носители, пока они смонтированы. Фиксируйте первую ошибку монтирования или копирования, а не только последующий симптом. Более широкий сценарий безопасной диагностики — см. [Устранение неполадок](/maintenance-and-recovery/Troubleshooting).
