# Загрузка модулей

На этой странице объясняется, как `load`, `noload`, `bext`, `union` и `toram=trim` изменяют параметры загрузки. Это расширенные настройки. При обычной загрузке автоматически подгружается набор модулей, предоставленный выбранным образом MiniOS.

MiniOS выбирает и монтирует свой набор модулей в initrd до передачи корня union установленной системе инициализации. Используйте эту страницу, если модуль на загрузочном носителе не появляется в работающей системе или если фильтр неожиданно изменяет запуск.

## Простыми словами

MiniOS собирается из пронумерованных только для чтения `.sb` модулей. Модули с меньшими номерами загружаются первыми; модули с большими номерами могут заменять файлы из модулей с меньшими номерами. Если активна записываемая сессия, она располагается выше всех модулей только для чтения.

Параметры `load=` и `noload=` фильтруют пути к модулям перед сборкой. Они используют сопоставление по регулярным выражениям, а не безопасный список точных имён, поэтому слишком широкий фильтр может исключить необходимые системные или ядровые модули из набора загрузки.

## Пояснения к параметрам

| Параметр | Что сообщает MiniOS | Основной риск |
|---|---|---|
| `load=PATTERN` | Оставлять только те кандидаты модулей, чьи пути соответствуют шаблону. | Неполный шаблон может пропустить необходимые модули. |
| `noload=PATTERN` | Исключить подходящие кандидаты после применения `load=`. | Необходимые системные, ядровые, прошивочные или пользовательские модули могут быть не загружены при старте. |
| `bext=EXTENSION` | Рассматривать другое расширение файла как суффикс кандидата на модуль. | Не преобразует файлы и не обеспечивает полную совместимость с модулями ядра. |
| `union=aufs` или `union=overlayfs` | Запрашивает файловую систему, используемую для объединения модулей с записываемым слоем. | Активация модулей во время работы отличается между AUFS и OverlayFS. |
| `toram=trim` | Копировать только выбранные модули и ограниченный набор необходимых данных в RAM. | Пропущенные модули и каталоги будут недоступны после отсоединения источника. |

Перед изменением фильтров сохраните текущую командную строку и набор модулей. Тестируйте изменения по одному и держите доступной рабочую запись загрузки.

## Уровни кандидатов

После определения каталога данных MiniOS, обычно `minios/`, initrd сканирует кандидатов на модули в следующем порядке:

1. Записи непосредственно в `minios/`. Это сканирование не является рекурсивным.
2. Записи рекурсивно ниже `minios/modules/`.
3. Записи рекурсивно ниже `minios/modules/` на источнике с поддержкой записи, зафиксированном initrd.

Третий уровень отделён от каталога `minios/modules/` в выбранном дереве данных только для чтения. Это позволяет долговечным пользовательским модулям переопределять файлы из ISO или другого источника только для чтения. Доступен только при обнаружении персистентности и наличии записываемого корня с этим каталогом.

Кандидатные пути при монтировании сводятся к их точному базовому имени. Например, `modules/work/50-extra.sb` и `modules/test/50-extra.sb` используют одну и ту же точку монтирования с именем `50-extra.sb`. Они не становятся двумя независимыми слоями. Кандидат на более позднем уровне с тем же базовым именем монтируется в ту же точку и заменяет предыдущий кандидат, видимый при сборке union.
Поэтому одинаковое базовое имя следует рассматривать как одну позицию для замены, а не как способ загрузить несколько модулей из разных каталогов.

Обычный формат модуля — это образ файловой системы SquashFS. Сканирование initrd ориентируется на имя файла: выбираются пути с нужным расширением, при этом не проверяется, является ли путь обычным файлом или валидным образом SquashFS. Поэтому при рекурсивном сканировании может встретиться другой объект файловой системы с подходящим именем. Ошибка монтирования через loop или SquashFS фиксируется в `mount`, но сама по себе не приводит к фатальной ошибке: загрузка может продолжиться с отсутствующим слоем. Проверяйте сомнительные файлы с помощью инструкции в разделе [Создание модулей](/preparing-and-customizing/Managing-Modules).

## Порядок и приоритет

В процессе обнаружения пути сортируются по числовому значению базового имени. Ведущий номер в именах, таких как `00-core.sb`, `01-kernel-VERSION.sb` и `50-extra.sb` определяет порядок модуля. Базовое имя без ведущего числа сортируется как ноль.
Используйте явные, уникальные числовые префиксы, а не полагайтесь на порядок при равных значениях.

В итоговом union более поздние, с большими номерами, модули имеют приоритет над более ранними с меньшими номерами. Если два выбранных модуля содержат один и тот же путь относительно корня, будет виден файл из модуля с более высоким приоритетом. Слой изменений с записью имеет приоритет над всеми модулями только для чтения.

Замена по уровню происходит до применения этого порядка модулей. Кандидат с более позднего уровня `50-extra.sb` заменяет файл с тем же базовым именем с предыдущего уровня, затем его префикс `50` определяет, где эта точка монтирования окажется в union.

## Расширение пакета

Параметр загрузки `bext=` определяет расширение файла, используемое для поиска данных, фильтрации кандидатов и монтирования модулей. По умолчанию это `sb`, поэтому обычно используется суффикс кандидата `.sb`:

```text
bext=sb
```

Изменение `bext` меняет выбранный суффикс имени файла; оно не конвертирует файл и не проверяет его файловую систему. Координация с ядром — исключение: всегда ищется `01-kernel-VERSION.sb`. При пользовательском расширении обычное сканирование кандидатов не выбирает эти `.sb` модули ядра.

## Фильтры load и noload

`load=` и `noload=` — это неякорные расширенные регулярные выражения, применяемые к строкам путей кандидатов, полученным на каждом уровне. Это не списки точных имён. Простое значение вроде `kernel` совпадает с этим текстом в любой части пути, а якоря нужно указывать явно, если требуется точное положение.
Пути различаются по уровням: кандидаты верхнего уровня — это базовые имена, рекурсивные кандидаты данных включают `modules/`, а кандидаты персистентности — абсолютные пути.

Запятые преобразуются в чередование регулярных выражений. Например:

```text
load=core,kernel,firmware
```

оценивается как `core|kernel|firmware`. Другие символы регулярных выражений не экранируются.

Числовой диапазон разворачивается только если весь фильтр — это один возрастающий диапазон, совпадающий с `^[0-9]+-[0-9]+$`. Например, `load=04-06` превращается в альтернативы `04|05|06`, при этом каждое сгенерированное значение дополняется до минимум двух цифр. Диапазон, встроенный в список через запятую или другое выражение, не разворачивается и сохраняет обычное ERE-значение.

Если оба параметра присутствуют, initrd сначала применяет `load=` а затем исключает совпадения с помощью `noload=`. Таким образом, `noload=` имеет приоритет. Нет защищённого набора основных или ядровых модулей: фильтры могут исключить `00-core`, согласованные `01-kernel` или любой другой кандидат. Такой выбор может привести к неполному корню или невозможности загрузки.

## Координация с работающим ядром

Версия работающего ядра берётся из токена `vmlinuz-VERSION` в командной строке ядра, если он есть, иначе используется `uname -r`. До монтирования модулей initrd координирует этот верхнеуровневый триплет:

```text
minios/01-kernel-VERSION.sb
minios/boot/vmlinuz-VERSION
minios/boot/initrfs-VERSION.img
```

Если какой-либо элемент отсутствует, initrd ищет все три файла в:

```text
minios/kernels/VERSION/
```

Когда триплет из репозитория найден полностью, модуль копируется в `minios/` а загрузочные файлы — в `minios/boot/`. Частичная копия удаляется. Если триплет не полный, настройка ядра возвращает ошибку, но выполнение продолжается до обычного этапа монтирования модулей. В результате система может позже не загрузиться из-за отсутствия поддерживающих файлов для текущего ядра в корневой файловой системе.

Другие верхнеуровневые файлы, совпадающие с `01-kernel-*.sb` считаются неактивными. Initrd пытается переместить каждый неактивный модуль и соответствующие ему файлы `vmlinuz` и `initrfs` в `minios/kernels/VERSION/`. Эти операции резервного копирования и перемещения требуют записываемого дерева данных; отдельные ошибки перемещения не считаются фатальными. Всегда используется `.sb`, независимо от `bext=`. Смотрите [Управление ядром](/preparing-and-customizing/Managing-Kernels) для поддерживаемых сценариев установки и активации ядра.

## Построение union

MiniOS выбирает `AUFS` если работающее ядро поддерживает его, иначе используется OverlayFS. `union=overlayfs` выбирает OverlayFS. `union=aufs` запрашивает `AUFS` но при отсутствии переходит на OverlayFS. Если `AUFS` недоступен.

С `AUFS`, initrd сначала монтирует пустой union с записываемой веткой изменений, затем добавляет каждый смонтированный модуль как ветку только для чтения. Ошибка создания union — фатальна. Ошибка при добавлении отдельной ветки `AUFS` не мешает продолжить загрузку с уже добавленными ветками, а MiniOS не отмечает персистентность как активную при неполном union.

С OverlayFS полный набор модулей передаётся как один перевёрнутый список `lowerdir` при монтировании union. Записываемый слой предоставляет свой `upperdir` и `workdir`. Ошибка монтирования такого union — фатальна. Левосторонний порядок и порядок добавления `AUFS` реализуют одно правило: более поздние, с большими номерами, модули скрывают конфликтующие пути из более ранних модулей.

Эта сборка при загрузке отличается от активации во время работы. После запуска `sb activate` и `sb deactivate` могут изменять только корень, смонтированный как `AUFS`. Нижние слои OverlayFS нельзя изменить на лету. Активация во время работы не влияет на выбор Next Boot, а добавление модуля Next Boot не активирует его в текущем корне. Подробнее см. [Менеджер модулей MiniOS](/preparing-and-customizing/Managing-Modules).

## Обрезка toram

`toram=trim` создает дерево данных RAM до персистентности и координации ядра.
Копируются только следующие элементы из выбранного дерева данных MiniOS:

- `config.conf`, который требуется этим путём копирования.
- `authorized_keys` если существует как обычный файл.
- Кандидаты верхнего уровня с подходящим расширением, выбранные через `load=` и `noload=`.
- Выбранные кандидаты с подходящим расширением рекурсивно ниже `modules/`, с сохранением относительных каталогов.
- Весь каталог `changes/` при запросе персистентности в командной строке.

Не копируются `boot/`, `kernels/`, `rootcopy/`, `config.conf.d/`, журналы, другие несистемные данные, невыбранные модули или отдельный уровень модулей для записи. В частности, резервное копирование из репозитория не может использовать каталог `kernels/`, который был пропущен при обрезке дерева RAM. Копируемый набор модулей фильтруется до обнаружения уровня модулей персистентности.

Нет предварительной проверки на вместимость RAM. Ошибка копирования `config.conf` или запрошенного `changes/` завершает выполнение функции копирования, но её вызывающие функции не всегда корректно останавливают загрузку. Ошибка копирования `authorized_keys` фиксируется, но не останавливает копирование. Выбранные модули копируются через конвейер; ошибка копирования отдельного модуля фиксируется, но её статус не всегда приводит к остановке загрузки. Нет транзакционного отката частично заполненного дерева RAM.

После копирования initrd пытается размонтировать исходный раздел, удалить старый путь данных и переместить дерево RAM на это место. Только успех всей цепочки означает отсоединение источника. Если цепочка неудачна, загрузка продолжается с использованием временного пути RAM. Связанные операции отсоединения ISO и Ventoy выполняются по возможности.
Следовательно, `toram=trim` не является доказательством того, что загрузочное устройство можно извлечь. Не отключайте его, пока диагностика не подтвердит, что его файловая система, loop-устройство и device-mapper больше не смонтированы и не используются.

## Rootcopy и передача корня

После монтирования модулей и построения union initrd копирует видимое содержимое `minios/rootcopy/` прямо в собранный union. Шаблон оболочки `*` не включает записи с точкой в начале непосредственно в `rootcopy/`, хотя скрытые файлы внутри скопированной папки сохраняются при копировании каталога. Это копирование файлов в записываемый слой, а не ещё один модуль только для чтения, поэтому оно может переопределять пути, предоставленные модулями. Ошибки копирования не считаются фатальными для этой функции.

Затем MiniOS выполняет раннюю настройку, записывает `fstab` нового корня и подключает `rootcopy/run/preinit.sh` при наличии, передавая путь union первым аргументом. Этот скрипт выполняется в окружении initrd до передачи корня и должен рассматриваться как привилегированный код загрузки.

На финальной границе initrd LiveKit переключает собранный union на `/`, оставляет старый initrd в `/run/initramfs` для завершения работы и запускает `init` нового корня. В Dracut тот же union подготавливается и Dracut выполняет финальный `switch_root`. После перехода на новый корень обычная загрузка продолжается внутри собранного корня; изменение файлов на загрузочном носителе больше не пересобирает выбранный набор нижних слоёв для этой загрузки.

## Безопасная диагностика

Предпочитайте просмотр только для чтения и фиксируйте исходную командную строку перед изменением фильтров:

```bash
cat /proc/cmdline
sb next-boot
sb list
findmnt -no FSTYPE,OPTIONS /
findmnt -R /run/initramfs 2>/dev/null
```

`sb next-boot` показывает текущий выбор по правилам, а `sb list` — слои, реально составляющие работающий корень. Различие может указывать на ошибку монтирования, замену по имени, изменение во время работы `AUFS`, или источник выбора, изменившийся после загрузки.

Для ранней диагностики добавьте `debug` для вывода трассировки оболочки, `timing` для замеров этапов или `rd.break` чтобы открыть оболочку после настройки initrd и до передачи корня. В этой оболочке проверьте `/memory/data`, `/memory/bundles`, точки монтирования и `/proc/cmdline`; не выполняйте ремонт файловых систем и не извлекайте носители, пока они смонтированы. Зафиксируйте первую ошибку монтирования или копирования, а не только последующий симптом. Подробнее см. [Устранение неполадок](/maintenance-and-recovery/Troubleshooting) для более широкой безопасной диагностики.
