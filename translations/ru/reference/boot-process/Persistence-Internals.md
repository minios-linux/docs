# Внутренняя организация персистентности

На этой странице объясняются параметры загрузки `perch`, `perchdir`, `perchmode`, `perchsize` и `perchreserve`. Эти параметры определяют, где сохраняются изменения из live-сессии. Для обычного использования выберите пункт с персистентностью в загрузочном меню или воспользуйтесь Менеджером сессий MiniOS вместо ручного редактирования параметров.

MiniOS формирует live-root из модулей только для чтения и одного записываемого верхнего слоя.
initrd определяет, будет ли этот верхний слой представлять собой нумерованную персистентную сессию или временный каталог в RAM. На этой странице описывается процесс выбора и активации во время загрузки. Для пользовательских настроек смотрите разделы [Режимы загрузки](/using-minios/Boot-Modes) и [Параметры загрузки](/reference/Boot-Parameters).

## Простыми словами

Без параметра персистентности MiniOS сохраняет изменения в RAM и удаляет их при завершении работы. Параметр персистентности заставляет MiniOS найти доступное хранилище, выбрать или создать нумерованную сессию, проверить совместимость и использовать эту сессию как записываемый слой.

Запрос персистентности не гарантирует её активацию. Если целевое хранилище только для чтения, заполнено, повреждено или несовместимо, MiniOS может продолжить работу с временным слоем RAM. Перед тем как полагаться на сохранённые изменения, внимательно прочитайте предупреждение при запуске.

## Объяснение параметров

| Параметр | Что сообщает MiniOS | Типичный выбор |
|---|---|---|
| `perchdir=resume` | Открыть стандартную совместимую сессию и, при поддерживаемых условиях, создать замену, если использовать её невозможно. | Обычная ежедневная работа. |
| `perchdir=new` | Создать новую нумерованную сессию. | Сохранить существующее рабочее пространство без изменений. |
| `perchdir=ask` | Показать сохранённые сессии после обнаружения подходящего хранилища и дать выбрать одну из них. Не может создать первую сессию на пустом носителе. | Несколько рабочих пространств на одном устройстве; используйте `perchdir=new` для первой сессии. |
| `perchdir=NUMBER` | Запросить конкретную нумерованную сессию. | Стабильная пользовательская запись загрузки после проверки ID сессии. |
| `perchmode=MODE` | Выбрать `native`, `dynfilefs`, `raw`, `luks` или существующую сессию `squashfs`. | Соответствие файловой системе и требованиям шифрования. |
| `perchsize=SIZE` | Запросить размер новой или увеличиваемой контейнерной сессии. | DynFileFS, raw или LUKS-хранилище. |
| `perchreserve=MB` | Вычесть резерв при определении размера нового или увеличиваемого контейнера и задать порог предупреждения о нехватке места. | Оставить рабочее пространство при выделении контейнера; это не лимит в процессе работы. |
| `perch` | Использовать старое поведение возобновления без автоматического создания замены. | Совместимость с существующей пользовательской записью; для современных меню предпочтительнее `perchdir=resume`. |

Не используйте персистентность вместе с `toram`, если ожидаете, что изменения будут записаны обратно на исходное устройство. MiniOS активирует скопированную сессию в RAM, и изменения в этой копии будут утеряны при завершении работы.

## Персистентность включается явно

initrd включает обработку персистентности только если в командной строке ядра присутствует один из следующих распознаваемых токенов:

- `perch`
- `perchdir=...`
- `perchmode=...`
- `perchsize=...`
- `perchreserve=...`

Если ни один из этих токенов не указан, включая случай, когда присутствует только нераспознанное имя `perch...`, MiniOS создаёт новый временный верхний слой в RAM. Все изменения, сделанные в этой загрузке, будут удалены при завершении работы.

Не все селекторы эквивалентны:

| Селектор | Поведение initrd |
|---|---|
| `perch` | Пытается возобновить сессию по умолчанию из метаданных. Не создаёт новую сессию автоматически, если ни одна не подходит или не проходит проверку совместимости. |
| `perchdir=resume` | Пробует сессию по умолчанию из метаданных и может автоматически создать новую совместимую замену. Это текущее поведение загрузочного меню при возобновлении. |
| `perchdir=new` | Выделяет каталог с номером, на единицу большим, чем максимальный существующий. Никогда не использует уже существующий каталог. |
| `perchdir=ask` | Предлагает выбрать из существующих сессий после обнаружения подходящего хранилища и сессии по умолчанию. Несовместимая сессия требует подтверждения. На пустом носителе используйте `perchdir=new` для создания первой сессии. |
| `perchdir=NUMBER` | Использует указанный каталог, если он существует. Если нет — может выбрать сессию по умолчанию из метаданных; не резервирует указанный номер. |

Другие распознаваемые параметры персистентности без селектора переходят в тот же устаревший режим возобновления, что и простой `perch`: они запрашивают персистентность, но не включают автоматическое создание. Если выбор или активация не приводят к рабочему верхнему слою, загрузка продолжается с RAM и публикуется предупреждение о неудаче.

## Хранилище сессий и его расположение

Обычно хранилище — это каталог `changes` рядом с данными MiniOS, где находятся нумерованные каталоги сессий и метаданные `session.conf` или `session.json`:

```text
minios/changes/
|-- session.conf
|-- session.json
|-- 1/
`-- 2/
```

Хранилище может быть выбрано как устройство с необязательным путём. Допустимы прямой путь `/dev/...`, `/dev/disk/by-label/LABEL/...`, `/dev/mapper/...`, `label:LABEL/...`, `askdisk` и `askdisk:custom:path`. Суффикс после двоеточия становится путём внутри выбранного устройства; путь через слэш после `askdisk` приводит к потере этого пользовательского пути. Выбранный подкаталог монтируется как хранилище сессий через bind-mount. MiniOS также может обнаружить раздел персистентности на том же диске и поддерживаемое хранилище Ventoy.

Перед выбором сессии initrd должен смонтировать место для хранения с возможностью записи и убедиться, что может создать и удалить маркер в хранилище. Блочное устройство, которое нельзя открыть для записи, монтирование только для чтения, недоступный путь или неудачная тестовая запись приводят к отказу в персистентности для этой загрузки. Существующие сессии не считаются доверенными только потому, что их файлы доступны для чтения.

## Выбор и совместимость

Метаданные сессии содержат режим хранения, а также могут содержать версию, редакцию, файловую систему объединения (union) и размер контейнера. При возобновлении сравниваются сохранённые режим, версия, редакция и union с запрошенными и с текущей системой MiniOS.
Отсутствие устаревших полей совместимости не считается несовпадением.

Явное указание `perchdir=resume` создаёт новую нумерованную сессию, если по умолчанию сессия отсутствует или если несоответствие режима, версии, редакции или union делает её неподходящей. Простой `perch`, прямой выбор по номеру и другие устаревшие запросы возобновления не создают замену автоматически и продолжают работу в RAM при неудаче выбора. `perchdir=ask` показывает информацию о совместимости и позволяет явно подтвердить выбор. Новая сессия по умолчанию создаётся в режиме `native`, если не был запрошен другой режим.

Режим хранения — часть проверки совместимости. Если выбор доходит до передачи управления backend, неизвестный запрошенный режим приводит к возврату к `native`, чей probe может выбрать DynFileFS на неподходящем носителе. Существующая сессия с другим сохранённым режимом может не пройти более раннюю проверку совместимости; в этом случае устаревший запрос возобновления продолжит работу в RAM, не доходя до такого возврата.

## Резерв свободного места и размеры

MiniOS использует 256 МиБ как стандартный резерв и порог предупреждения о нехватке места. Расчёт ведётся в файловых блоках по 1024 байта. `perchreserve` принимает целое неотрицательное число без единицы измерения, ограничено 4096, и возвращается к 256 при отсутствии или ошибке. Резерв уменьшает объём, выделяемый новому или увеличиваемому контейнеру. Это не лимит: нативная сессия или последующие записи могут использовать оставшееся место на файловой системе. При загрузке появляется предупреждение, если свободное место равно или меньше порога.

Размеры контейнеров указываются в целых числах, выделяемых в МиБ:

- Простое число, `M` или `MB` — это МиБ.
- `G` или `GB` умножают число на 1000 МиБ.
- `T` или `TB` умножают число на 1 000 000 МиБ.
- Максимальный логический запрос — 1 000 000 МиБ, дополнительно ограничивается доступным местом после резерва.
- Менеджер сессий MiniOS ограничивает raw и LUKS-файлы 4000 МиБ на FAT32. При активации в initrd это ограничение надёжно применяется к LUKS, а слишком большой raw-файл может дойти до выделения и завершиться ошибкой вместо уменьшения.
- Новые raw и LUKS-сессии по умолчанию — 4000 МиБ.
- Новая сессия DynFileFS, созданная initrd, по умолчанию использует доступную ёмкость после резерва, округлённую вниз до ближайших 1000 МиБ.

Увеличение контейнера выполняется по возможности, уменьшение не поддерживается. `perchsize` не влияет на размер нативных или SquashFS сессий. Менеджер сессий MiniOS использует собственное значение по умолчанию 4000 МиБ для новых контейнерных сессий; подробнее см. [Управление сессиями](/using-minios/Sessions-and-Persistence).

## Активация хранилища

Во всех успешных режимах должен быть предоставлен записываемый верхний слой, ожидаемый выбранной файловой системой объединения. Простое монтирование backend не гарантирует, что персистентность активна. Native, DynFileFS, raw и LUKS могут обновлять метаданные персистентной сессии до проверки union; SquashFS откладывает запись этих метаданных. Защищённое состояние текущей загрузки публикуется только после того, как окончательный root union подтверждён с ожидаемым верхним слоем.

### Native

В режиме Native сначала исключаются известные не-POSIX файловые системы, такие как FAT, exFAT и NTFS. Затем проводится проверка поведения файловой системы: создаётся файл и символическая ссылка, а также проверяется изменение режима исполнения. Если проверка проходит успешно, каталог сессии с номером монтируется через bind как область для записи.

Если файловая система заведомо неподходящая или POSIX-проверка не проходит, режим Native переключается на DynFileFS. При ошибке после активации native происходит откат; новый пустой кандидат удаляется, если это безопасно.

### DynFileFS

DynFileFS, реализованный вспомогательной утилитой с поддержкой `dynblk`, хранит один логический образ блока в `changes.dat` и его нумерованные сегментные файлы. Вспомогательная утилита должна успешно смонтировать и предоставить `virtual.dat`; иначе активация завершится с ошибкой, чтобы не создать случайно только-файл RAM с именем, похожим на персистентный.

Внутри логического образа находится ext4. Существующие образы проверяются перед монтированием для записи; если результат проверки файловой системы превышает статус "исправленные ошибки", сессия отклоняется и не монтируется для записи. Увеличение размера возможно только в большую сторону, внутренний ext4 расширяется при возможности. Для диагностики пользователю смотрите [Устранение неполадок](/maintenance-and-recovery/Troubleshooting).

### Raw

В режиме Raw используется фиксированный ext4-образ `changes.img`. Новые образы выделяются и форматируются перед использованием. Существующие образы проверяются перед монтированием, могут быть увеличены до запрошенного размера, и ext4 расширяется для использования всего образа. При неудачной проверке или монтировании контейнер остаётся доступным для восстановления, а загрузка продолжается в RAM.

### LUKS

В режиме LUKS используется контейнер LUKS2 `changes.luks` с ext4 внутри.
Доступен только если в initrd есть маркер поддержки шифрования и необходимые инструменты. При создании требуется подтверждение пароля. Для существующего контейнера допускается три попытки разблокировки через консоль загрузки.

initrd выполняет аутентификацию перед увеличением существующего зашифрованного файла, затем проверяет и расширяет ext4 перед монтированием. Если создание, разблокировка, проверка, изменение размера или монтирование завершаются неудачно, MiniOS очищает маппинг и продолжает загрузку в RAM. Никогда не происходит возврата к native, DynFileFS, raw или другому незашифрованному варианту персистентности.
Пароли не сохраняются в метаданных сессии и не передаются как аргументы команд.
См. [Безопасность](/maintenance-and-recovery/Security).

### SquashFS

initrd может активировать только существующую сессию SquashFS; создать новую `changes.sb` невозможно. При активации строго проверяются однозначные метаданные снапшота: его дайджест, сжатый и несжатый размер, количество файлов, тип union и политика сохранения. Также проверяются тип файла и точный размер, доступная RAM и swap, SHA-256-дайджест до и после извлечения, а также совместимость с текущим union.

Снапшот извлекается с жёсткой обработкой ошибок и xattr во временный ограниченный ext4-образ в RAM. Для OverlayFS этот образ содержит отдельные каталоги `changes` и `workdir`; для AUFS его корень — это записываемая ветка.
Ошибочные метаданные, недостаток памяти, изменение дайджеста, ошибки извлечения или некорректная политика приводят к отказу активации и оставляют загрузку на обычном верхнем слое RAM.

Сессия с меткой `dirty` означает, что предыдущая загрузка не завершила корректный переход к чистому завершению работы. SquashFS в этом случае предупреждает и восстанавливает последний успешно сохранённый `changes.sb`; несохранённые изменения прерванной загрузки не считаются отдельным поколением отката.

Менеджер сессий MiniOS и системный backend сохранения создают и атомарно заменяют снапшоты SquashFS с точным захватом. При загрузке снапшот может быть прочитан с записываемого FAT, exFAT или NTFS, так как извлечение происходит во временный ext4-верхний слой. Создание и точное сохранение зависят от файловой системы: их staging-область должна сохранять ссылки, владельцев, режимы, xattr, ACL, capability и whiteout-файлы union, поэтому текущее сохранение требует подходящей POSIX-файловой системы. Подробнее см. [Управление сессиями](/using-minios/Sessions-and-Persistence).

## Активация union и граница восстановления

Для AUFS активированный корень изменений становится нулевой веткой для записи. Для OverlayFS initrd формирует `upperdir` и `workdir` под активированным корнем изменений и монтирует модули только для чтения как нижние каталоги. Затем initrd проверяет live-ветку AUFS или OverlayFS `upperdir` перед публикацией статуса активной персистентности.

Если backend персистентности, обновление метаданных или эта проверка завершаются неудачно, монтирования откатываются по возможности, успешное состояние персистентности не публикуется, и загрузка продолжается в RAM. Ошибка при формировании корневого union приводит к запуску аварийной оболочки initramfs. Выход из этой оболочки может позволить продолжить настройку с некорректным корнем; это не ремонт и не безопасный откат. AUFS сохраняет попытки добавления модулей в ветки, но неполный union пересекает границу восстановления: MiniOS не помечает персистентность как активную.

Ошибки проверки контейнера специально не позволяют монтировать подозрительную сессию для записи.
Не заменяйте и не восстанавливайте файлы сессии во время загрузки. Сначала сохраните затронутое хранилище; см. [Резервное копирование MiniOS](/maintenance-and-recovery/Backing-Up-MiniOS) и [Устранение неполадок](/maintenance-and-recovery/Troubleshooting).

## Активное, текущее и состояние текущей загрузки

В метаданных долговременной сессии `default=` — это **активная** сессия, выбранная для следующего возобновления, а `running=` — сессия, используемая для текущей загрузки. При активации записываются оба поля и сессия помечается как `dirty`.
После того как точки монтирования персистентности исчезают при корректном завершении работы, MiniOS удаляет `running=` и помечает сессию как `clean`.

Эти поля метаданных могут быть устаревшими после сбоя, неудачной записи метаданных, ошибки построения union, копирования хранилища или прерванного завершения работы. Компоненты, позволяющие сохранять изменения во время работы, не доверяют только `running=`. Они используют защищённое состояние текущей загрузки от initrd, привязанное к ID загрузки, номеру сессии, режиму, идентификатору хранилища, статусу записи, долговечности и подтверждённому активному поколению. Ошибка или отсутствие записи о текущей загрузке означает, что персистентность не должна рассматриваться как разрешённая цель для сохранения.

С `toram` и распознанным запросом персистентности хранилище сессий копируется в RAM перед активацией. Такая копия может быть доступна для записи и использоваться как верхний слой во время работы, но её состояние текущей загрузки помечается как недолговечное. Изменения в этой копии RAM не возвращаются на исходное устройство и теряются при завершении работы.
