# Внутренняя организация персистентности

На этой странице рассматриваются `perch`, `perchdir`, `perchmode`, `perchsize` и `perchreserve` параметры загрузки. Эти параметры определяют, где сохраняются изменения из live-сессии. Для обычного использования выберите пункт с персистентностью в меню загрузки или используйте Менеджер сессий MiniOS вместо ручного редактирования параметров.

MiniOS формирует live root из модулей только для чтения и одного записываемого верхнего слоя.
initrd определяет, будет ли этот верхний слой представлять собой пронумерованную персистентную сессию или временный каталог в RAM. На этой странице описывается процесс выбора и активации на этапе загрузки. Для пользовательских настроек см. [Режимы загрузки](/using-minios/Boot-Modes) и [Параметры загрузки](/reference/Boot-Parameters).

## Простыми словами

Без параметра персистентности MiniOS сохраняет изменения в RAM и удаляет их при завершении работы. Если задан параметр персистентности, MiniOS ищет доступное хранилище, выбирает или создает пронумерованную сессию, проверяет совместимость и использует эту сессию как записываемый слой.

Запрос персистентности не гарантирует её активацию. Если целевое хранилище только для чтения, заполнено, повреждено или несовместимо, MiniOS может продолжить работу с временным слоем RAM. Перед тем как полагаться на сохранённые изменения, обратите внимание на предупреждение при запуске.

## Пояснения к параметрам

| Параметр | Что сообщает MiniOS | Типичный выбор |
|---|---|---|
| `perchdir=resume` | Открыть стандартную совместимую сессию и, при поддерживаемых условиях, создать новую, если текущая недоступна. | Обычная ежедневная работа. |
| `perchdir=new` | Создать новую пронумерованную сессию. | Сохранить существующее рабочее пространство без изменений. |
| `perchdir=ask` | Показать сохранённые сессии после обнаружения подходящего хранилища и дать возможность выбрать одну из них. Не может создать первую сессию на пустом хранилище. | Несколько рабочих пространств на одном устройстве; используйте `perchdir=new` для первой сессии. |
| `perchdir=NUMBER` | Запросить конкретную пронумерованную сессию. | Стабильная пользовательская запись загрузки после проверки идентификатора сессии. |
| `perchmode=MODE` | Выберите `native`, `dynfilefs`, `raw`, `luks` или существующую `squashfs` сессию. | Соответствие файловой системе и требованиям к шифрованию. |
| `perchsize=SIZE` | Запросить размер новой или увеличиваемой контейнерной сессии. | DynFileFS, raw или LUKS-хранилище. |
| `perchreserve=MB` | Вычесть резерв при определении размера нового или увеличиваемого контейнера и задать порог предупреждения о нехватке места. | Оставить рабочее пространство при выделении контейнера; это не ограничение на время работы. |
| `perch` | Использовать старое поведение восстановления без автоматического создания замены. | Совместимость с существующей пользовательской записью; рекомендуется использовать `perchdir=resume` для текущих меню. |

Не сочетайте персистентность с `toram` если ожидается, что изменения будут записаны обратно на исходное устройство. MiniOS активирует скопированную сессию в RAM, и изменения в этой копии будут потеряны при завершении работы.

## Персистентность включается явно

initrd включает обработку персистентности только если в командной строке ядра присутствует один из следующих распознаваемых токенов:

- `perch`
- `perchdir=...`
- `perchmode=...`
- `perchsize=...`
- `perchreserve=...`

Если ни один из этих токенов не задан, в том числе если присутствует только нераспознанное имя `perch...` , MiniOS создаёт новый записываемый верхний слой в RAM. Все изменения, сделанные в этой загрузке, будут удалены при завершении работы.

Не все селекторы равнозначны:

| Селектор | Поведение initrd |
|---|---|
| `perch` | Пытается восстановить сессию по умолчанию из метаданных. Не создаёт новую сессию автоматически, если подходящей нет или не проходит проверку совместимости. |
| `perchdir=resume` | Пробует использовать сессию по умолчанию из метаданных и может автоматически создать новую совместимую замену. Это текущее поведение восстановления через меню загрузки. |
| `perchdir=new` | Создаёт каталог с идентификатором на единицу больше самого большого существующего. Никогда не использует уже существующий каталог повторно. |
| `perchdir=ask` | Предлагает выбрать из существующих сессий после обнаружения подходящего хранилища и значения по умолчанию. Несовместимая сессия требует подтверждения. Для пустого хранилища используйте `perchdir=new` для создания первой сессии. |
| `perchdir=NUMBER` | Использует указанный каталог, если он существует. Если нет — выбор может вернуться к значению по умолчанию из метаданных; не резервирует запрошенный номер. |

Другие распознаваемые параметры персистентности без селектора ведут по тому же устаревшему пути восстановления, что и голый `perch`: они запрашивают персистентность, но не включают автоматическое создание. Если выбор или активация не приводят к рабочему верхнему слою, загрузка продолжается с временным верхним слоем RAM и выдаёт предупреждение о неудаче.

## Хранилище сессий и его расположение

Обычное хранилище — это `changes` каталог рядом с данными MiniOS, с пронумерованными директориями сессий и `session.conf` или `session.json` метаданными:

```text
minios/changes/
|-- session.conf
|-- session.json
|-- 1/
`-- 2/
```

В качестве хранилища также можно выбрать устройство и, при необходимости, путь. Допустимы такие варианты, как прямой `/dev/...` путь, `/dev/disk/by-label/LABEL/...`, `/dev/mapper/...`, `label:LABEL/...`, `askdisk`, и `askdisk:custom:path`. Суффикс, разделённый двоеточием, становится путем внутри выбранного устройства; путь через слэш после `askdisk` не учитывает этот пользовательский путь. Выбранная поддиректория монтируется как хранилище сессии через bind-монтирование. MiniOS также может обнаружить раздел для постоянного хранения на том же диске и поддерживаемое хранилище Ventoy для постоянства.

До выбора сессии initrd должен смонтировать расположение с возможностью записи и убедиться, что может создать и удалить маркер в хранилище. Блочное устройство, которое нельзя открыть для записи, монтирование только для чтения, недоступный путь или неудачная проверка записи — всё это приведёт к отказу в использовании постоянства для этой загрузки. Существующим сессиям не доверяют только потому, что их файлы доступны для чтения.

## Выбор и совместимость

Метаданные сессии фиксируют режим хранения и могут содержать версию MiniOS, редакцию, тип union-файловой системы и размер контейнера. При восстановлении сравниваются сохранённые режим, версия, редакция и union с запрошенными и с текущей системой.
Отсутствие устаревших полей совместимости не считается несовпадением.

Явное указание `perchdir=resume` создаёт новую пронумерованную сессию, если значение по умолчанию отсутствует или если зафиксированные режим, версия, редакция или union не совпадают с текущими. Простое указание `perch`, прямой выбор по номеру и другие устаревшие запросы восстановления не создают замену автоматически и продолжают работу во временном слое RAM после неудачного выбора. `perchdir=ask` показывает информацию о совместимости и позволяет явно проигнорировать несовпадение. Новая сессия по умолчанию создаётся в режиме `native`, если не был запрошен другой режим.

Режим хранения входит в понятие совместимости. Если выбор доходит до backend dispatch, неизвестный запрошенный режим переходит к `native`, где probe может выбрать DynFileFS при неподходящем хранилище. Если у существующей сессии другой сохранённый режим, это может привести к раннему отказу по совместимости; устаревший запрос восстановления в таком случае продолжит работу во временном слое RAM без перехода к этому запасному варианту.

## Резерв пространства и размеры

MiniOS использует 256 МиБ как стандартный резерв при выделении и порог предупреждения о нехватке места. Расчёт ведётся в файловых блоках по 1024 байта. `perchreserve` принимает неотрицательное целое число без единицы измерения, ограничивает его 4096 и возвращается к 256, если значение отсутствует или некорректно. Резерв уменьшает доступное пространство для нового или увеличиваемого контейнера. Это не квота: нативная сессия или последующие записи могут занять оставшееся место на файловой системе. При загрузке появляется предупреждение, если свободного места стало меньше или равно порогу.

Размеры контейнеров задаются целыми числами в МиБ:

- Просто число, `M`, или `MB` означает МиБ.
- `G` или `GB` умножает число на 1000 МиБ.
- `T` или `TB` умножает число на 1 000 000 МиБ.
- Максимальный логический запрос — 1 000 000 МиБ, но он дополнительно ограничивается доступным пространством после резерва.
- Менеджер сессий MiniOS ограничивает размер файлов raw и LUKS 4000 МиБ на FAT32. При активации в initrd ограничение надёжно применяется к LUKS, а превышающий размер raw может дойти до выделения и завершиться ошибкой, а не быть автоматически уменьшен.
- Новые сессии raw и LUKS по умолчанию имеют размер 4000 МиБ.
- Для новых сессий DynFileFS, создаваемых в initrd, по умолчанию используется всё доступное пространство после резерва, округлённое до ближайших 1000 МиБ, если возможно.

Увеличение контейнера выполняется по возможности, уменьшение не поддерживается. `perchsize` не определяет размер для нативных или SquashFS сессий. Менеджер сессий MiniOS использует свой стандарт 4000 МиБ для новых контейнерных сессий; см. [Управление сессиями](/using-minios/Sessions-and-Persistence).

## Активация хранилища

Во всех успешных режимах должен быть предоставлен записываемый верхний слой, ожидаемый выбранной union-файловой системой. Простое монтирование backend не гарантирует активную персистентность. Native, DynFileFS, raw и LUKS могут обновлять метаданные персистентной сессии до проверки union; SquashFS откладывает запись метаданных. Защищённое состояние текущей загрузки публикуется только после того, как итоговый корневой union подтверждён с ожидаемым верхним слоем.

### Native

В режиме Native сначала исключаются известные не-POSIX файловые системы, такие как FAT, exFAT и NTFS. Затем проводится проверка поведения файловой системы: создаётся файл и символическая ссылка, а также проверяется изменение режима исполнения. Если проверка проходит успешно, каталог сессии монтируется через bind как область для записи.

Если файловая система заведомо не подходит или проверка POSIX не прошла, режим Native переключается на DynFileFS. В случае сбоя после активации native изменения откатываются; новый пустой кандидат удаляется, если это безопасно.

### DynFileFS

DynFileFS, реализованный через `dynblk`-совместимый вспомогательный модуль, хранит один логический образ блока в `changes.dat` и его пронумерованные сегментные файлы. Вспомогательный модуль должен успешно смонтировать и предоставить `virtual.dat`; иначе активация завершается ошибкой, чтобы не создать файл только для RAM с именем, похожим на персистентный.

В логическом образе используется ext4. Существующие образы проверяются до монтирования для записи; если результат проверки файловой системы выше статуса «ошибки исправлены», сессия отклоняется и не монтируется для записи. Увеличение размера поддерживается, внутренний ext4 расширяется при возможности. Для диагностики см. [Устранение неполадок](/maintenance-and-recovery/Troubleshooting).

### Raw

В режиме Raw используется фиксированный `changes.img` образ ext4. Новые образы выделяются и форматируются перед использованием. Существующие образы проверяются до монтирования, могут быть увеличены до большего размера по запросу, и ext4 расширяется для использования всего образа. В случае сбоя проверки или монтирования контейнер остаётся доступным для восстановления, а загрузка продолжается во временном слое RAM.

### LUKS

В режиме LUKS используется контейнер LUKS2 `changes.luks` с ext4 внутри.
Доступен только если в initrd есть маркер поддержки шифрования и необходимые инструменты. При создании требуется подтверждение ввода. Для существующего контейнера предоставляется три попытки разблокировки через консоль загрузки.

initrd выполняет аутентификацию перед увеличением существующего зашифрованного файла, затем проверяет и расширяет ext4 перед монтированием. В случае сбоя создания, разблокировки, проверки, изменения размера или монтирования MiniOS очищает маппинг и продолжает работу во временном слое RAM. Никогда не происходит перехода на native, DynFileFS, raw или другую незашифрованную персистентность.
Пароли не сохраняются в метаданных сессии и не передаются как аргументы команд.
См. [Безопасность](/maintenance-and-recovery/Security).

### SquashFS

initrd может активировать только существующую сессию SquashFS; создать новую `changes.sb` невозможно. При активации проверяются строгие однозначные метаданные снапшота: его дайджест, сжатый и несжатый размер, количество записей, тип union и политика сохранения. Также проверяются тип и точный размер файла, доступная RAM и swap, SHA-256 дайджест до и после извлечения, а также совместимость текущего union.

Снапшот извлекается с жёсткой обработкой ошибок и xattr во временный ограниченный образ ext4 в RAM. Для OverlayFS этот образ содержит отдельные каталоги `changes` и `workdir`; для AUFS корнем является writable-ветка.
Ошибочные метаданные, недостаток памяти, изменение дайджеста, ошибки извлечения или некорректная политика приводят к отказу активации и оставляют загрузку на обычном верхнем слое RAM.

Сессия с пометкой `dirty` означает, что предыдущая загрузка не завершила корректный переход к завершению работы. SquashFS тогда выдаёт предупреждение и восстанавливает последний успешно сохранённый `changes.sb`; несохранённые изменения прерванной загрузки не считаются отдельным поколением для отката.

Менеджер сессий MiniOS и системный backend сохранения создают и атомарно заменяют снапшоты SquashFS с точной фиксацией. При загрузке может быть прочитан существующий снапшот с записываемого FAT, exFAT или NTFS, так как извлечение происходит во временном ext4-верхнем слое. Создание и точное сохранение по-прежнему зависят от файловой системы: их собственная staging-область должна сохранять ссылки, владельцев, режимы, xattr, ACL, capabilities и union-whiteout, поэтому текущее сохранение требует подходящей POSIX-файловой системы. См. [Управление сессиями](/using-minios/Sessions-and-Persistence).

## Активация union и граница восстановления

Для AUFS активированный корень изменений становится writable-веткой с номером ноль. Для OverlayFS initrd формирует `upperdir` и `workdir` под активированным корнем изменений и монтирует модули только для чтения как нижние директории. Затем initrd проверяет live-ветку AUFS или OverlayFS `upperdir` перед публикацией статуса активной персистентности.

Если backend персистентности, обновление метаданных или эта проверка завершаются неудачно, монтирования откатываются по возможности, состояние активной персистентности не публикуется, а загрузка продолжается с временным верхним слоем RAM. Неудача при формировании корневого union приводит к запуску аварийной оболочки initramfs. Выход из этой оболочки может позволить продолжить настройку с некорректным корнем; это не ремонт и не безопасный откат. AUFS сохраняет попытки добавления модулей, но неполный union пересекает границу восстановления: MiniOS не помечает персистентность как активную.

Сбой проверки контейнера специально не допускает монтирования подозрительной сессии для записи.
Не заменяйте и не восстанавливайте файлы сессии во время загрузки. Сначала сохраните затронутое хранилище; см. [Резервное копирование MiniOS](/maintenance-and-recovery/Backing-Up-MiniOS) и [Устранение неполадок](/maintenance-and-recovery/Troubleshooting).

## Активное, текущее и состояние текущей загрузки

В долговременных метаданных сессии `default=` — это **активная** сессия, выбранная для следующего восстановления, а `running=` — сессия, зафиксированная как обслуживающая текущую загрузку. При активации оба поля записываются и эта сессия помечается как `dirty`.
После того как монтирования персистентности исчезли при корректном завершении работы, MiniOS удаляет `running=` и помечает сессию как `clean`.

Эти поля метаданных могут устареть после сбоя, неудачной записи метаданных, ошибки сборки union, копирования хранилища или прерванного завершения работы. Компоненты во время работы, которые поддерживают сохранение, не доверяют только `running=`. Они используют защищённое состояние текущей загрузки от initrd, привязанное к идентификатору загрузки, номеру сессии, режиму, реальному идентификатору хранилища, статусу записи, долговечности и проверенному активному поколению. Отсутствие или сбой записи текущей загрузки означает, что персистентность не должна считаться допустимой целью для сохранения.

С `toram` и распознанным запросом персистентности хранилище сессий копируется в RAM перед активацией. Копия сессии может быть доступна для записи и использоваться как рабочий верхний слой, но её состояние текущей загрузки помечено как недолговечное. Изменения в этой копии RAM не возвращаются на исходное устройство и теряются при завершении работы.
