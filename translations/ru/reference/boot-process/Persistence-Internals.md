# Внутренняя реализация персистентности

На этой странице объясняются `perch`, `perchdir`, `perchmode`, `perchsize`, `perchreserve`, `perchencrypt`, `perchcomp`, и `perchtoram` параметры загрузки. Эти параметры определяют, где сохраняются изменения из live-сессии, как создаётся новая сессия и копируется ли поддерживаемое хранилище сессии в RAM. Для обычного использования выберите пункт с персистентностью в загрузочном меню или воспользуйтесь Менеджер сессий MiniOS вместо ручного редактирования параметров.

MiniOS формирует live root из модулей только для чтения и одного верхнего слоя с возможностью записи.
initrd определяет, будет ли этот верхний слой пронумерованной персистентной сессией или временным каталогом в RAM. На этой странице описывается, как принимается это решение во время загрузки и как происходит активация. Для пользовательских настроек см. [Режимы загрузки](/using-minios/Boot-Modes) и [Параметры загрузки](/reference/Boot-Parameters).

## Простыми словами

Без параметра персистентности MiniOS сохраняет изменения в RAM и удаляет их при завершении работы. Если задан параметр персистентности, MiniOS ищет доступное хранилище, выбирает или создаёт пронумерованную сессию, проверяет совместимость и использует эту сессию как слой для записи.

Запрос персистентности не гарантирует её активацию. Если целевое хранилище доступно только для чтения, заполнено, повреждено или несовместимо, MiniOS может продолжить работу с временным слоем RAM. Перед тем как полагаться на сохранённые изменения, обратите внимание на предупреждение при запуске.

## Пояснение параметров

| Параметр | Что обозначает MiniOS | Обычный выбор |
|---|---|---|
| `perchdir=resume` | Открывает стандартную совместимую сессию и, при поддерживаемых условиях, создаёт замену, если она недоступна. | Обычная ежедневная работа. |
| `perchdir=setup` | Интерактивный выбор хранилища для постоянства и поддерживаемых вариантов шифрования/сжатия, затем создание новой сессии с номером. | Текущий **Начать новую сессию** элемент загрузочного меню. |
| `perchdir=new` | Создать новую сессию с номером напрямую, используя выбранный/стандартный `perchmode`, шифрование, сжатие и размер, без отображения выбора хранилища. | Скриптовые или экспертные загрузочные записи с уже заданными параметрами хранения. |
| `perchdir=ask` | Показать сохранённые сессии и дать выбрать одну. Если в хранилище нет сохранённых сессий, выборщик запускает тот же процесс настройки, что и `perchdir=setup`. | Несколько рабочих пространств на одном устройстве, включая первое интерактивное создание на пустом хранилище. |
| `perchdir=NUMBER` | Запросить определённую сессию с номером. | Стабильная пользовательская загрузочная запись после проверки ID сессии. |
| `perchmode=MODE` | Выбрать `native`, `dynfilefs`, `dynblk`, `vmdk`, `raw` или `squashfs`. | Соответствует файловой системе и выбранной модели постоянства. |
| `perchencrypt=luks` | Добавить слой LUKS2 при создании сессии Raw, DynFileFS, DynBlk или VMDK. | Зашифровать поддерживаемое хранилище-контейнер. |
| `perchsize=SIZE` | Запросить размер новой или увеличиваемой сессии-контейнера. | DynFileFS, DynBlk, VMDK или raw; шифрование не влияет на семантику размера хранилища. |
| `perchcomp=CODEC` | Выбрать сжатие бэкенда DynBlk для вновь созданной сессии DynBlk. | `none`, `lz4`, `lz4hc`, `lzo`, `lzo-rle`, `zstd`, `deflate` или `842`; доступность зависит от текущего ядра. Сжатие отключается, если LUKS оборачивает DynBlk. |
| `perchreserve=MB` | Вычесть запас при определении размера нового или увеличиваемого контейнера и задать порог предупреждения о нехватке места. | Оставляет рабочее пространство при выделении контейнера; это не ограничение в процессе работы. |
| `perch` | Использовать старое поведение восстановления без автоматического создания замены. | Совместимость с существующей пользовательской записью; рекомендуется `perchdir=resume` для текущих меню. |
| `perchtoram=off`, `perchtoram=trim`, `perchtoram=full` | Управлять копированием постоянства независимо от системы `toram`. | `off` сохраняет исходное хранилище активным; `trim` копирует только выбранную поддерживаемую сессию; `full` копирует все поддерживаемые контейнерные/сессии SquashFS. |

Если запрошено постоянство, система `toram` делает `perchtoram=trim` это значением по умолчанию, если не указан явный режим постоянства RAM. Без системы `toram`, постоянство по умолчанию сохраняется на хранилище. Скопированная сессия не является надёжной во время работы, но текущий Session Manager может явно сохранить поддерживаемое состояние на базе RAM в исходное хранилище или опубликовать его как новую сессию, если исходное хранилище доступно и совпадает с идентификатором при загрузке.

## Персистентность включается явно

initrd включает обработку персистентности только если в командной строке ядра присутствует один из этих распознаваемых токенов:

- `perch`
- `perchdir=...`
- `perchmode=...`
- `perchencrypt=...`
- `perchsize=...`
- `perchcomp=...`
- `perchreserve=...`

Если ни один из этих токенов не задан, включая случай, когда присутствует только неизвестное имя `perch...` , MiniOS создаёт новый верхний слой с возможностью записи в RAM. Все изменения, сделанные в этой загрузке, будут удалены при завершении работы.

Селекторы не равнозначны:

| Селектор | Поведение initrd |
|---|---|
| `perch` | Пытается восстановить сессию по умолчанию из метаданных. Не создаёт новую сессию автоматически, если ни одна не подходит или не проходит проверку совместимости. |
| `perchdir=resume` | Пробует сессию по умолчанию из метаданных и может автоматически создать новую совместимую замену. Это текущее поведение восстановления через загрузочное меню. |
| `perchdir=setup` | Сначала открывает выбор backend, записывает выбранные backend/шифрование/сжатие, затем переходит к созданию новой сессии. |
| `perchdir=new` | Создаёт каталог с номером на единицу больше максимального существующего. Никогда не использует существующий каталог и не открывает выбор backend. |
| `perchdir=ask` | Предлагает существующие сессии, если они есть; несовместимая существующая сессия требует подтверждения. Если в хранилище нет сессии по умолчанию, переключается на `setup` , чтобы первую сессию можно было создать интерактивно. |
| `perchdir=NUMBER` | Использует указанный каталог, если он существует. Если нет — выбор может вернуться к значению по умолчанию из метаданных; не резервирует запрошенный номер. |

Другие распознаваемые параметры персистентности без селектора переходят на тот же старый путь восстановления, что и пустой `perch`: они запрашивают персистентность, но не включают автоматическое создание. Если выбор или активация не приводят к рабочему верхнему слою, загрузка продолжается с временным верхним слоем RAM и публикуется предупреждение о сбое.

## Хранилище сессий и его расположение

Обычное хранилище — это каталог `changes` рядом с данными MiniOS, с пронумерованными каталогами сессий и `session.conf` или `session.json` метаданными:

```text
minios/changes/
|-- session.conf
|-- session.json
|-- 1/
`-- 2/
```

Вместо этого хранилище может быть выбрано как устройство с необязательным путём. Допустимые варианты включают прямой путь `/dev/...` , `/dev/disk/by-label/LABEL/...`, `/dev/mapper/...`, `label:LABEL/...`, `askdisk` и `askdisk:custom:path`. Двоеточие в конце становится путём внутри выбранного устройства; если использовать слэш после `askdisk` , этот пользовательский путь будет проигнорирован. Выбранный подкаталог монтируется как хранилище сессий через bind-mount. MiniOS также может обнаружить раздел персистентности на том же диске и поддерживаемое хранилище персистентности Ventoy.

Перед выбором сессии initrd должен смонтировать место для записи и убедиться, что может создать и удалить маркер в хранилище. Блочное устройство, которое нельзя открыть для записи, монтирование только для чтения, недоступный путь или неудачная попытка записи — всё это приведёт к отказу в использовании персистентности при данной загрузке. Существующие сессии не считаются доверенными только потому, что их файлы доступны для чтения.

## Выбор и совместимость

Метаданные сессии содержат режим хранения и могут содержать версию MiniOS, редакцию, файловую систему union и размер контейнера. При восстановлении сравниваются записанные режим, версия, редакция и union с запрошенным режимом и текущей системой.
Отсутствие старых полей совместимости не считается несовпадением.

Литерал `perchdir=resume` создаёт новую пронумерованную сессию, если стандартная отсутствует или если несоответствие режима, версии, редакции или union делает стандартную сессию неподходящей. Пустой `perch`, прямой выбор по номеру и другие старые запросы восстановления не создают замену автоматически и продолжают работу в RAM после неудачного выбора. `perchdir=ask` показывает информацию о совместимости и позволяет явно проигнорировать несовпадение. Новая сессия по умолчанию создаётся в режиме `native`, если не был запрошен другой режим.

Режим хранения — часть совместимости. Если выбор доходит до backend, неизвестный запрошенный режим возвращается к `native`, который может выбрать DynFileFS на неподходящем носителе. Существующая сессия с другим записанным режимом может не пройти более раннюю проверку совместимости; в этом случае старый запрос восстановления продолжит работу в RAM, не доходя до этого возврата.

## Резерв свободного места и размеры

MiniOS использует 256 МиБ как стандартный резерв и порог предупреждения о нехватке места. Расчёт ведётся в блоках файловой системы по 1024 байта. `perchreserve` принимает неотрицательное целое число без единицы измерения, ограничено 4096, по умолчанию 256 при отсутствии или ошибке. Резерв уменьшает доступное пространство для нового или увеличиваемого контейнера. Это не квота: нативная сессия или последующая запись могут использовать оставшееся место. При загрузке появляется предупреждение, если свободное место равно или меньше порога.

Размеры контейнеров задаются целым числом в МиБ:

- Число без суффикса, `M` или `MB` означает МиБ.
- `G` или `GB` умножает число на 1000 МиБ.
- `T` или `TB` умножает число на 1 000 000 МиБ.
- Raw-контейнеры ограничены 1 000 000 МиБ и доступным после резерва местом. DynFileFS имеет отдельное ограничение, учитывающее RAM, и жёсткий потолок 2 000 000 МиБ. DynBlk получает ограничение по геометрии из собственного формата от `dynblk limits --format dynblk`; MiniOS не накладывает отдельного потолка в 512 ГиБ.
- Raw — это один файл-хранилище, поэтому FAT32 ограничивает его размер 4000 МиБ в MiniOS. То же ограничение действует для Raw, обёрнутого в LUKS2.
- Новая raw-сессия по умолчанию имеет размер 4000 МиБ. Шифрование не создаёт отдельной политики размера LUKS: зашифрованные Raw, DynFileFS, DynBlk или VMDK-сессии используют те же правила размера, что и их backend.
- Новая сессия DynFileFS, созданная initrd без `perchsize` , использует до 16 ГиБ логической ёмкости. Если хранилище не может вместить столько после `perchreserve` и индекса DynFileFS, размер по умолчанию уменьшается до доступного. Индекс формата-400 занимает около 2 МиБ RAM и около 2 МиБ места на каждую ГиБ объявленной логической ёмкости, даже если полезная нагрузка пуста. Поэтому MiniOS также ограничивает ёмкость DynFileFS по физическому объёму RAM и жёстким потолком 2 000 000 МиБ.
- Новая сессия DynBlk без `perchsize` , также ограничивается 16 ГиБ и уменьшается, если после `perchreserve`. Явно заданный размер DynBlk — это запрос на thin-ёмкость, который проверяется по лимиту backend. Метаданные для объявленных частей создаются сразу, но место под данные выделяется по мере необходимости. DynBlk использует собственный ограниченный кэш метаданных, не зависящий от заполнения.

Рост контейнера — по возможности, уменьшение не поддерживается. `perchsize` не определяет размер нативных или SquashFS сессий. Менеджер сессий MiniOS по умолчанию создаёт raw- и DynFileFS-контейнеры размером 4000 МиБ, а DynBlk/VMDK — 16 ГиБ; для зашифрованных вариантов используются те же значения backend. См. [Управление сессиями](/using-minios/Sessions-and-Persistence).

## Активация хранилища

Все успешные backend должны предоставить верхний слой с возможностью записи, ожидаемый выбранной файловой системой union. Монтирование backend само по себе не гарантирует активную персистентность. Native, DynFileFS, DynBlk, VMDK и raw могут обновлять метаданные сессии до проверки union; SquashFS откладывает запись метаданных. Raw, DynFileFS, DynBlk и VMDK могут также использовать шифрование LUKS2. Защищённое состояние текущей загрузки публикуется только после подтверждения, что root union использует ожидаемый верхний слой.

| Backend | Постоянное представление | Модель ёмкости | Требования к хранилищу | Слой LUKS2 MiniOS |
|---|---|---|---|---|
| `native` | Файлы и каталоги непосредственно в пронумерованном каталоге сессии | Использует место на файловой системе напрямую; `perchsize` не применяется | Файловая система с возможностью записи, проходящая проверку POSIX | Нет |
| `dynfilefs` | Format-400 `changes.dat` плюс сегментные файлы, предоставляющие ext4 `virtual.dat` | Тонкая полезная нагрузка с плотным индексом по размеру ёмкости | Файловая система с возможностью записи: POSIX, FAT32, NTFS или exFAT | Да |
| `dynblk` | Format-1 `volumeNNN.db` файлы, предоставляющие `/dev/dynblkN`, поверх которых ext4 | Тонкое виртуальное блочное устройство с дисковыми отображениями и ограниченным кэшем | Файловая система, поддерживаемая ядром backend DynBlk, и достаточные ресурсы backend | Да |
| `vmdk` | `volume.vmdk` плюс раздельные разрежённые `volume-sNNN.vmdk` экстенты, предоставляемые драйвером DynBlk, поверх которых ext4 | Тонкое раздельное разрежённое виртуальное блочное устройство | Файловая система, поддерживаемая backend VMDK DynBlk и `vmdk-session-v1` поддержка | Да |
| `raw` | Один файл фиксированного размера `changes.img` , содержащий ext4 | Файл создаётся с запрошенным логическим размером; только увеличение | Файловая система с возможностью записи, способная вместить образ; FAT32 ограничен 4000 МиБ | Да |
| `squashfs` | Сжатый `changes.sb` снимок; рабочий верхний слой воссоздаётся в RAM | Размер снимка соответствует зафиксированным изменениям; `perchsize` не применяется | Существующие снимки можно читать с поддерживаемых носителей с возможностью записи; для точного сохранения требуется подходящее POSIX-хранилище персистентности | Нет |

### Нативный режим

В нативном режиме содержимое слоя union с возможностью записи хранится непосредственно в пронумерованном каталоге сессии. Нет внутреннего образа, loop-устройства, FUSE-контейнера или отдельной блочной файловой системы, поэтому ёмкость просто соответствует свободному месту на файловой системе, а `perchsize` не применяется. Это минимизирует накладные расходы контейнера и сохраняет обычную видимость файлов для восстановления и резервного копирования.

MiniOS сначала исключает известные не-POSIX файловые системы, такие как FAT, exFAT и NTFS. Затем он проверяет поведение файловой системы, создавая файл и символическую ссылку и проверяя изменение режима на исполняемый. Если проверка проходит успешно, пронумерованный каталог сессии монтируется через bind как область для записи. Если файловая система заведомо неподходящая или проверка POSIX не проходит, нативный режим переключается на DynFileFS. При ошибке после активации native откат выполняется; новый пустой кандидат удаляется, если это безопасно.

Слой персистентности LUKS2 MiniOS не применяется к нативному режиму, так как у него нет контейнера или блочного устройства для шифрования. Тем не менее, native-сессия может находиться на внешнем зашифрованном хранилище.

### DynFileFS

DynFileFS — это backend контейнера формата-400 на базе FUSE. Он предоставляет один логический `virtual.dat` образ, при этом данные хранятся в `changes.dat` плюс пронумерованные сегментные файлы. Хелпер должен успешно смонтировать и предоставить `virtual.dat`; иначе активация завершается с ошибкой, чтобы не создать файл только для RAM с постоянным именем.

Его индекс отображения плотный относительно объявленной логической ёмкости: на каждый 4-КиБ логический блок приходится один 8-байтовый offset. Это примерно 2 МиБ индекса RAM на 1 ГиБ виртуальной ёмкости, и примерно столько же хранится в индексах сегментов даже до записи полезных данных. Само выделение полезной нагрузки остаётся динамическим. Поскольку статичный бинарник initrd — i686, MiniOS также применяет ограничение по логическому размеру с учётом RAM и жёсткий потолок 2 000 000 МиБ ниже точки отказа по адресному пространству.

Внутри логического образа находится ext4. Существующие образы проверяются перед монтированием для записи; если результат проверки файловой системы выше статуса «исправленные ошибки», сессия отклоняется вместо монтирования для записи. Увеличение размера возможно только в большую сторону, при этом ext4 расширяется по возможности. Для диагностики см. [Устранение неполадок](/maintenance-and-recovery/Troubleshooting).

### DynBlk

Режим `dynblk` использует блочное устройство ядра, отдельное от DynFileFS. Каждая пронумерованная сессия владеет `volume000.db` и всеми её пронумерованными частями (`volume001.db`, ..., `volume1000.db`, и далее). Нативная разметка — `DBSPRS01`, формат диска **1**. Неподдерживаемые разметки отклоняются, а не конвертируются молча. Следите за соответствием версий CLI и модулей.

MiniOS создаёт ext4 на всём диске, возвращённом `/dev/dynblk-control` , например `/dev/dynblk3`; не предполагается, что `dynblk0` свободен. Существующий ext4 проверяется перед записью. Защищённое состояние загрузки фиксирует именно это устройство, чтобы при завершении работы отсоединять его только после закрытия всех пользователей и верхней файловой системы. Допускается несколько независимых устройств.

Менеджер сессий, установщик и initramfs запрашивают `dynblk limits --format dynblk` для получения лимита геометрии установленного backend. Текущий guard ресурсов допускает 65536 частей: стандартные 1-ГиБ логические части позволяют до 64 ТиБ. Меньшие физические лимиты частей уменьшают виртуальный предел. Это ограничение по геометрии, а не гарантия, что хост сможет открыть столько файлов или имеет достаточно RAM/места. Рост поддерживается, уменьшение — нет.

Таблицы отображения хранятся на диске. `--map-memory-mb` управляет кэшем метаданных на устройство (по умолчанию 1 МиБ, диапазон 1..64 МиБ), больше не процент от RAM или лимит на отображённые данные. Описания экстентов, векторы открытых файлов и небольшие каталоги растут с геометрией, а не с заполнением. При подключении метаданные отображения сканируются и временно восстанавливается состояние выделения по одной части; полезные данные не читаются. Полная `dynblk check` читает полезные данные. `engine_memory_bytes` не включает page cache файловой системы, внутренности кодека и другие выделения ядра.

Файлы метаданных для всех объявленных частей инициализируются при создании/расширении; фактические данные остаются тонкими. Части ограничены 4000 МиБ. Для резервного копирования сохраняйте всю отсоединённую область, не предполагая трёхзначных номеров или фиксированного последнего номера. Новый том может выбрать сжатие через `perchcomp`; при последующих загрузках используется сохранённый кодек. LUKS2 поверх DynBlk принудительно включает сжатие `none`. Частичные записи в сжатые данные сейчас перекомпрессируют соответствующий 64-КиБ grain. Истощение ресурсов или хранилища всё равно может привести к ошибкам записи; верхнюю файловую систему нужно отмонтировать перед отсоединением.

### Сессии VMDK

Режим `vmdk` сессии использует тот же драйвер с реальными `twoGbMaxExtentSparse`
образами. Основной — `volume.vmdk`, с `volume-s001.vmdk` и последующими
частями; каждая часть покрывает до 2 ГиБ логического пространства. Описание ограничено
менее 1 МиБ, поэтому длина имени файла и количество экстентов ограничивают ёмкость.
Менеджер сессий, установщик и initramfs запрашивают `dynblk limits --format vmdk`.
Нативный режим продолжает использовать `volume000.db`; ни один из режимов не переопределяет
файлы другого. Управляемые сессии не импортируют произвольный внешний VMDK с разметкой как метаданные сессии.
как метаданные сессии.

Поддержка VMDK-сессий объявляется через `vmdk-session-v1` в
`/etc/minios-initramfs-dynblk` внутри initrd. Текущее окружение и каждый
исходный initrd, копируемый установщиком, должны поддерживать этот режим. В VMDK нет собственного сжатия;
`perchcomp` игнорируется с предупреждением при загрузке, а Менеджер сессий отклоняет
не-`none` VMDK-кодек. LUKS2 остаётся отдельным дополнительным слоем шифрования. Оба режима публикуют
фактический режим сессии и владеющее `dynblk_device` в защищённом состоянии загрузки,
и обе реализации завершения работы закрывают это устройство после выхода всех пользователей.

Оба формата драйвера поддерживают `writeback`, `writethrough`, `none`, `directsync` и явные политики `unsafe`подключения. Прямые режимы требуют ext2/ext4 в качестве основы. `mount -t dynblk /path/to/image /mnt -o inner-fstype=ext4,cache=writeback` подключает существующую файловую систему; `umount` освобождает устройство, принадлежащее хелперу, после закрытия последнего пользователя. Ручной `dynblk load` имеет явный срок жизни. Это не создаёт файловую систему и не разблокирует LUKS.

### Raw

Raw-режим использует один `changes.img` файл с ext4. Длина файла устанавливается по запрошенной логической ёмкости при создании, поэтому, в отличие от динамических backend, ёмкость фиксирована до явного увеличения. Нижележащая файловая система может хранить неиспользуемые экстенты разрежённо, но MiniOS всё равно рассматривает Raw как хранилище с фиксированной ёмкостью и проверяет доступное место перед созданием или увеличением. Так как всё содержится в одном файле, FAT32 ограничивает размер 4000 МиБ.

Существующие Raw-образы проверяются с помощью `e2fsck` перед монтированием для записи. Увеличение сначала расширяет `changes.img` , затем расширяет ext4 с помощью `resize2fs`; уменьшение не поддерживается. При ошибке проверки или монтирования образ сохраняется для восстановления, а загрузка продолжается в RAM. В Raw нет демона FUSE или собственной метаданных блочного хранилища, что упрощает восстановление, но отсутствует thin-ёмкость, как у DynFileFS и DynBlk.

### Слой шифрования LUKS

LUKS2 — это дополнительный слой шифрования, выбираемый через `perchencrypt=luks` при создании Raw-, DynFileFS, DynBlk или VMDK-сессии. Существующие сессии используют состояние шифрования из метаданных; указание `perchencrypt` позже не меняет и не конвертирует уже существующую сессию без шифрования.

Граница шифрования зависит от backend: Raw подключает `changes.img` через loop-устройство и размещает LUKS2 внутри этого файла; DynFileFS подключает свой `virtual.dat` через loop-устройство и шифрует этот логический образ; DynBlk использует выделенное `/dev/dynblkN` блочное устройство напрямую; VMDK использует блочное устройство, предоставляемое тем же драйвером DynBlk для split sparse-образа. Во всех четырёх случаях MiniOS создаёт ext4 внутри `/dev/mapper/...`, поэтому содержимое файловой системы и метаданные внутри маппера зашифрованы на диске. Метаданные backend вне LUKS, дескрипторы VMDK, загрузочные файлы, метаданные сессии и другие файлы на носителе персистентности остаются незашифрованными.

Значения по умолчанию для размера, ограничения на рост, ограничения FAT32 и поведение thin/fixed-выделения определяются backend. initrd проходит аутентификацию перед увеличением существующего зашифрованного backend, закрывает маппер перед ростом backend, затем повторно открывает его, проверяет ext4 и расширяет файловую систему перед монтированием. Для зашифрованных DynBlk сжатие backend принудительно устанавливается в `none`.

При создании пароль запрашивается дважды. Существующие зашифрованные сессии допускают три попытки ввода пароля на консоли загрузки. Три неверных пароля вызывают фатальный сценарий загрузки: MiniOS не продолжает работу в RAM, не интерпретирует сессию как нешифрованную, не выбирает другой backend и не создаёт замену. Другие ошибки создания, проверки, изменения размера или монтирования сохраняют поведение восстановления backend без fallback на нешифрованный режим. Пароли не сохраняются в метаданных сессии и не передаются как аргументы команд. Экспорт логических данных содержит расшифрованные файлы сессии, а не зашифрованный образ backend.

См. [Безопасность](/maintenance-and-recovery/Security) для границ защиты и особенностей резервного копирования.

### SquashFS

initrd обычно активирует существующую сессию SquashFS. Интерактивная настройка создаёт метаданные нулевого поколения с включённым сохранением при завершении работы, но не создаёт `changes.sb`; верхний слой для записи существует только в RAM до первого сохранения системой по требованию или при завершении работы. Сессия нулевого поколения действительна только если поля артефакта снимка и `changes.sb` отсутствуют. Для последующих поколений активация проверяет строгие однозначные метаданные снимка, включая его дайджест, сжатый и несжатый размер, количество записей, тип union и политику сохранения. Также проверяется тип файла и точный размер, доступные RAM и swap, SHA-256 дайджест до и после извлечения и совместимость текущего union.

Снимок извлекается с жёсткой обработкой ошибок и xattr во временный ext4-образ с ограничением по размеру в RAM. Для OverlayFS этот образ содержит отдельные каталоги `changes` и `workdir`; для AUFS корень этого образа становится writable-веткой.
Ошибочные метаданные, недостаток памяти, изменение дайджеста, ошибки извлечения или некорректная политика приводят к неудачной активации и загрузке с обычным верхним слоем RAM.

Сессия с пометкой `dirty` означает, что предыдущая загрузка не завершила переход к чистому завершению работы. SquashFS тогда предупреждает и восстанавливает последний успешно сохранённый `changes.sb`; несохранённые изменения прерванной загрузки не считаются отдельным поколением отката.

Менеджер сессий MiniOS и системный сервис сохранения backend создают и атомарно заменяют снимки SquashFS с помощью точного захвата. При загрузке снимок может быть прочитан с поддерживаемых носителей FAT, exFAT или NTFS, так как извлечение происходит во временный ext4-верхний слой. Создание и точное сохранение зависят от файловой системы: хранилище сессий должно поддерживать создание приватной рабочей области, метаданные Linux и надёжную публикацию на подходящей POSIX-файловой системе.

При сохранении backend сначала захватывает стабильное дерево файлов в приватном tmpfs под root, если initrd предоставляет доверенный tmpfs с достаточным запасом. Если RAM недостаточно, используется предыдущая рабочая область на диске. Компрессор пишет напрямую в приватный каталог сессии с правами 0700, а не в дополнительный образ RAM с последующим копированием на диск. MiniOS проверяет сжатый результат и его идентичность, синхронизирует, перемещает во временное имя-кандидат, затем повторно валидирует и атомарно заменяет активный `changes.sb`. Неудачные копии или сжатие не заменяют последний успешный снимок.

При рабочей долговечной сессии `/var/log/minios` и `/var/log/live` bind-монтируются из `boot-logs/` внутри пронумерованной сессии. Эти диагностические логи записываются независимо от верхнего слоя RAM и снимка при завершении работы. Если хранилище персистентности не было долговечно активировано, эти логи не гарантируются после перезагрузки. Обычные логи и кэши настраиваются отдельно; см. [Производительность](/maintenance-and-recovery/Performance#reduce-cache-and-log-writes-with-perch).

SquashFS не имеет `perchsize`: его сохранённый размер соответствует сжатым изменениям, а оперативная память определяется извлечённым writable-верхом. Слой персистентности LUKS MiniOS не применяется к `changes.sb`; если нужна конфиденциальность снимка, хранилище должно быть зашифровано вне этого слоя. См. [Управление сессиями](/using-minios/Sessions-and-Persistence).

## Активация union и граница восстановления

Для AUFS активированный корень изменений становится writable-веткой с индексом 0. Для OverlayFS initrd формирует `upperdir` и `workdir` под активированным корнем изменений и монтирует модули только для чтения как нижние каталоги. Затем initrd проверяет live-ветку AUFS или OverlayFS `upperdir` перед публикацией статуса персистентности как активного.

Если backend персистентности, обновление метаданных или эта проверка завершаются с ошибкой, монтирования откатываются по возможности, статус персистентности не публикуется, и загрузка продолжается с writable-слоем RAM. Ошибка построения root union приводит к запуску initramfs shell. Выход из этой оболочки может позволить продолжить настройку с некорректным root; это не восстановление и не безопасный fallback. AUFS сохраняет попытки добавления модулей по принципу best-effort, но неполный union пересекает границу восстановления: MiniOS не помечает персистентность как активную.

Ошибки проверки контейнера намеренно не монтируют подозрительную сессию с возможностью записи.
Не заменяйте и не восстанавливайте файлы сессии при загрузке. Сначала сохраните затронутое хранилище; см. [Резервное копирование MiniOS](/maintenance-and-recovery/Backing-Up-MiniOS) и [Устранение неполадок](/maintenance-and-recovery/Troubleshooting).

## Активное, работающее и текущее состояние загрузки

В долговечных метаданных сессии `default=` — это **активная** сессия, выбранная для следующего восстановления, а `running=` — это сессия, записанная как источник текущей загрузки. Активация записывает оба поля и помечает эту сессию как `dirty`.
После удаления монтирований персистентности при чистом завершении работы MiniOS удаляет `running=` и помечает сессию как `clean`.

Эти поля метаданных могут устареть после сбоя, неудачной записи метаданных, неудачного построения union, копирования хранилища или прерванного завершения работы. Компоненты во время работы, разрешающие сохранение, не доверяют только `running=` . Они используют защищённое состояние текущей загрузки из initrd, привязанное к идентификатору загрузки, номеру сессии, режиму, фактическому идентификатору хранилища, статусу записи, долговечности, проверенному активному поколению и, для DynBlk, точному подключённому `/dev/dynblkN` устройству. Отсутствие или ошибка текущей записи загрузки означает, что персистентность не должна использоваться как целевое хранилище для сохранения.

С `perchtoram=trim` или `full` поддерживаемые контейнеры сессий копируются во временный tmpfs перед активацией. Копируемая сессия может быть writable и использоваться как рабочий верхний слой, но защищённое состояние текущей загрузки помечает её как недолговечную и записывает отдельный идентификатор `ram-origin` для исходного хранилища. `trim` копирует только выбранную поддерживаемую сессию и соответствующие метаданные; `full` копирует все поддерживаемые Raw, DynFileFS, DynBlk, VMDK или SquashFS-сессии в хранилище. Нативные сессии-каталоги не копируются. Текущий Менеджер сессий использует `ram-origin` для поиска исходного хранилища по UUID файловой системы и может явно сохранить сессию на базе RAM обратно или как новую пронумерованную сессию. Несохранённые изменения RAM всё равно будут потеряны, если не произойдёт успешная запись обратно.

Для сопутствующих инструкций см. [Режимы загрузки](/using-minios/Boot-Modes), [Параметры загрузки](/reference/Boot-Parameters), [Сессии и персистентность](/using-minios/Sessions-and-Persistence), [Резервное копирование MiniOS](/maintenance-and-recovery/Backing-Up-MiniOS), [Безопасность](/maintenance-and-recovery/Security), и [Устранение неполадок](/maintenance-and-recovery/Troubleshooting).

## Освобождение места с учётом сессий

`minios-session reclaim ID` поддерживает сессии DynFileFS, DynBlk и VMDK. Для нешифрованной сессии выполняется FITRIM на реальной внутренней ext4-файловой системе, никогда не на объединённом корне AUFS/OverlayFS, после чего вызывается операция освобождения места в backend. Для освобождения места в DynFileFS требуется ядро DynFileFS версии 4.6.0 или новее.

Для работающей сессии DynFileFS Менеджер сессий входит во временное приватное пространство монтирования, чтобы получить доступ к `virtual.dat` под live ext4 поверх монтирования, не мешая активному демону, loop-устройству или монтированиям union. Для работающих устройств DynBlk/VMDK проводится проверка по защищённому состоянию текущей загрузки. Неактивные сессии временно подключаются и монтируются; если сессия уже смонтирована Менеджером сессий, используется это подключение. Если размонтирование занято, процесс остановится, чтобы не отключать хранилище под живой файловой системой.

Ни при загрузке, ни при завершении работы автоматическая компактация не выполняется. `--compact` — это явный выбор пользователя через CLI или неотмеченную опцию в диалоге Менеджера сессий и может перемещать живые данные, увеличивая количество операций записи во flash. Без этого backend освобождает только то место, которое можно вернуть без перемещения данных, например, разрежённые диапазоны или полностью свободные хвосты файлов; на файловых системах, таких как exFAT, освобождённые внутренние диапазоны могут оставаться пригодными для повторного использования внутри контейнера, даже если не возвращаются хостовой файловой системе. Для зашифрованных сессий освобождается только место, известное backend, и не включается discard через dm-crypt без явного разрешения.
