# Внутренняя организация персистентности

На этой странице рассматриваются `perch`, `perchdir`, `perchmode`, `perchsize` и `perchreserve` параметры загрузки. Эти параметры определяют, где сохраняются изменения из live-сессии. Для обычного использования выберите пункт с персистентностью в меню загрузки или используйте Менеджер сессий MiniOS вместо ручного редактирования параметров.

MiniOS формирует live root из модулей только для чтения и одного записываемого верхнего слоя.
initrd определяет, будет ли этот верхний слой представлять собой пронумерованную персистентную сессию или временный каталог в RAM. На этой странице описывается процесс выбора и активации на этапе загрузки. Для пользовательских настроек см. [Режимы загрузки](/using-minios/Boot-Modes) и [Параметры загрузки](/reference/Boot-Parameters).

## Простыми словами

Без параметра персистентности MiniOS сохраняет изменения в RAM и удаляет их при завершении работы. Если задан параметр персистентности, MiniOS ищет доступное хранилище, выбирает или создает пронумерованную сессию, проверяет совместимость и использует эту сессию как записываемый слой.

Запрос персистентности не гарантирует её активацию. Если целевое хранилище только для чтения, заполнено, повреждено или несовместимо, MiniOS может продолжить работу с временным слоем RAM. Перед тем как полагаться на сохранённые изменения, обратите внимание на предупреждение при запуске.

## Пояснение параметров

| Параметр | Что сообщает MiniOS | Обычный выбор |
|---|---|---|
| `perchdir=resume` | Открывает стандартную совместимую сессию и, при поддерживаемых условиях, создает замену, если она недоступна. | Обычная ежедневная работа. |
| `perchdir=new` | Создать новую сессию с номером. | Оставить существующее рабочее пространство без изменений. |
| `perchdir=ask` | Показать сохранённые сессии после обнаружения хранилища с возможностью восстановления и дать выбрать одну из них. Не может создать первую сессию при пустом хранилище. | Несколько рабочих пространств на одном устройстве; используйте `perchdir=new` для первой сессии. |
| `perchdir=NUMBER` | Запросить конкретную сессию по номеру. | Постоянная пользовательская загрузка после проверки ID сессии. |
| `perchmode=MODE` | Выберите `native`, `dynfilefs`, `dynblk`, `raw` или `squashfs`. | Соответствует файловой системе и выбранной модели сохранения данных. |
| `perchencrypt=luks` | Добавляет слой LUKS2 при создании сессии Raw, DynFileFS или DynBlk. | Шифрует поддерживаемый контейнерный бэкенд. |
| `perchsize=SIZE` | Запросить размер новой или расширяемой сессии-контейнера. | DynFileFS, DynBlk или raw; шифрование не влияет на размер бэкенда. |
| `perchcomp=CODEC` | Выбрать сжатие бэкенда DynBlk для вновь создаваемой сессии DynBlk. | `none`, `lz4`, `lz4hc`, `lzo`, `lzo-rle`, `zstd`, `deflate` или `842`; доступность зависит от используемого ядра. Сжатие отключается, если LUKS используется поверх DynBlk. |
| `perchreserve=MB` | Вычитает резерв при определении размера нового или расширяемого контейнера и устанавливает порог предупреждения о нехватке места. | Оставляет рабочее пространство при выделении контейнера; это не лимит на время работы. |
| `perch` | Использовать старое поведение восстановления без автоматического создания замены. | Совместимость с существующей пользовательской записью; для текущих меню предпочтительнее `perchdir=resume`. |

Не совмещайте сохранение данных с `toram` если ожидается, что изменения будут записаны обратно на исходное устройство. MiniOS активирует копию сессии в RAM, и все изменения в этой копии будут потеряны при завершении работы.

## Управление постоянством выполняется явно

initrd включает обработку постоянства только если в командной строке ядра присутствует один из следующих распознаваемых токенов:

- `perch`
- `perchdir=...`
- `perchmode=...`
- `perchencrypt=...`
- `perchsize=...`
- `perchcomp=...`
- `perchreserve=...`

Если ни один из этих токенов не указан, включая случаи, когда присутствует только нераспознанное `perch...` имя, MiniOS создает новый доступный для записи upper в RAM. Все изменения, внесённые в ходе этой загрузки, будут удалены при завершении работы.

Селекторы работают по-разному:

| Селектор | Поведение initrd |
|---|---|
| `perch` | Пытается восстановить значение по умолчанию из метаданных. Не создает новую сессию автоматически, если подходящей нет или проверка совместимости не пройдена. |
| `perchdir=resume` | Пробует значение по умолчанию из метаданных и может автоматически создать новую совместимую замену. Это текущее поведение восстановления через загрузочное меню. |
| `perchdir=new` | Создаёт каталог с числовым идентификатором, который на единицу больше самого большого существующего ID. Никогда не использует уже существующий каталог повторно. |
| `perchdir=ask` | Предлагает существующие сессии после обнаружения подходящего хранилища и значения по умолчанию. Если найденная сессия несовместима, требуется подтверждение. Если хранилище пустое, используйте `perchdir=new` для создания первой сессии. |
| `perchdir=NUMBER` | Использует этот каталог, если он существует. Если нет — выбор может быть перенаправлен на значение по умолчанию, записанное в метаданных; запрошенный номер не резервируется. |

Другие распознаваемые параметры постоянства без селектора переходят по тому же устаревшему пути восстановления, что и простой `perch`: они запрашивают постоянство, но не включают автоматическое создание. Если выбор или активация не приводят к созданию подходящего upper, загрузка продолжается с использованием RAM upper и отображается предупреждение о сбое.

## Хранилище сессий и его расположение

Обычное хранилище — это `changes` каталог рядом с данными MiniOS, с пронумерованными директориями сессий и `session.conf` или `session.json` метаданными:

```text
minios/changes/
|-- session.conf
|-- session.json
|-- 1/
`-- 2/
```

В качестве хранилища также можно выбрать устройство и, при необходимости, путь. Допустимы такие варианты, как прямой `/dev/...` путь, `/dev/disk/by-label/LABEL/...`, `/dev/mapper/...`, `label:LABEL/...`, `askdisk`, и `askdisk:custom:path`. Суффикс, разделённый двоеточием, становится путем внутри выбранного устройства; путь через слэш после `askdisk` не учитывает этот пользовательский путь. Выбранная поддиректория монтируется как хранилище сессии через bind-монтирование. MiniOS также может обнаружить раздел для постоянного хранения на том же диске и поддерживаемое хранилище Ventoy для постоянства.

До выбора сессии initrd должен смонтировать расположение с возможностью записи и убедиться, что может создать и удалить маркер в хранилище. Блочное устройство, которое нельзя открыть для записи, монтирование только для чтения, недоступный путь или неудачная проверка записи — всё это приведёт к отказу в использовании постоянства для этой загрузки. Существующим сессиям не доверяют только потому, что их файлы доступны для чтения.

## Выбор и совместимость

Метаданные сессии фиксируют режим хранения и могут содержать версию MiniOS, редакцию, тип union-файловой системы и размер контейнера. При восстановлении сравниваются сохранённые режим, версия, редакция и union с запрошенными и с текущей системой.
Отсутствие устаревших полей совместимости не считается несовпадением.

Явное указание `perchdir=resume` создаёт новую пронумерованную сессию, если значение по умолчанию отсутствует или если зафиксированные режим, версия, редакция или union не совпадают с текущими. Простое указание `perch`, прямой выбор по номеру и другие устаревшие запросы восстановления не создают замену автоматически и продолжают работу во временном слое RAM после неудачного выбора. `perchdir=ask` показывает информацию о совместимости и позволяет явно проигнорировать несовпадение. Новая сессия по умолчанию создаётся в режиме `native`, если не был запрошен другой режим.

Режим хранения входит в понятие совместимости. Если выбор доходит до backend dispatch, неизвестный запрошенный режим переходит к `native`, где probe может выбрать DynFileFS при неподходящем хранилище. Если у существующей сессии другой сохранённый режим, это может привести к раннему отказу по совместимости; устаревший запрос восстановления в таком случае продолжит работу во временном слое RAM без перехода к этому запасному варианту.

## Резерв пространства и размеры

MiniOS использует 256 MiB в качестве стандартного резерва и порога предупреждения о нехватке места. Расчёт ведётся в файловых блоках по 1024 байта.`perchreserve` принимает неотрицательное целое число без единицы измерения, ограничивается 4096 и возвращается к 256, если значение отсутствует или некорректно. Резерв уменьшает объём пространства, доступного для нового или увеличивающегося контейнера. Это не квота: нативная сессия или последующие записи всё равно могут использовать оставшееся место на файловой системе. При запуске появляется предупреждение, если свободного пространства осталось не больше порогового значения.

Размеры контейнеров задаются целыми числами, которые выделяются в MiB:

- Число без единицы, `M`, или `MB` означает MiB.
- `G` или `GB` умножает число на 1000 MiB.
- `T` или `TB` умножает число на 1 000 000 MiB.
- Raw-контейнеры ограничены 1 000 000 MiB и доступным после резерва пространством. DynFileFS имеет отдельный лимит, учитывающий RAM, и жёсткий потолок в 2 000 000 MiB. Для DynBlk действует собственный лимит формата/ABI — 512 GiB.
- Raw — это один файл-хранилище, поэтому FAT32 ограничивает его размером 4000 MiB в MiniOS. Такое же ограничение действует, если Raw используется внутри LUKS2.
- Новая raw-сессия по умолчанию создаётся размером 4000 MiB. Шифрование не задаёт отдельную политику размера для LUKS: зашифрованная Raw-, DynFileFS- или DynBlk-сессия использует правила размера своего базового хранилища.
- Новая сессия DynFileFS, созданная через initrd, без `perchsize` использует до 16 GiB логической ёмкости. Если базовое хранилище не сможет вместить такой объём после `perchreserve` и накладных расходов индекса DynFileFS, по умолчанию устанавливается доступная ёмкость. Индекс формата-400 занимает около 2 MiB RAM и примерно 2 MiB дискового пространства на каждый GiB заявленной логической ёмкости, даже если полезная нагрузка пуста. Поэтому MiniOS также ограничивает ёмкость DynFileFS исходя из физического RAM и тестируемого жёсткого лимита в 2 000 000 MiB.
- Новая сессия DynBlk без `perchsize` также использует автоматический лимит в 16 GiB, который уменьшается, если после `perchreserve` остаётся меньше места. Явно заданный виртуальный размер DynBlk по-прежнему является запросом на тонкое выделение и ограничивается только лимитом формата/ABI в 512 GiB; физические файлы-хранилища создаются по мере необходимости. DynBlk использует собственную политику по управлению разреженной памятью и не требует от MiniOS задания этого бюджета.

Увеличение размера контейнера выполняется по возможности, уменьшение не поддерживается.`perchsize` не определяет размер для нативных или SquashFS-сессий. Менеджер сессий MiniOS по умолчанию устанавливает вручную созданные raw- и DynFileFS-контейнеры на 4000 MiB, а DynBlk — на 16 GiB; для зашифрованных вариантов действуют те же значения по умолчанию для соответствующих хранилищ. Подробнее см. в разделе [Управление сессиями](/using-minios/Sessions-and-Persistence).

## Активация хранилища

Все успешно подключённые бэкенды должны предоставлять доступную для записи верхнюю директорию, ожидаемую выбранной объединяющей файловой системой. Монтирование бэкенда само по себе не гарантирует активность постоянного хранения. Форматы Native, DynFileFS, DynBlk и raw могут обновлять метаданные постоянной сессии до проверки объединения; SquashFS откладывает запись этих метаданных. Raw, DynFileFS и DynBlk дополнительно поддерживают шифрование LUKS2. Защищённое состояние текущей загрузки публикуется только после подтверждения использования ожидаемой верхней директории в финальном объединении корня.

| Бэкенд | Постоянное представление | Модель ёмкости | Требования к базовому хранилищу | MiniOS слой LUKS2 |
|---|---|---|---|---|
| `native` | Файлы и каталоги непосредственно в пронумерованной директории сессии | Использует пространство базовой файловой системы напрямую; `perchsize` не применяется | Файловая система с поддержкой записи, проходящая проверку POSIX-совместимости | Нет |
| `dynfilefs` | Формат-400 `changes.dat` плюс сегментные файлы, предоставляющие ext4 `virtual.dat` | Компактный контейнер с плотным индексом по размеру ёмкости | Хранилище с поддержкой записи: POSIX, FAT32, NTFS или exFAT | Да |
| `dynblk` | Формат-1 `volumeNNN.db` файлы, предоставляющие `/dev/dynblkN`, с ext4 поверх | Виртуальное блочное устройство с тонкой настройкой и разреженными отображениями во время работы | Файловая система, поддерживаемая ядром бэкенда DynBlk, и достаточные ресурсы бэкенда | Да |
| `raw` | Один файл фиксированного размера `changes.img` с ext4 внутри | Файл создаётся с заданным логическим размером; возможен только рост | Файловая система с поддержкой записи, способная хранить образ; для FAT32 ограничение — 4000 Миб | Да |
| `squashfs` | Сжатый `changes.sb` снимок; рабочая область для записи восстанавливается в RAM | Размер снимка определяется зафиксированными изменениями; `perchsize` не применяется | Существующие снимки можно читать с поддерживаемых носителей с записью, но для точного сохранения требуется промежуточная файловая система с поддержкой POSIX | Нет |

### Режим Native

В режиме Native содержимое записываемого объединённого слоя сохраняется напрямую в пронумерованной директории сессии. Здесь не используется внутренний образ, loop-устройство, контейнер FUSE или отдельная блочная файловая система, поэтому объём определяется только свободным местом на основной файловой системе, а `perchsize` не применяется. Это обеспечивает минимальные накладные расходы контейнера и сохраняет обычную видимость файлов для восстановления и резервного копирования.

MiniOS сначала исключает известные не-POSIX файловые системы, такие как FAT, exFAT и NTFS. Затем он проверяет поведение реальной файловой системы, создавая файл и символическую ссылку и проверяя изменение режима исполнения. Если проверка проходит успешно, пронумерованная директория сессии монтируется напрямую как область для записи. Если файловая система заведомо не подходит или POSIX-проверка неудачна, режим native переключается на DynFileFS. В случае сбоя после активации native происходит откат; новый пустой кандидат удаляется, когда это безопасно.

Слой персистентности LUKS2 MiniOS не применяется к режиму native, так как в native нет контейнера или блочного устройства, которое можно было бы зашифровать. Тем не менее, native-персистентность может находиться на хранилище, зашифрованном вне этого слоя персистентности.

### DynFileFS

DynFileFS — это контейнерный бэкенд формата 400 на основе FUSE. Он предоставляет один логический `virtual.dat` образ, при этом данные хранятся в `changes.dat` плюс пронумерованных сегментных файлах. Вспомогательная утилита должна успешно смонтировать и предоставить `virtual.dat`; в противном случае активация завершится с ошибкой, чтобы не создать случайно только RAM-файл с именем, похожим на постоянный.

Его индекс отображения плотный относительно объявленной логической ёмкости: каждый 4-КиБ логический блок имеет одно 8-байтное смещение. Это примерно 2 МБ индекса RAM на 1 ГиБ виртуальной ёмкости, и примерно столько же хранится в индексах сегментов-носителей ещё до записи полезных данных. Выделение полезной нагрузки остаётся динамическим. Поскольку статический бинарный initrd — i686, MiniOS также применяет ограничение по логическому размеру с учётом RAM и жёсткий потолок в 2 000 000 МиБ, что ниже проверенной точки отказа адресного пространства.

Логический образ содержит ext4. Существующие образы проверяются перед монтированием в режиме записи; если результат проверки файловой системы превышает статус «исправленные ошибки», сессия отклоняется и не монтируется для записи. Изменение размера возможно только в большую сторону, и внутренняя файловая система ext4 расширяется при возможности. Для диагностики, ориентированной на пользователя, см. [Устранение неполадок](/maintenance-and-recovery/Troubleshooting).

### DynBlk

Режим `dynblk` представляет собой бэкенд блочного устройства ядра, отдельный от DynFileFS. Каждая сессия с уникальным номером владеет `volume000.db` пространством имён, в котором тома создаются по мере необходимости, от `volume001.db` до `volume063.db`. При подключении тома через `/dev/dynblk-control` возвращается динамически выделенное блочное устройство целого диска, например `/dev/dynblk0` или `/dev/dynblk3`; MiniOS должен использовать только возвращённое устройство и не должен предполагать, что `dynblk0` свободно. Можно одновременно подключить несколько томов DynBlk.

MiniOS создаёт ext4 непосредственно на устройстве целого диска DynBlk, проверяет существующий ext4 перед записью и поддерживает увеличение объёма до лимита формата 1 — 512 ГиБ. Уменьшение размера не поддерживается. Защищённое состояние загрузки фиксирует точное `/dev/dynblkN` устройство, используемое в текущей постоянной сессии, чтобы при завершении работы отсоединялось именно оно после размонтирования файловой системы. Это остаётся корректным даже при временном параллельном подключении другой сессии DynBlk через Session Manager.

Виртуальная ёмкость реализована по принципу thin provisioning: пространство на хосте не выделяется заранее, не используется отображение RAM. DynBlk хранит 128 логических отображений по 4 КиБ в каждом 4-КиБ чанке во время работы, поэтому плотное отображение памяти составляет примерно 8 МБ на 1 ГиБ. Указатели дерева уровня 0 хранятся вместе с этими разрежёнными чанками; фиксированный индекс внутренних узлов — 396 312 байт на каждое подключённое устройство, а счётчики ссылок на физические страницы выделяются по мере необходимости чанками по 4 КиБ, каждый из которых покрывает 8 МБ базового пространства. Если явный лимит отображения не задан, драйвер DynBlk сам выбирает примерно 25% доступной RAM по данным ядра после нормализации до 64 МБ, но не более 4096 МБ. MiniOS оставляет эту политику на усмотрение драйвера.

Новый том DynBlk может использовать бэкенд-сжатие, выбранное через `perchcomp`. Сжатие — это свойство формата хранения DynBlk и оно фиксируется для тома при создании. Если LUKS2 оборачивает DynBlk, MiniOS принудительно устанавливает сжатие DynBlk в `none`, так как слой шифрования находится выше устройства DynBlk. Фактическая запись может завершиться неудачей из-за нехватки свободного места в нижележащей файловой системе, ограничений пространства в 64-частной базе или отказа в размещении отображения DynBlk. Неудачные или заблокированные устройства отсоединяются только после размонтирования верхней файловой системы; при восстановлении формат проверяется при следующем подключении.

### Raw

Режим Raw использует один `changes.img` файл с ext4. Длина файла устанавливается в соответствии с запрошенной логической ёмкостью при создании, поэтому, в отличие от динамических бэкендов, сама ёмкость фиксирована до явного увеличения. Нижележащая файловая система может хранить неинициализированные области разреженно, но MiniOS всё равно рассматривает Raw как хранилище с фиксированной ёмкостью и проверяет наличие свободного места перед созданием или увеличением. Поскольку всё содержится в одном файле на хосте, для FAT32 действует ограничение 4000 МиБ.

Существующие образы Raw проверяются с помощью `e2fsck` перед монтированием в режиме записи. Увеличение сначала расширяет `changes.img`, а затем расширяет ext4 с помощью `resize2fs`; уменьшение не поддерживается. При неудачной проверке или монтировании образ сохраняется для восстановления, а загрузка продолжается в RAM. В Raw нет демона FUSE или собственной метаинформации блочного хранилища, что упрощает восстановление, но отсутствует поддержка динамического выделения ёмкости, как у DynFileFS и DynBlk.

### Слой шифрования LUKS

LUKS2 — это дополнительный слой шифрования, который можно выбрать с помощью `perchencrypt=luks` при создании сессии Raw, DynFileFS или DynBlk. Для существующих сессий состояние шифрования определяется метаданными сессии; указание `perchencrypt` позже не изменяет и не конвертирует уже существующую сессию без шифрования.

Граница шифрования зависит от выбранного бэкенда: Raw подключает `changes.img` через loop-устройство и размещает LUKS2 внутри этого файла; DynFileFS подключает свой видимый `virtual.dat` через loop-устройство и шифрует этот логический образ; DynBlk использует `/dev/dynblkN` блочное устройство напрямую как источник для LUKS2. Во всех трёх случаях MiniOS создаёт ext4 внутри `/dev/mapper/...`, поэтому содержимое и метаданные файловой системы внутри mapper зашифрованы на диске. Метаданные бэкенда вне границы LUKS, загрузочные файлы, метаданные сессии и другие файлы на носителе остаются незашифрованными.

Параметры размера, ограничения на рост, ограничения FAT32 и поведение при тонком/фиксированном выделении относятся к исходному бэкенду. initrd выполняет аутентификацию перед увеличением размера уже зашифрованного бэкенда, закрывает mapper перед расширением бэкенда, затем повторно открывает его, проверяет ext4 и расширяет файловую систему перед монтированием. Для зашифрованных DynBlk сжатие на уровне бэкенда принудительно устанавливается в `none`.

При создании система дважды запрашивает парольную фразу. Для существующих зашифрованных сессий на загрузочной консоли допускается три попытки ввода пароля. Три неверных ввода приводят к фатальному сценарию загрузки: MiniOS не продолжает работу в RAM, не переводит текущую сессию в режим без шифрования, не выбирает другой бэкенд и не создаёт замену. Остальные ошибки при создании, проверке, изменении размера или монтировании обрабатываются стандартными для бэкенда способами восстановления без перехода в режим без шифрования. Парольные фразы не сохраняются в метаданных сессии и не передаются как аргументы команд. При логическом экспорте содержатся расшифрованные файлы сессии, а не образ зашифрованного бэкенда.

См. [Безопасность](/maintenance-and-recovery/Security) для информации о границах защиты и резервном копировании.

### SquashFS

Обычно initrd активирует существующую сессию SquashFS. Интерактивная настройка создает метаданные нулевого поколения с включённым сохранением при завершении работы, но не создаёт `changes.sb`; записываемый верхний слой существует только в RAM до тех пор, пока работающая система не выполнит первое сохранение по требованию или при завершении работы. Сессия нулевого поколения считается действительной только при отсутствии полей артефакта снимка и `changes.sb`. Для последующих поколений при активации проверяются строгие, однозначные метаданные снимка, включая его дайджест, сжатый и несжатый размеры, количество записей, тип union и политику сохранения. Также проверяется тип файла и точный размер, доступные RAM и swap, SHA-256-дайджест до и после извлечения, а также текущая совместимость union.

Снимок извлекается с строгой обработкой ошибок и xattr во временный, ограниченный по размеру образ ext4 в RAM. Для OverlayFS этот образ содержит отдельные `changes` и `workdir` директории; для AUFS корень этого образа является записываемой веткой.
Некорректные метаданные, недостаток памяти, изменение дайджеста, ошибки извлечения или неверная политика приводят к сбою активации и оставляют загрузку на обычном верхнем слое RAM.

Сессия с пометкой `dirty` означает, что предыдущая загрузка не завершила переход к чистому завершению работы. SquashFS в этом случае предупреждает и восстанавливает последний успешно сохранённый `changes.sb`; несохранённые изменения из прерванной загрузки не считаются отдельным поколением для отката.

Менеджер сессий MiniOS и системный бэкенд сохранения создают и атомарно заменяют снимки SquashFS с точной фиксацией. При активации загрузки существующий снимок может быть считан с записываемых носителей FAT, exFAT или NTFS, так как извлечение происходит во временный верхний слой ext4. Создание и точное сохранение по-прежнему зависят от файловой системы: их приватная staging-область должна сохранять ссылки, владельцев, режимы, xattr, ACL, capabilities и union-whiteout, поэтому текущее сохранение требует подходящей POSIX-совместимой файловой системы.

У SquashFS нет `perchsize`: его сохранённый размер соответствует сжатым зафиксированным изменениям, а объём памяти во время работы определяется извлечённым записываемым верхним слоем. Слой LUKS-персистентности MiniOS не оборачивает `changes.sb`; если требуется конфиденциальность снимка, хранилище должно быть зашифровано вне этого слоя. См. [Управление сессиями](/using-minios/Sessions-and-Persistence).

## Активация union и граница восстановления

Для AUFS активированный корень изменений становится writable-веткой с номером ноль. Для OverlayFS initrd формирует `upperdir` и `workdir` под активированным корнем изменений и монтирует модули только для чтения как нижние директории. Затем initrd проверяет live-ветку AUFS или OverlayFS `upperdir` перед публикацией статуса активной персистентности.

Если backend персистентности, обновление метаданных или эта проверка завершаются неудачно, монтирования откатываются по возможности, состояние активной персистентности не публикуется, а загрузка продолжается с временным верхним слоем RAM. Неудача при формировании корневого union приводит к запуску аварийной оболочки initramfs. Выход из этой оболочки может позволить продолжить настройку с некорректным корнем; это не ремонт и не безопасный откат. AUFS сохраняет попытки добавления модулей, но неполный union пересекает границу восстановления: MiniOS не помечает персистентность как активную.

Сбой проверки контейнера специально не допускает монтирования подозрительной сессии для записи.
Не заменяйте и не восстанавливайте файлы сессии во время загрузки. Сначала сохраните затронутое хранилище; см. [Резервное копирование MiniOS](/maintenance-and-recovery/Backing-Up-MiniOS) и [Устранение неполадок](/maintenance-and-recovery/Troubleshooting).

## Активное, работающее и текущее состояние загрузки

В метаданных устойчивой сессии, `default=` — это **активная** сессия, выбранная для следующего возобновления, а `running=` — это сессия, зафиксированная как обеспечивающая текущую загрузку. При активации обе эти записи обновляются, и сессия помечается как `dirty`.
После того как точки монтирования персистентности исчезают при корректном завершении работы, MiniOS удаляет `running=` и помечает сессию как `clean`.

Эти поля метаданных могут устареть после сбоя, неудачной записи метаданных, неудачного построения объединения, копирования хранилища или прерванного завершения работы. Компоненты среды выполнения, которые поддерживают сохранение, не доверяют только `running=` этим данным. Они используют защищённое состояние текущей загрузки initrd, связанное с идентификатором загрузки, номером сессии, режимом, фактической идентичностью хранилища, возможностью записи, уровнем устойчивости, подтверждённым активным поколением и, для DynBlk, точным подключённым `/dev/dynblkN` устройством. Отсутствие или повреждение записи о текущей загрузке означает, что персистентность не может использоваться как разрешённая цель для сохранения.

При использовании `toram` и распознанном запросе на персистентность хранилище сессии копируется в RAM перед активацией. Скопированная сессия может быть доступна для записи и использоваться как рабочий верхний слой, но её состояние текущей загрузки помечается как неустойчивое. Изменения в этой копии RAM не возвращаются на исходное устройство и теряются при завершении работы.
