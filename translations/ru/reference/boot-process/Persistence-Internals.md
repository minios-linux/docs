# Внутренняя организация персистентности

На этой странице рассматриваются `perch`, `perchdir`, `perchmode`, `perchsize` и `perchreserve` параметры загрузки. Эти параметры определяют, где сохраняются изменения из live-сессии. Для обычного использования выберите пункт с персистентностью в меню загрузки или используйте Менеджер сессий MiniOS вместо ручного редактирования параметров.

MiniOS формирует live root из модулей только для чтения и одного записываемого верхнего слоя.
initrd определяет, будет ли этот верхний слой представлять собой пронумерованную персистентную сессию или временный каталог в RAM. На этой странице описывается процесс выбора и активации на этапе загрузки. Для пользовательских настроек см. [Режимы загрузки](/using-minios/Boot-Modes) и [Параметры загрузки](/reference/Boot-Parameters).

## Простыми словами

Без параметра персистентности MiniOS сохраняет изменения в RAM и удаляет их при завершении работы. Если задан параметр персистентности, MiniOS ищет доступное хранилище, выбирает или создает пронумерованную сессию, проверяет совместимость и использует эту сессию как записываемый слой.

Запрос персистентности не гарантирует её активацию. Если целевое хранилище только для чтения, заполнено, повреждено или несовместимо, MiniOS может продолжить работу с временным слоем RAM. Перед тем как полагаться на сохранённые изменения, обратите внимание на предупреждение при запуске.

## Пояснение параметров

| Параметр | Что сообщает MiniOS | Типичный выбор |
|---|---|---|
| `perchdir=resume` | Открывает стандартную совместимую сессию и, при поддерживаемых условиях, создает замену, если она недоступна. | Обычная ежедневная работа. |
| `perchdir=new` | Создать новую сессию с номером. | Сохранить существующее рабочее пространство без изменений. |
| `perchdir=ask` | Показать сохранённые сессии после обнаружения возобновляемого хранилища и предоставить выбор. Не может создать первую сессию на пустом хранилище. | Несколько рабочих пространств на одном устройстве; используйте `perchdir=new` для первой сессии. |
| `perchdir=NUMBER` | Запросить конкретную сессию по номеру. | Стабильная пользовательская загрузка после проверки идентификатора сессии. |
| `perchmode=MODE` | Выберите `native`, `dynfilefs`, `dynblk`, `vmdk`, `raw`, или `squashfs`. | Выберите файловую систему и желаемую модель сохранения данных. |
| `perchencrypt=luks` | Добавить слой LUKS2 при создании Raw, DynFileFS, DynBlk или VMDK-сессии. | Зашифровать поддерживаемый контейнерный backend. |
| `perchsize=SIZE` | Запросить размер новой или увеличивающейся контейнерной сессии. | DynFileFS, DynBlk, VMDK или raw; шифрование не изменяет правила расчёта размера backend. |
| `perchcomp=CODEC` | Выбрать сжатие backend DynBlk для новой сессии DynBlk. | `none`, `lz4`, `lz4hc`, `lzo`, `lzo-rle`, `zstd`, `deflate`, или `842`; доступность всё равно зависит от текущего ядра. Сжатие отключается, если LUKS оборачивает DynBlk. |
| `perchreserve=MB` | Вычесть запас при расчёте размера нового или увеличивающегося контейнера и установить порог предупреждения о нехватке места. | Оставить рабочее пространство при выделении контейнера; это не ограничение по квоте во время работы. |
| `perch` | Использовать старое поведение возобновления без автоматического создания замены. | Совместимость с существующей пользовательской записью; рекомендуется использовать `perchdir=resume` для текущих меню. |

Не сочетайте постоянство с `toram` если ожидается, что изменения будут записаны обратно на исходное устройство. MiniOS активирует скопированную сессию в RAM, и все изменения в этой копии будут утеряны при завершении работы.

## Управление постоянством выполняется явно

initrd включает обработку постоянства только если в командной строке ядра присутствует один из следующих распознаваемых токенов:

- `perch`
- `perchdir=...`
- `perchmode=...`
- `perchencrypt=...`
- `perchsize=...`
- `perchcomp=...`
- `perchreserve=...`

Если ни один из этих токенов не указан, включая случаи, когда присутствует только нераспознанное `perch...` имя, MiniOS создает новый доступный для записи upper в RAM. Все изменения, внесённые в ходе этой загрузки, будут удалены при завершении работы.

Селекторы работают по-разному:

| Селектор | Поведение initrd |
|---|---|
| `perch` | Пытается восстановить значение по умолчанию из метаданных. Не создает новую сессию автоматически, если подходящей нет или проверка совместимости не пройдена. |
| `perchdir=resume` | Пробует значение по умолчанию из метаданных и может автоматически создать новую совместимую замену. Это текущее поведение восстановления через загрузочное меню. |
| `perchdir=new` | Создаёт каталог с числовым идентификатором, который на единицу больше самого большого существующего ID. Никогда не использует уже существующий каталог повторно. |
| `perchdir=ask` | Предлагает существующие сессии после обнаружения подходящего хранилища и значения по умолчанию. Если найденная сессия несовместима, требуется подтверждение. Если хранилище пустое, используйте `perchdir=new` для создания первой сессии. |
| `perchdir=NUMBER` | Использует этот каталог, если он существует. Если нет — выбор может быть перенаправлен на значение по умолчанию, записанное в метаданных; запрошенный номер не резервируется. |

Другие распознаваемые параметры постоянства без селектора переходят по тому же устаревшему пути восстановления, что и простой `perch`: они запрашивают постоянство, но не включают автоматическое создание. Если выбор или активация не приводят к созданию подходящего upper, загрузка продолжается с использованием RAM upper и отображается предупреждение о сбое.

## Хранилище сессий и его расположение

Обычное хранилище — это `changes` каталог рядом с данными MiniOS, с пронумерованными директориями сессий и `session.conf` или `session.json` метаданными:

```text
minios/changes/
|-- session.conf
|-- session.json
|-- 1/
`-- 2/
```

В качестве хранилища также можно выбрать устройство и, при необходимости, путь. Допустимы такие варианты, как прямой `/dev/...` путь, `/dev/disk/by-label/LABEL/...`, `/dev/mapper/...`, `label:LABEL/...`, `askdisk`, и `askdisk:custom:path`. Суффикс, разделённый двоеточием, становится путем внутри выбранного устройства; путь через слэш после `askdisk` не учитывает этот пользовательский путь. Выбранная поддиректория монтируется как хранилище сессии через bind-монтирование. MiniOS также может обнаружить раздел для постоянного хранения на том же диске и поддерживаемое хранилище Ventoy для постоянства.

До выбора сессии initrd должен смонтировать расположение с возможностью записи и убедиться, что может создать и удалить маркер в хранилище. Блочное устройство, которое нельзя открыть для записи, монтирование только для чтения, недоступный путь или неудачная проверка записи — всё это приведёт к отказу в использовании постоянства для этой загрузки. Существующим сессиям не доверяют только потому, что их файлы доступны для чтения.

## Выбор и совместимость

Метаданные сессии фиксируют режим хранения и могут содержать версию MiniOS, редакцию, тип union-файловой системы и размер контейнера. При восстановлении сравниваются сохранённые режим, версия, редакция и union с запрошенными и с текущей системой.
Отсутствие устаревших полей совместимости не считается несовпадением.

Явное указание `perchdir=resume` создаёт новую пронумерованную сессию, если значение по умолчанию отсутствует или если зафиксированные режим, версия, редакция или union не совпадают с текущими. Простое указание `perch`, прямой выбор по номеру и другие устаревшие запросы восстановления не создают замену автоматически и продолжают работу во временном слое RAM после неудачного выбора. `perchdir=ask` показывает информацию о совместимости и позволяет явно проигнорировать несовпадение. Новая сессия по умолчанию создаётся в режиме `native`, если не был запрошен другой режим.

Режим хранения входит в понятие совместимости. Если выбор доходит до backend dispatch, неизвестный запрошенный режим переходит к `native`, где probe может выбрать DynFileFS при неподходящем хранилище. Если у существующей сессии другой сохранённый режим, это может привести к раннему отказу по совместимости; устаревший запрос восстановления в таком случае продолжит работу во временном слое RAM без перехода к этому запасному варианту.

## Резерв пространства и размеры

MiniOS использует 256 МиБ как стандартный запас и порог предупреждения о нехватке места. Расчёт ведётся по файловым блокам размером 1024 байта. `perchreserve` принимает неотрицательное целое число без единицы измерения, ограничено максимумом 4096 и возвращается к 256 при отсутствии или ошибке значения. Запас уменьшает доступное пространство для нового или увеличивающегося контейнера. Это не квота: нативная сессия или последующие записи могут занять оставшееся место файловой системы. При загрузке появляется предупреждение, если свободное место равно или меньше порога.

Размеры контейнеров задаются целыми значениями в МиБ:

- Число без единицы, `M`, или `MB` означает МиБ.
- `G` или `GB` умножает число на 1000 МиБ.
- `T` или `TB` умножает число на 1 000 000 МиБ.
- Raw-контейнеры ограничены 1 000 000 МиБ и доступным после резерва пространством. DynFileFS имеет отдельное ограничение с учётом RAM и жёсткий предел 2 000 000 МиБ. DynBlk получает лимит геометрии в собственном формате из `dynblk limits --format dynblk`; MiniOS не накладывает отдельного ограничения в 512 ГиБ.
- Raw — это один файл backend, поэтому FAT32 ограничивает его 4000 МиБ в MiniOS. То же ограничение действует, если Raw обёрнут в LUKS2.
- Новая raw-сессия по умолчанию создаётся размером 4000 МиБ. Шифрование не задаёт отдельную политику размера LUKS: зашифрованные Raw, DynFileFS, DynBlk или VMDK-сессии используют правила размера своего backend.
- Новая сессия DynFileFS, созданная через initrd без `perchsize` использует до 16 ГиБ логической ёмкости. Если хранилище не может вместить столько после `perchreserve` и накладных расходов индекса DynFileFS, по умолчанию используется доступная ёмкость. Индекс формата-400 требует около 2 МиБ RAM и примерно 2 МиБ хранилища на каждый ГиБ объявленной логической ёмкости, даже если полезная нагрузка пуста. Поэтому MiniOS также ограничивает ёмкость DynFileFS по физическому RAM и тестируемым пределом в 2 000 000 МиБ.
- Новая сессия DynBlk без `perchsize` также ограничена автоматическим потолком в 16 ГиБ и уменьшается, если после `perchreserve`. Явно заданный размер DynBlk — это запрос на тонкую ёмкость, который проверяется по лимиту установленного backend. Метаданные для объявленных частей создаются сразу, но место под данные выделяется по мере необходимости. DynBlk использует ограниченный кэш метаданных, не зависящий от заполнения полезной нагрузкой.

Увеличение контейнера выполняется по возможности, уменьшение не поддерживается. `perchsize` не задаёт размер для нативных или SquashFS сессий. Менеджер сессий MiniOS по умолчанию создаёт вручную raw- и DynFileFS-контейнеры размером 4000 МиБ, а DynBlk — 16 ГиБ; зашифрованные варианты используют те же значения backend по умолчанию. Подробнее см. [Управление сессиями](/using-minios/Sessions-and-Persistence).

## Активация хранилища

Все успешные backend-решения должны предоставлять доступную для записи верхнюю директорию, ожидаемую выбранной объединяющей файловой системой (union filesystem). Монтирование backend не гарантирует, что постоянство уже активно. Native, DynFileFS, DynBlk, VMDK и raw могут обновлять метаданные сессии до проверки union; SquashFS откладывает фиксацию этих метаданных. Raw, DynFileFS, DynBlk и VMDK дополнительно поддерживают шифрование LUKS2. Защищённое состояние текущей загрузки публикуется только после подтверждения финального root union с ожидаемой верхней директорией.

| Backend | Постоянное представление | Модель ёмкости | Требования к базовому хранилищу | MiniOS слой LUKS2 |
|---|---|---|---|---|
| `native` | Файлы и каталоги непосредственно в пронумерованной директории сессии | Использует пространство базовой файловой системы напрямую; `perchsize` не применяется | Доступная для записи файловая система, проходящая проверку поведения POSIX | Нет |
| `dynfilefs` | Format-400 `changes.dat` плюс сегментные файлы с ext4 `virtual.dat` | Тонкий payload с плотным индексом по размеру ёмкости | Доступное для записи хранилище с поддержкой POSIX, FAT32, NTFS или exFAT | Да |
| `dynblk` | Format-1 `volumeNNN.db` файлы с `/dev/dynblkN`, с ext4 поверх | Тонкое виртуальное блочное устройство с отображением на диск и ограниченным кэшем | Файловая система, поддерживаемая ядром backend DynBlk, и достаточные ресурсы backend | Да |
| `raw` | Один файл фиксированного размера `changes.img` с ext4 внутри | Файл создаётся с запрошенным логическим размером; только увеличение | Доступная для записи файловая система, способная разместить образ; FAT32 ограничен 4000 МБ | Да |
| `squashfs` | Сжатый `changes.sb` снимок; доступная для записи верхняя директория восстанавливается в RAM во время выполнения | Размер снимка соответствует зафиксированным изменениям; `perchsize` не применяется | Существующие снимки можно читать с поддерживаемых носителей с возможностью записи; для точного сохранения требуется подходящее хранилище с поддержкой POSIX | Нет |

### Режим Native

В режиме Native содержимое записываемого объединённого слоя сохраняется напрямую в пронумерованной директории сессии. Здесь не используется внутренний образ, loop-устройство, контейнер FUSE или отдельная блочная файловая система, поэтому объём определяется только свободным местом на основной файловой системе, а `perchsize` не применяется. Это обеспечивает минимальные накладные расходы контейнера и сохраняет обычную видимость файлов для восстановления и резервного копирования.

MiniOS сначала исключает известные не-POSIX файловые системы, такие как FAT, exFAT и NTFS. Затем он проверяет поведение реальной файловой системы, создавая файл и символическую ссылку и проверяя изменение режима исполнения. Если проверка проходит успешно, пронумерованная директория сессии монтируется напрямую как область для записи. Если файловая система заведомо не подходит или POSIX-проверка неудачна, режим native переключается на DynFileFS. В случае сбоя после активации native происходит откат; новый пустой кандидат удаляется, когда это безопасно.

Слой персистентности LUKS2 MiniOS не применяется к режиму native, так как в native нет контейнера или блочного устройства, которое можно было бы зашифровать. Тем не менее, native-персистентность может находиться на хранилище, зашифрованном вне этого слоя персистентности.

### DynFileFS

DynFileFS — это контейнерный бэкенд формата 400 на основе FUSE. Он предоставляет один логический `virtual.dat` образ, при этом данные хранятся в `changes.dat` плюс пронумерованных сегментных файлах. Вспомогательная утилита должна успешно смонтировать и предоставить `virtual.dat`; в противном случае активация завершится с ошибкой, чтобы не создать случайно только RAM-файл с именем, похожим на постоянный.

Его индекс отображения плотный относительно объявленной логической ёмкости: каждый 4-КиБ логический блок имеет одно 8-байтное смещение. Это примерно 2 МБ индекса RAM на 1 ГиБ виртуальной ёмкости, и примерно столько же хранится в индексах сегментов-носителей ещё до записи полезных данных. Выделение полезной нагрузки остаётся динамическим. Поскольку статический бинарный initrd — i686, MiniOS также применяет ограничение по логическому размеру с учётом RAM и жёсткий потолок в 2 000 000 МиБ, что ниже проверенной точки отказа адресного пространства.

Логический образ содержит ext4. Существующие образы проверяются перед монтированием в режиме записи; если результат проверки файловой системы превышает статус «исправленные ошибки», сессия отклоняется и не монтируется для записи. Изменение размера возможно только в большую сторону, и внутренняя файловая система ext4 расширяется при возможности. Для диагностики, ориентированной на пользователя, см. [Устранение неполадок](/maintenance-and-recovery/Troubleshooting).

### DynBlk

Режим `dynblk` использует блочное устройство ядра, отдельное от DynFileFS. Каждая сессия с номером владеет `volume000.db` и всеми её номерами (`volume001.db`, ..., `volume1000.db`, и далее). Нативная разметка — `DBSPRS01`, формат диска **1**. Неподдерживаемые разметки отклоняются, а не преобразуются молча. Следите, чтобы версии CLI и модулей совпадали.

MiniOS создаёт ext4 на всём диске, возвращаемом `/dev/dynblk-control`, например, `/dev/dynblk3`; не предполагает, что `dynblk0` свободен. Существующий ext4 проверяется перед записью. Защищённые записи состояния загрузки фиксируют именно это устройство, чтобы при завершении работы оно отключалось только после закрытия всех пользователей и верхней файловой системы. Допускается работа с несколькими независимыми устройствами.

Менеджер сессий, установщик и initramfs запрашивают `dynblk limits --format dynblk` для получения лимита геометрии установленного backend. Текущий ограничитель ресурсов допускает 65536 частей: стандартные логические диапазоны по 1 ГиБ позволяют до 64 ТиБ. Меньшие физические лимиты частей уменьшают виртуальный предел. Это потолок по геометрии, а не гарантия, что хост сможет открыть столько файлов или имеет достаточно RAM/места. Поддерживается увеличение; уменьшение — нет.

Таблицы отображения хранятся на диске. `--map-memory-mb` управляет кэшем метаданных на устройство (по умолчанию 1 МиБ, диапазон 1..64 МиБ), больше не процент от RAM и не ограничение на отображаемые данные. Описания экстентов, векторы открытых файлов и небольшие каталоги увеличиваются с геометрией, а не с заполнением полезной нагрузкой. При подключении сканируются метаданные отображения и временно восстанавливается состояние выделения по одной части; содержимое не читается целиком. Полная `dynblk check` читает данные. `engine_memory_bytes` не включает файловый кэш ядра, внутренности кодека и другие выделения ядра.

Метаданные для всех объявленных частей инициализируются при создании/увеличении; сами данные остаются тонкими. Части ограничены 4000 МиБ. Резервное копирование выполняется для всего отсоединённого пространства имён, без предположения о трёхзначных номерах или фиксированном последнем элементе. Для нового тома можно выбрать сжатие через `perchcomp`; при последующих загрузках используется сохранённый кодек. LUKS2 поверх DynBlk принудительно включает сжатие `none`. Частичные записи в сжатые данные сейчас пересжимают соответствующий 64-КиБ блок. При нехватке ресурсов или места запись может завершиться с ошибкой; верхняя файловая система должна быть отмонтирована до отсоединения.

### Сессии VMDK

Режим `vmdk` сессии использует тот же драйвер с реальными `twoGbMaxExtentSparse`
образами. Основной файл — `volume.vmdk`, с `volume-s001.vmdk` и последующими
частями; каждая часть покрывает до 2 ГиБ логического пространства. Описание ограничено
менее чем 1 МиБ, поэтому длина имени файла и количество экстентов ограничивают ёмкость.
Менеджер сессий, установщик и initramfs запрашивают `dynblk limits --format vmdk`.
В нативном режиме продолжает использовать `volume000.db`; ни один режим не интерпретирует файлы другого
типа. Управляемые сессии не импортируют произвольно разбитый внешний VMDK
как метаданные сессии.

Поддержка сессий VMDK объявляется через `vmdk-session-v1` в
`/etc/minios-initramfs-dynblk` внутри initrd. Текущее окружение и каждый
исходный initrd, скопированный установщиком, должны поддерживать этот режим. VMDK не поддерживает собственное сжатие;
`perchcomp` игнорируется с предупреждением при загрузке, а Менеджер сессий отклоняет
не-`none` VMDK-кодек. LUKS остаётся отдельным дополнительным слоем. Оба режима публикуют
фактический режим сессии и владеющий `dynblk_device` в защищённом состоянии загрузки,
и обе реализации завершения работы закрывают это устройство после выхода всех пользователей.

Оба формата драйвера поддерживают `writeback`, `writethrough`, `none`, `directsync` и явные `unsafe`политики подключения. Прямые режимы требуют ext2/ext4 в качестве основы. `mount -t dynblk /path/to/image /mnt -o inner-fstype=ext4,cache=writeback` подключает существующую файловую систему; `umount` освобождает устройство после закрытия последнего пользователя. Ручной `dynblk load` имеет явный срок жизни. Это не создаёт файловую систему и не разблокирует LUKS.

### Raw

Режим Raw использует один `changes.img` файл с ext4. Длина файла устанавливается в соответствии с запрошенной логической ёмкостью при создании, поэтому, в отличие от динамических бэкендов, сама ёмкость фиксирована до явного увеличения. Нижележащая файловая система может хранить неинициализированные области разреженно, но MiniOS всё равно рассматривает Raw как хранилище с фиксированной ёмкостью и проверяет наличие свободного места перед созданием или увеличением. Поскольку всё содержится в одном файле на хосте, для FAT32 действует ограничение 4000 МиБ.

Существующие образы Raw проверяются с помощью `e2fsck` перед монтированием в режиме записи. Увеличение сначала расширяет `changes.img`, а затем расширяет ext4 с помощью `resize2fs`; уменьшение не поддерживается. При неудачной проверке или монтировании образ сохраняется для восстановления, а загрузка продолжается в RAM. В Raw нет демона FUSE или собственной метаинформации блочного хранилища, что упрощает восстановление, но отсутствует поддержка динамического выделения ёмкости, как у DynFileFS и DynBlk.

### Слой шифрования LUKS

LUKS2 — это дополнительный слой шифрования, выбираемый с помощью `perchencrypt=luks` при создании Raw, DynFileFS, DynBlk или VMDK-сессии. Для существующих сессий состояние шифрования определяется метаданными сессии; указание `perchencrypt` позже не меняет и не конвертирует уже существующую сессию в открытом виде.

Граница шифрования зависит от backend: Raw подключает `changes.img` через loop-устройство и размещает LUKS2 внутри этого файла; DynFileFS подключает свой открытый `virtual.dat` через loop-устройство и шифрует этот логический образ; DynBlk использует блочное устройство `/dev/dynblkN` напрямую как источник LUKS2. Во всех трёх случаях MiniOS создаёт ext4 внутри `/dev/mapper/...`, поэтому содержимое и метаданные файловой системы внутри маппера зашифрованы на диске. Метаданные backend вне границы LUKS, файлы загрузки, метаданные сессии и другие файлы на носителе постоянства остаются незашифрованными.

Значения по умолчанию для размера, ограничения на рост, ограничения FAT32 и поведение тонкого/фиксированного выделения по-прежнему определяются backend. Initrd проходит аутентификацию перед увеличением существующего зашифрованного backend, закрывает маппер перед увеличением backend, затем вновь открывает его, проверяет ext4 и расширяет файловую систему перед монтированием. Для зашифрованных DynBlk сжатие backend принудительно устанавливается в `none`.

При создании пароль вводится дважды. Для существующих зашифрованных сессий разрешено три попытки разблокировки на консоли загрузки. Три неверных пароля приводят к фатальному завершению загрузки: MiniOS не продолжает работу в RAM, не интерпретирует эту же сессию как открытую, не выбирает другой backend и не создаёт замену. Другие ошибки при создании, проверке, изменении размера или монтировании сохраняют своё поведение восстановления, характерное для backend, без перехода в открытый режим. Пароли не сохраняются в метаданных сессии и не передаются как аргументы команд. При экспорте логических данных выгружаются расшифрованные файлы сессии, а не образ зашифрованного backend.

Подробнее см. [Безопасность](/maintenance-and-recovery/Security) о границе защиты и особенностях резервного копирования.

### SquashFS

initrd обычно активирует существующую сессию SquashFS. Интерактивная настройка создаёт метаданные нулевого поколения с включённым сохранением при завершении работы, но не создаёт `changes.sb`; доступная для записи верхняя директория существует только в RAM до первого сохранения системой по требованию или при завершении работы. Сессия нулевого поколения считается действительной только при отсутствии полей артефакта снимка и `changes.sb`. Для последующих поколений активация проверяет строгие однозначные метаданные снимка, включая его digest, сжатый и несжатый размеры, количество элементов, тип union и политику сохранения. Также проверяются тип и точный размер файла, доступные RAM и swap, SHA-256 digest до и после извлечения, а также совместимость текущего union.

Снимок извлекается с жёсткой обработкой ошибок и xattr во временный ext4-образ с ограничением размера в RAM. Для OverlayFS этот образ содержит отдельные `changes` и `workdir` каталоги; для AUFS корень образа является доступной для записи веткой.
Некорректные метаданные, недостаточно памяти, изменения digest, ошибки извлечения или некорректная политика приводят к ошибке активации и загрузке с обычной верхней директорией RAM.

Сессия с пометкой `dirty` означает, что предыдущая загрузка не завершила корректный переход к выключению. SquashFS в этом случае предупреждает и восстанавливает последний успешно сохранённый `changes.sb`; несохранённые изменения прерванной загрузки не считаются отдельным поколением отката.

Менеджер сессий MiniOS и backend сохранения системы создают и атомарно заменяют снимки SquashFS с помощью точного захвата. При загрузке снимок может быть прочитан с доступного для записи FAT, exFAT или NTFS, так как извлечение происходит во временной ext4-верхней директории. Создание и точное сохранение зависят от файловой системы: хранилище сессии должно поддерживать создание приватного рабочего пространства, Linux-метаданные и надёжную публикацию на подходящей POSIX-файловой системе.

Во время сохранения backend сначала фиксирует стабильное дерево файлов в приватном хранилище памяти, принадлежащем root, если initrd предоставляет доверенный tmpfs с достаточным запасом. Если RAM недостаточно, используется предыдущее рабочее пространство на диске. Компрессор пишет напрямую в одну приватную директорию сессии с правами 0700, а не в дополнительный образ RAM с последующим копированием на диск. MiniOS проверяет сжатый результат и его идентичность, синхронизирует, перемещает во временное приватное имя, затем повторно валидирует кандидат перед атомарной заменой активного `changes.sb`. Неудачные копии или сжатие не заменяют последний успешный снимок.

При исправной долговременной сессии `/var/log/minios` и `/var/log/live` монтируются с помощью bind из `boot-logs/` внутри пронумерованной сессии. Эти диагностические данные при запуске записываются независимо от верхней директории RAM и снимка при завершении работы. Если хранилище постоянства не было активировано надёжно, такие логи не гарантируют сохранность после перезапуска. Обычные логи и кэши можно настроить отдельно; см. [Производительность](/maintenance-and-recovery/Performance#reduce-cache-and-log-writes-with-perch).

SquashFS не имеет `perchsize`: его сохранённый размер соответствует сжатым зафиксированным изменениям, а объём оперативной памяти определяется извлечённой доступной для записи верхней директорией. Слой постоянства LUKS MiniOS не оборачивает `changes.sb`; если требуется конфиденциальность снимка, базовое хранилище должно быть зашифровано вне этого слоя. Подробнее см. [Управление сессиями](/using-minios/Sessions-and-Persistence).

## Активация union и граница восстановления

Для AUFS активированный корень изменений становится writable-веткой с номером ноль. Для OverlayFS initrd формирует `upperdir` и `workdir` под активированным корнем изменений и монтирует модули только для чтения как нижние директории. Затем initrd проверяет live-ветку AUFS или OverlayFS `upperdir` перед публикацией статуса активной персистентности.

Если backend персистентности, обновление метаданных или эта проверка завершаются неудачно, монтирования откатываются по возможности, состояние активной персистентности не публикуется, а загрузка продолжается с временным верхним слоем RAM. Неудача при формировании корневого union приводит к запуску аварийной оболочки initramfs. Выход из этой оболочки может позволить продолжить настройку с некорректным корнем; это не ремонт и не безопасный откат. AUFS сохраняет попытки добавления модулей, но неполный union пересекает границу восстановления: MiniOS не помечает персистентность как активную.

Сбой проверки контейнера специально не допускает монтирования подозрительной сессии для записи.
Не заменяйте и не восстанавливайте файлы сессии во время загрузки. Сначала сохраните затронутое хранилище; см. [Резервное копирование MiniOS](/maintenance-and-recovery/Backing-Up-MiniOS) и [Устранение неполадок](/maintenance-and-recovery/Troubleshooting).

## Активное, работающее и текущее состояние загрузки

В метаданных устойчивой сессии, `default=` — это **активная** сессия, выбранная для следующего возобновления, а `running=` — это сессия, зафиксированная как обеспечивающая текущую загрузку. При активации обе эти записи обновляются, и сессия помечается как `dirty`.
После того как точки монтирования персистентности исчезают при корректном завершении работы, MiniOS удаляет `running=` и помечает сессию как `clean`.

Эти поля метаданных могут устареть после сбоя, неудачной записи метаданных, неудачного построения объединения, копирования хранилища или прерванного завершения работы. Компоненты среды выполнения, которые поддерживают сохранение, не доверяют только `running=` этим данным. Они используют защищённое состояние текущей загрузки initrd, связанное с идентификатором загрузки, номером сессии, режимом, фактической идентичностью хранилища, возможностью записи, уровнем устойчивости, подтверждённым активным поколением и, для DynBlk, точным подключённым `/dev/dynblkN` устройством. Отсутствие или повреждение записи о текущей загрузке означает, что персистентность не может использоваться как разрешённая цель для сохранения.

При использовании `toram` и распознанном запросе на персистентность хранилище сессии копируется в RAM перед активацией. Скопированная сессия может быть доступна для записи и использоваться как рабочий верхний слой, но её состояние текущей загрузки помечается как неустойчивое. Изменения в этой копии RAM не возвращаются на исходное устройство и теряются при завершении работы.

Для получения дополнительной информации по эксплуатации см. [Режимы загрузки](/using-minios/Boot-Modes), [Параметры загрузки](/reference/Boot-Parameters), [Сессии и персистентность](/using-minios/Sessions-and-Persistence), [Резервное копирование MiniOS](/maintenance-and-recovery/Backing-Up-MiniOS), [Безопасность](/maintenance-and-recovery/Security), и [Устранение неполадок](/maintenance-and-recovery/Troubleshooting).

## Освобождение пространства с учётом сессий

`minios-session reclaim ID` работает с любым блочным форматом. Для открытых
сессий сообщает свободные диапазоны ext4 через FITRIM, затем вызывает `dynblk reclaim`.
Для активной сессии устройство привязывается к защищённому состоянию текущей загрузки, и
проверяется фактическое монтирование ext4; корень union никогда не обрабатывается напрямую.
Неактивные сессии временно подключаются и монтируются для этой операции.

Ни при загрузке, ни при завершении работы автоматическая компактация не выполняется. `--compact` — это
явный выбор пользователя в CLI или неотмеченной опции в диалоге Менеджера сессий.
Без этого выполняется только пробивание дыр (hole punching), где поддерживается, и усечение свободного хвоста.
Политика удаления данных LUKS не изменяется командой сессии.
