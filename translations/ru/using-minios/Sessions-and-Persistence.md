# Сессии и постоянство

Сессии MiniOS сохраняют изменения, внесённые в рабочую систему, между перезагрузками. Каждая сессия — это каталог с уникальным номером в `minios/changes/`; модули MiniOS остаются только для чтения, а выбранная сессия предоставляет записываемый слой объединённой файловой системы.

Используйте Менеджер сессий MiniOS из запущенной системы MiniOS:

```bash
minios-session-manager
```

Эквивалентная утилита командной строки — `minios-session`. Для выполнения команд, изменяющих данные, требуются права администратора, поэтому в примерах ниже используется `sudo`.

## Режимы сессий

| Режим | Хранилище | Основные ограничения | Слой MiniOS LUKS2 |
|------|---------|------------------|--------------------|
| `native` | Изменения сохраняются непосредственно в каталоге сессии | Требуется файловая система с поддержкой записи, сохраняющая метаданные Linux и поддерживающая операции, которые определяет MiniOS. Ёмкость определяется свободным местом на носителе; `perchsize` не применяется. | Нет |
| `dynfilefs` | Расширяемая ext4 `virtual.dat`на базе файлов-сегментов формата 400 | Работает на файловых системах с поддержкой записи: POSIX, FAT32, NTFS и exFAT. Данные занимают мало места, но индекс сопоставления увеличивается пропорционально объявленной логической ёмкости. | Да |
| `dynblk` | Тонкий ext4 на блочном устройстве ядра с поддержкой `volumeNNN.db` файлов | Требуются CLI DynBlk, модуль ядра и поддержка initrd. Размер, создаваемый при загрузке, по умолчанию до 16 ГиБ; максимальный размер можно узнать с помощью `dynblk limits`. Для сопоставлений на диске используется ограниченный кэш метаданных. | Да |
| `vmdk` | Тонкий ext4 на стандартном раздельном разрежённом VMDK, предоставляемый драйвером DynBlk | Использует `volume.vmdk` и `volume-sNNN.vmdk`. Без сжатия. Требуется `vmdk-session-v1` в маркере initrd. Такой же ручной лимит 16 ГиБ по умолчанию, как у DynBlk; узнать ограничения можно через `dynblk limits --format vmdk` . | Да |
| `raw` | Одиночный `changes.img` файл с ext4 | Фиксированная логическая ёмкость, увеличение только вручную. Работает на файловых системах с поддержкой записи: POSIX, FAT32, NTFS и exFAT; FAT32 ограничен 4000 МиБ. | Да |
| `squashfs` | Сжатый снимок в `changes.sb`; при запуске записываемый верхний слой восстанавливается в RAM | `perchsize` не применяется. Существующие снимки можно восстановить с поддерживаемых носителей с записью; для точного сохранения требуется подходящее хранилище с поддержкой POSIX. | Нет |

Raw, DynFileFS, DynBlk и VMDK могут быть дополнительно зашифрованы с помощью LUKS2. Бэкенд хранения остаётся прежним, а метаданные сессии фиксируют шифрование отдельно. DynFileFS и raw, созданные через `minios-session` по умолчанию имеют 4000 МиБ; DynBlk и VMDK — 16 ГиБ. Размеры указываются в МиБ; `GB` и `TB` суффиксы преобразуют в 1000 и 1 000 000 МиБ. Raw ограничен 4000 МиБ на FAT32 независимо от шифрования. Данные DynFileFS увеличиваются по мере необходимости, но индекс формата 400 рассчитан на всю логическую ёмкость и требует около 2 МиБ RAM плюс примерно 2 МиБ резервного хранилища на каждый ГиБ. DynBlk хранит таблицы сопоставления на диске и ограниченный кэш метаданных в RAM, по умолчанию 1 МиБ, а не процент от RAM. Векторы extent/файлов и каталоги растут с увеличением частей, а заполнение данными не требует полной резидентной карты. Узнать лимит установленной ёмкости можно через `dynblk limits --format dynblk`. Фактическая запись ограничивается свободным местом на нижележащей файловой системе и доступными ресурсами бэкенда. Операции изменения размера контейнера могут только увеличивать сессию; уменьшение не поддерживается.

Режим Native — самый простой и быстрый вариант на совместимой файловой системе.
Используйте DynFileFS, если файловая система для постоянства не поддерживает метаданные Linux.
Выберите DynBlk, если нужен реальный блочный девайс ядра с тонкими файлами-бэкендами; драйвер может одновременно подключать несколько независимых томов DynBlk, а Менеджер сессий использует путь к устройству, возвращённый драйвером, а не предполагает, что `/dev/dynblk0` свободен. DynBlk и VMDK недоступны при включённом UEFI Secure Boot, так как MiniOS не подписывает внешний модуль ядра DynBlk. Поэтому установщик и Менеджер сессий скрывают эти режимы и отклоняют явные запросы на создание до попытки загрузки модуля.
Используйте raw при необходимости фиксированного выделения, добавьте LUKS2 для шифрования сессии, а для точного сжатого снимка — SquashFS.

Выполните следующие команды для проверки файловой системы постоянства и доступных на ней режимов:

```bash
sudo minios-session info
sudo minios-session status
```

Сессии нельзя создавать на носителях только для чтения. Initrd может прочитать и активировать существующий снимок SquashFS, сохранённый на записываемых FAT, exFAT или NTFS, так как он извлекает снимок во временный ext4-верхний слой. Для создания или точного сохранения снимка требуется, чтобы хранилище поддерживало необходимые метаданные POSIX и приватную, надёжную публикацию. Для точного захвата рабочее дерево использует доверенный RAM, если доступен, с резервом на диск при недостатке RAM.

## Выбор сессии при загрузке

Любой распознанный параметр постоянства включает обработку постоянства. В загрузочных меню MiniOS обычно предлагаются варианты продолжения, создания новой, выбора, а также загрузки без постоянства. Официальное описание логики выбора, совместимости, резервирования и активации приведено в [Постоянство initrd](/reference/boot-process/Persistence-Internals).

| Параметр | Назначение |
|-----------|---------|
| `perch` | Использовать устаревший режим продолжения по принципу best-effort. Пробует метаданные по умолчанию, но не создаёт замену, если подходящей нет. |
| `perchdir=resume` | Продолжить сессией по умолчанию из метаданных и, если она отсутствует или несовместима, разрешить initrd создать новую совместимую замену. Это поведение по умолчанию для продолжения в меню загрузки. |
| `perchdir=setup` | Открыть интерактивный выбор бэкенда постоянства, затем создать новую сессию с номером. Это текущий режим **Начать новую сессию** . |
| `perchdir=new` | Создать новую сессию с номером напрямую из выбранных/стандартных настроек бэкенда, шифрования, сжатия и размера без открытия выбора бэкенда. |
| `perchdir=ask` | Выбрать существующую сессию; если хранилище пусто, автоматически запустить тот же процесс настройки, что и при `perchdir=setup` . |
| `perchdir=<id>` | Выбрать указанную сессию по номеру напрямую. |
| `perchdir=<device/path>` | Использовать место для постоянства на устройстве, включая `/dev/...` и `label:...` форматы, поддерживаемые initrd. |
| `perchmode=<mode>` | Установить `native`, `dynfilefs`, `dynblk`, `vmdk`, `raw`, или `squashfs` . |
| `perchencrypt=luks` | Зашифровать новую сессию Raw, DynFileFS, DynBlk или VMDK с помощью LUKS2. Для существующих сессий шифрование определяется только метаданными. |
| `perchcomp=<codec>` | Выбрать сжатие бэкенда DynBlk для новой сессии DynBlk. Сжатие принудительно устанавливается в `none` при использовании DynBlk с LUKS2. |
| `perchsize=<size>` | Установить новый или больший размер контейнера; значения без суффикса указываются в МиБ, а `MB`, `GB`, и `TB` суффиксы также поддерживаются. |

Если режим не задан для новой сессии, при загрузке используется native. На FAT32/NTFS/exFAT создание по умолчанию переходит в DynFileFS. Новый raw-контейнер по умолчанию — 4000 МиБ. Новые сессии DynFileFS, DynBlk и VMDK без `perchsize` используют до 16 ГиБ; если после резерва остаётся меньше места, размер автоматически уменьшается. DynFileFS также учитывает накладные расходы индекса и лимит RAM. Явное увеличение DynBlk зависит от лимита бэкенда, узнать который можно через `dynblk limits --format dynblk`. При Secure Boot initrd не предлагает режимы DynBlk/VMDK и считает явную или продолжаемую сессию DynBlk/VMDK недоступной, не пытаясь загрузить неподписанный модуль.
Сессии SquashFS можно захватить из работающей системы через Менеджер сессий MiniOS или `minios-session create squashfs`. При настройке initrd создаются только метаданные сессии нулевого поколения, а записываемый верхний слой хранится в RAM. В работающей системе первый `changes.sb` снимок создаётся по требованию или при завершении работы.

При продолжении работы MiniOS проверяет записанную версию, редакцию, объединённую файловую систему и режим. Явный `perchdir=resume` может создать новую сессию вместо отсутствующей или несовместимой по умолчанию. Простые `perch`, прямой выбор по номеру и другие устаревшие запросы продолжения не создают замену автоматически.
При интерактивном выборе перед разрешением несовместимой сессии отображается предупреждение. Если выбор или активация не удаётся, загрузка продолжается с временным верхним слоем RAM и предупреждением о постоянстве.

Хранилище сессий имеет следующий вид:

```text
minios/changes/
|-- session.conf
|-- 1/
|-- 2/
`-- N/
```

`session.conf` записывает идентификаторы по умолчанию и текущей сессии, а также режим, версию, редакцию, объединённую файловую систему, размер, состояние и специфичные для режима параметры для каждой сессии.
Это постоянные метаданные, фиксируемые реализацией загрузки, но сами по себе не подтверждают текущее состояние во время работы. Не редактируйте и не перемещайте данные сессий вручную, пока сессия смонтирована; используйте Менеджер сессий MiniOS или `minios-session`.

## Активные и запущенные сессии

Эти термины описывают разные состояния:

- **активная** сессия — это та, которая выбрана по умолчанию для следующей загрузки.
- Концептуально, **запущенная** сессия — это та, чей записываемый слой обеспечивает постоянство для текущей загрузки.

Поле постоянной `running=` фиксирует это предполагаемое соответствие. Сбой, ошибка при построении union, копирование хранилища или прерванное завершение работы могут привести к устареванию этого поля, даже если текущая загрузка использует RAM или другую сессию. Поэтому для операций, таких как сохранение SquashFS, требуется защищённое состояние текущей загрузки, связанное с идентификатором загрузки initrd, и проверенный смонтированный верхний слой; они не полагаются только на `running=` . Подробнее см. [Активное, запущенное и состояние текущей загрузки](/reference/boot-process/Persistence-Internals#active-running-and-current-boot-state) .

Активация сессии меняет выбор для следующей загрузки, но не переключает текущую объединённую файловую систему:

```bash
sudo minios-session active
sudo minios-session running
sudo minios-session activate <id>
```

Активную сессию нельзя удалить или преобразовать на месте. Запущенную сессию обычно нельзя удалить, экспортировать, скопировать, увеличить или преобразовать. Очистка также защищает оба идентификатора.

## Справочник команд

Просмотр сессий и проверка хранилища:

```bash
sudo minios-session list
sudo minios-session active
sudo minios-session running
sudo minios-session info
sudo minios-session status
```

Создание сессий:

```bash
sudo minios-session create
sudo minios-session create native
sudo minios-session create dynfilefs
sudo minios-session create dynblk 16GB
sudo minios-session create vmdk 16GB
sudo minios-session create raw 4GB
sudo minios-session create raw 4GB --encryption luks
sudo minios-session create squashfs --policy shutdown
sudo minios-session create squashfs --policy manual --autosave 60
```

`create` без указания режима выбирает native. Создание SquashFS фиксирует текущие изменения в live-системе и не имеет фиксированного размера. Политика сохранения при завершении работы по умолчанию — `shutdown`; периодическое сохранение по умолчанию отключено.

Сохранить запущенную сессию SquashFS или поддерживаемую сессию постоянства, которую текущая загрузка скопировала в RAM:

```bash
sudo minios-session save <running-session-id>
sudo minios-session save <running-ram-session-id> --as-new
```

Для SquashFS, `save` пересобирает текущий снимок. Для Raw на базе RAM, DynFileFS, DynBlk, VMDK или сессии SquashFS он записывает копию RAM обратно в исходное хранилище постоянства. `--as-new` сохраняет исходную сессию и публикует состояние RAM под новым номером сессии. Исходный носитель должен быть доступен, поддерживать запись и совпадать с идентификатором файловой системы, зафиксированным при загрузке.

Настройте автоматическое сохранение SquashFS отдельно:

```bash
sudo minios-session settings <squashfs-id> --shutdown on
sudo minios-session settings <squashfs-id> --shutdown off --autosave 0
sudo minios-session settings <squashfs-id> --shutdown on --autosave 60
```

Допустимые интервалы: `30`, `60`, `120`, `240`, и `480` минут; `0` отключает периодическое сохранение. Настройки для завершения работы и периодических сохранений независимы.

Экспорт и импорт `.tar.zst` архивов:

```bash
sudo minios-session export <id> /path/to/session.tar.zst
sudo minios-session import /path/to/session.tar.zst
sudo minios-session import /path/to/session.tar.zst --auto-convert
sudo minios-session import /path/to/session.tar.zst --force-mode dynfilefs
sudo minios-session import /path/to/session.tar.zst --force-mode dynblk
sudo minios-session import /path/to/session.tar.zst --force-mode raw --force-encryption luks
```

Принимаются только `.tar.zst` импорты. Пути и содержимое архивов проверяются, а извлечение ограничено. `--auto-convert` выбирает совместимый режим для текущей файловой системы. `--force-mode <mode>` позволяет явно выбрать доступный режим. Экспорт, копирование/клонирование и преобразование не поддерживаются для сессий SquashFS; используйте её процедуру сохранения и следуйте [Резервное копирование MiniOS](/maintenance-and-recovery/Backing-Up-MiniOS) вместо ручного копирования или восстановления содержимого live-сессии.

Копирование или преобразование сессии:

```bash
sudo minios-session copy <id>
sudo minios-session copy <id> --to-mode raw --size 4GB
sudo minios-session copy <id> --to-mode dynblk --size 16GB
sudo minios-session clone <id>
sudo minios-session convert <id> dynfilefs --size 4GB
sudo minios-session convert <id> dynblk --size 16GB --new-session
sudo minios-session convert <id> raw --to-encryption luks --size 4GB --new-session
```

`copy` — это логическое копирование файловой системы с присвоением нового идентификатора сессии. Можно изменить бэкенд, ёмкость или шифрование, а также создать новые идентификаторы ext4 и LUKS. `clone` физически копирует отсоединённый бэкенд, сохраняя заголовок LUKS, keyslots, LUKS UUID и ext4 UUID. `convert` по умолчанию заменяет исходную сессию; используйте `--new-session` для её сохранения. Размер имеет значение только для контейнера-назначения.

Увеличение, удаление или очистка сессий:

```bash
sudo minios-session resize <id> 8GB
sudo minios-session delete <id>
sudo minios-session cleanup
sudo minios-session cleanup --days 30
```

Изменение размера поддерживается для DynFileFS, DynBlk, VMDK и raw-сессий, включая зашифрованные, и требует размера больше текущего. Изменение размера DynBlk сначала увеличивает виртуальное блочное устройство, затем расширяет файловую систему ext4; новая виртуальная ёмкость не выделяется заранее. Очистка по умолчанию применяется к сессиям старше 30 дней.

Все команды принимают `--json`, а для выбора другого хранилища сессий используйте `--sessions-dir PATH` :

```bash
sudo minios-session --json list
sudo minios-session --sessions-dir /mnt/store/minios/changes list
```

## Сессия с поддержкой записи на базе RAM

Когда initrd копирует поддерживаемую сессию постоянства в RAM с помощью `perchtoram`, запущенная сессия больше не пишет напрямую в исходный бэкенд. MiniOS фиксирует исходное хранилище по UUID файловой системы и номеру сессии, а не по `/dev/sdX` имени. Менеджер сессий отображает такую сессию RAM даже при временном отключении исходного устройства.

Если исходное хранилище доступно, поддерживает запись и не изменялось, **Сохранить сейчас** записывает состояние RAM обратно в исходную сессию. **Сохранить на носитель как новую сессию** сохраняет исходный источник без изменений и публикует состояние RAM как новую сессию с новым номером. CLI-эквиваленты — `minios-session save <id>` и `minios-session save <id> --as-new` . Сохранение отображает прогресс копирования и может быть отменено до публикации; сама публикация завершается атомарно после запуска.

Если исходный носитель отсутствует, доступен только для чтения, не совпадает с идентификатором при загрузке или исходная сессия изменилась независимо, запись отклоняется — не происходит попытки записи на другое устройство по имени. Повторно подключите исходный носитель и попробуйте снова или используйте сохранение как новую сессию, если исходная сессия изменилась. Сессии native directory не копируются текущей `perchtoram` реализацией, поэтому этот путь записи применяется к Raw, DynFileFS, DynBlk, VMDK и SquashFS.

## Поведение сохранения SquashFS

Сессия SquashFS распаковывается в RAM для работы с записываемым слоем. При сохранении пересоздаётся и проверяется точный снимок, затем атомарно заменяет `changes.sb` .
Откат к предыдущим поколениям не сохраняется. Сохранить сейчас доступно из иконки в трее, Менеджера сессий MiniOS или `minios-session save` независимо от автоматической политики.

При каждом сохранении MiniOS копирует стабильное дерево изменений во внутреннее хранилище RAM, если хватает памяти. При сжатии записывается **один** образ в приватный каталог внутри сессии с номером. Только после проверки содержимого файловой системы, дайджеста, идентификатора и надёжной синхронизации сохраняющий процесс заменяет `changes.sb`. Второго полного сжатого образа в RAM или второй записи этого образа на устройство постоянства нет. При нехватке RAM для дерева только рабочее дерево переносится на диск; сжатый кандидат всё равно требует одну запись. Подробнее см. [Производительность](/maintenance-and-recovery/Performance#reduce-cache-and-log-writes-with-perch) — о политике кэширования и записи логов.

Диагностика загрузки для надёжной сессии SquashFS хранится в её `boot-logs/minios/` и `boot-logs/live/` каталогах. Они не зависят от успешного снимка при завершении работы и доступны даже если последние изменения в верхнем слое RAM не были сохранены. Хранилище должно поддерживать запись; обычные журналы могут быть временными, если выбрано `LIVE_LOG_STORAGE=volatile` .

Сохранение при завершении реализовано через основной триггер завершения MiniOS и `minios-squashfs-save` бэкенд, поэтому не зависит от наличия или запуска Менеджера сессий MiniOS. Периодическое сохранение проверяется каждые 30 минут через systemd-таймер или SysV-демон, оба используют один и тот же бэкенд автосохранения. Пересоздание снимка требует ресурсов CPU и полностью переписывает снимок; рекомендуется интервал не менее часа.

Во время работы сессии на базе RAM — SquashFS, новый захваченный и активированный снимок SquashFS может взять на себя целевой объект сохранения. После передачи старый запущенный снимок можно удалить без перезагрузки:

```bash
sudo minios-session activate <new-squashfs-id>
sudo minios-session delete <old-running-squashfs-id> --handoff
```

Это исключение применяется только к корректной передаче текущей загрузки SquashFS. Для других режимов постоянства защита от удаления сохраняется.

## Шифрование

LUKS2 — это дополнительный слой шифрования поверх хранилища Raw, DynFileFS, DynBlk или VMDK; это не отдельный режим сессии. Доступен только если `/run/initramfs/etc/minios-initramfs-crypt` содержит `luks-layer-v1` и доступны инструменты и возможности выбранного бэкенда. При выборе LUKS2 сжатие бэкенда DynBlk отключается.

При создании LUKS в интерактивном режиме пароль вводится дважды. Операции чтения или создания LUKS-данных могут получать пароль из стандартного ввода через `--password-stdin`. Пароли не передаются в аргументах команд или метаданных сессии. При загрузке initrd запрашивает пароль в консоли. Три неверных попытки приводят к фатальному завершению загрузки; MiniOS не продолжает работу с открытым текстом, RAM, другим бэкендом или заменой сессии по тому же запросу.

Для неактивной, отсоединённой зашифрованной сессии Raw, DynFileFS, DynBlk или VMDK Менеджер сессий предлагает **Изменить пароль...** . CLI-эквивалент:

```bash
sudo minios-session change-passphrase <id>
```

Запрашиваются текущий пароль, новый пароль и подтверждение. При использовании `--password-stdin` введите эти три строки по порядку. Выбранный keyslot заменяется без переформатирования или повторного шифрования всех файлов. Активные, запущенные или смонтированные сессии нужно предварительно отсоединить; дополнительные keyslot LUKS, созданные вне Менеджера сессий, не изменяются.

Зашифрованный экспорт содержит расшифрованные логические файлы сессии, а не сам зашифрованный бэкенд. Импорт, копирование или преобразование в LUKS создаёт новый зашифрованный бэкенд с новыми идентификаторами.

## Монтирование неактивной сессии

Менеджер сессий может смонтировать неактивную, не запущенную сессию Raw, DynFileFS, DynBlk или VMDK с правом записи без назначения её загрузкой по умолчанию. Щёлкните правой кнопкой мыши по сессии и выберите **Смонтировать сессию**; для зашифрованных сессий потребуется пароль LUKS. Можно одновременно смонтировать несколько сессий с разными идентификаторами. **Открыть смонтированную папку** открывает подключённую файловую систему, а **Открыть папку сессии** открывает каталог с номером сессии и её файлами-бэкендами.

Закрытие Менеджера сессий не завершает монтирование, выполненное через графический интерфейс. Откройте приложение снова, чтобы увидеть его, и выберите **Отмонтировать сессию** . Если отмонтирование занято, MiniOS оставляет демон, loop-устройство или устройство DynBlk подключёнными, чтобы не отключать хранилище под работающей файловой системой.

В отдельной CLI монтирование поддерживается до закрытия стандартного ввода или получения Ctrl+C:

```bash
sudo minios-session mount <id>
```

Команда откажет в монтировании активной или запущенной сессии и никогда не форматирует существующую файловую систему из-за ошибки монтирования.

## Резервные копии и неудачные сессии

Для сессий native, DynFileFS, DynBlk, VMDK и raw, включая зашифрованные, используйте `export` для логического резервного копирования вместо копирования каталога смонтированной сессии. Храните полученный архив на другом устройстве и убедитесь, что его можно импортировать, прежде чем полагаться на него. Импорт всегда создаёт новую сессию с номером; активируйте её вручную, когда будете готовы использовать.
Для процедур резервного копирования SquashFS и всего устройства см. [Резервное копирование MiniOS](/maintenance-and-recovery/Backing-Up-MiniOS) .

Если сессия выходит из строя из-за заполнения хранилища, прерывания записи или повторного создания пустых сессий, прекратите любые изменения на этом носителе. Если возможно, сначала экспортируйте читаемую неактивную сессию, затем следуйте разделу [Устранение неполадок](/maintenance-and-recovery/Troubleshooting) .

Начинайте диагностику без изменений данных сессии:

```bash
sudo minios-session list
sudo minios-session active
sudo minios-session running
sudo minios-session status
sudo minios-session info
```

При загрузке файловые системы контейнеров проверяются до активации записи. При серьёзных ошибках проверки файловой системы контейнер сохраняется для восстановления, а не монтируется для записи. SquashFS обнаруживает незавершённое предыдущее состояние и восстанавливает последний успешно сохранённый снимок. Удаляйте сессии только через Менеджер сессий MiniOS или `minios-session delete`; не удаляйте каталоги сессий вручную.

## Возврат неиспользуемого пространства DynFileFS, DynBlk и VMDK

В Менеджере сессий щёлкните правой кнопкой мыши по сессии DynFileFS, DynBlk или VMDK и выберите **Освободить место...** . Диалог работает как для запущенной, так и для неактивной поддерживаемой сессии, а также повторно использует сессию, уже смонтированную через Менеджер сессий. Для сессии без шифрования MiniOS запускает FITRIM на внутренней ext4-файловой системе, а затем просит бэкенд вернуть известное свободное пространство. Отсоединённые сессии временно подключаются и освобождаются только после корректного размонтирования файловой системы.

Для освобождения пространства DynFileFS требуется DynFileFS версии 4.6.0 или новее. Если пакет был обновлён при активном старом демоне DynFileFS, перезагрузите систему с обновлённым бэкендом перед возвратом пространства для этой сессии.

```sh
sudo minios-session reclaim 3 --json
# Explicitly permit live-data relocation (additional flash writes):
sudo minios-session reclaim 3 --compact --json
```

Флажок компактирования **выключен по умолчанию**, в том числе на exFAT.
Автоматическое компактирование не выполняется. В зашифрованных сессиях освобождается только пространство, уже
известное бэкенду; операция не включает discard через LUKS и не
раскрывает схему выделения. Ошибки устройства и неудачный trim останавливают операцию.

### Низкоуровневые команды драйвера

С текущим DynBlk нативным или разделённым VMDK-бэкендом удаление целых зерен
делает их размещение повторно используемым. На файловой системе ext4 освобождённые диапазоны
также могут автоматически освобождаться с помощью hole punching. На exFAT автоматическая очистка только усекает
полностью свободные хвосты файлов. **Автоматическая очистка никогда не перемещает активные данные.**

Используйте `fstrim` на смонтированной внутренней файловой системе изменений (не на объединённом AUFS/OverlayFS
корне), чтобы сообщить об удалённых блоках, затем `dynblk reclaim /dev/dynblkN --execute` для
очистки без перемещения данных. Выбирайте фактическое устройство сессии, а не предполагаемый индекс.
Чтобы вручную запросить ресурсоёмкую компактную запись на месте, добавьте `--compact`.
Это работает без конвертации образа или изменения размера виртуальной файловой системы;
другие операции чтения/записи могут выполняться между этапами освобождения. Это не автоматический режим по умолчанию.
Необязательная опция `--scan-zeroes`читает отображённые зерна и по умолчанию не включена.

Эти команды также доступны в обновлённом initrd DynBlk CLI. Автоматическая
компактизация при запуске не включена. Для зашифрованных сессий сохраняется текущая политика удаления
данных; инструменты не включают прозрачную передачу discard для dm-crypt без уведомления пользователя.
Только для чтения или `cache=unsafe`подключённые тома не подлежат очистке. Сообщаемые освобождённые
диапазоны и усечённые длины не совпадают с измеряемым свободным пространством файловой системы.

## Рабочие процессы сессий VMDK

VMDK — это отдельный режим сессии, а не новый кодек сжатия. Создание, активация,
изменение размера, экспорт/импорт, копирование, клонирование и преобразование используют те же команды Менеджера сессий, что и другие режимы контейнеров:


```sh
minios-session create vmdk 16384 --activate
minios-session copy 3 --to-mode vmdk --size 16384
minios-session import /path/to/session.tar.zst --force-mode vmdk
```

Архивы сессий содержат логические файлы и метаданные, а не произвольное внешнее
подключение VMDK. Управляемые сессии VMDK используют канонический `volume.vmdk`дескриптор
и все его `volume-sNNN.vmdk`части. Не переименовывайте части и не копируйте live-образ
в обход драйвера. Переключение между native DynBlk и VMDK требует явного
копирования/преобразования; ручное изменение `session_mode` не является преобразованием.

Установщик предлагает VMDK только при поддержке на текущей системе и отклоняет образы, у которых скопированный initrd не содержит
возможности. Обновите CLI,`vmdk-session-v1`драйвер, инструменты сессий и скрипты загрузки одновременно перед созданием сессий VMDK.
