# Архитектура системы MiniOS

MiniOS загружает операционную систему только для чтения, собранную из модулей SquashFS, и добавляет один доступный для записи слой для текущей сессии. За поиск носителя, выбор модулей и хранилища, построение корневой файловой системы, применение ранней конфигурации и передачу управления установленной init-системе отвечает initramfs.

## Обнаружение загрузочного источника

BIOS или UEFI-загрузчик загружает ядро Linux и initramfs MiniOS из
`minios/boot/`. Затем initramfs обнаруживает дерево данных MiniOS, содержащее
живые модули. Источник может быть локальным, выбранным интерактивно или
предоставленным по поддерживаемому сетевому пути; локальный ISO-файл монтируется через loop
до использования его дерева данных. Точная очередность и допустимые формы `from=` описаны в разделе
[Обнаружение системы в initrd](/configuration/Initrd-System-Discovery.md).

На этом же этапе поддерживаются HTTP ISO и PXE-источники. Необязательная сетевая
инициализация на ранней стадии загрузки используется только для **загрузки MiniOS по сети** (PXE / HTTP ISO).
Это не постоянная настройка сетевой сессии. См.
[Загрузка по сети](/installation/Network-Boot.md).

После обнаружения MiniOS может при необходимости подготовить копию в RAM. Необходимость
в исходном источнике зависит от режима копирования, наличия постоянства и успешного
отключения. Операционная модель описана в разделе [Режимы загрузки](/configuration/Boot-Modes.md).

## Состав модулей

Каждый файл `.sb` представляет собой файловую систему SquashFS только для чтения. Встроенные модули хранятся
непосредственно в `minios/`; дополнительные расположения модулей могут участвовать в
упорядоченной композиции. Initramfs выбирает, упорядочивает и монтирует итоговые
слои только для чтения. Кандидатные уровни, замена базовых имён, фильтры, пользовательские расширения
пакетов и координация с работающим ядром описаны в разделе
[Загрузка модулей в initrd](/configuration/Initrd-Module-Loading.md).

Типичный образ Xfce содержит следующие роли в указанном порядке, хотя точные имена
и количество зависят от сборки и модулей, пропущенных для данной цели:

```text
00-core-<arch>.sb
01-kernel-<version>-<arch>.sb
02-firmware-<arch>.sb
03-gui-base-<arch>.sb
04-xfce-desktop-<arch>.sb
05-apps-<arch>.sb or the next applicable module
```

Позднее подключённые модули имеют более высокий приоритет и могут заменять пути, предоставленные предыдущими
модулями. Модуль может зависеть от файлов во всех модулях с меньшим номером, поэтому набор
модульных файлов — это упорядоченная композиция, а не просто коллекция
независимых пакетов.

## AUFS и OverlayFS

MiniOS использует объединённую файловую систему (union filesystem), чтобы представить модули и слой записи как единое
корневое файловое пространство. Если работающее ядро поддерживает AUFS, используется именно оно; в противном случае применяется OverlayFS. `union=aufs` запрашивает AUFS, но всё равно переключается на
OverlayFS, если AUFS недоступен; `union=overlayfs` выбирает OverlayFS.

Между этими реализациями есть важное различие в работе:

- AUFS начинает с ветки для записи и добавляет смонтированные модули как ветки только для чтения.
  MiniOS может активировать или деактивировать модуль в работающей системе, если
  монтирование AUFS поддерживает такую операцию.
- OverlayFS получает полный упорядоченный список `lowerdir` при монтировании корня,
  а также `upperdir` и `workdir`. Набор нижележащих модулей нельзя
  изменить на лету через Менеджер модулей.

Поэтому Менеджер модулей разделяет состояния **Запущено сейчас** (текущий набор смонтированных модулей)
и **Следующая загрузка** (модули, выбранные текущим носителем и правилами загрузки). Добавление
или удаление постоянного модуля обычно влияет только на следующую загрузку. Создание или
открытие модуля не активирует его. Активация и деактивация модулей во время работы
доступны только с AUFS.

После сборки корня и завершения ранней инициализации initrd LiveKit использует
`pivot_root`, сохраняет старый initrd для завершения работы и запускает init нового корня.
В случае dracut путь подготавливает тот же собранный корень, но финальный `switch_root` выполняет dracut.
Подробнее о границе передачи см. в разделе
[Загрузка модулей в initrd](/configuration/Initrd-Module-Loading.md).

## Слой записи и сессии

Без постоянства слой записи размещается в памяти и исчезает при
выключении. При наличии постоянства можно активировать пронумерованную сессию с поддерживаемым
хранилищем. Выбор, совместимость, ошибки активации, права текущей загрузки и устойчивость описаны в разделе
[Постоянство в initrd](/configuration/Initrd-Persistence.md).

| Режим | Хранилище для записи | Примечания |
|------|----------------------|------------|
| `native` | Файлы сохраняются непосредственно в каталоге сессии | Требуется доступная для записи POSIX-файловая система, сохраняющая метаданные Linux. |
| `dynfilefs` | Расширяемая файловая система ext4, разбитая на файлы-основы | Поддерживаются POSIX-файловые системы, а также носители FAT32, NTFS или exFAT. |
| `raw` | Фиксированный `changes.img` с ext4 | Поддерживаются POSIX-файловые системы, а также носители FAT32, NTFS или exFAT. |
| `luks` | LUKS2 `changes.luks` с ext4 | Требуются cryptsetup и initramfs, собранный с поддержкой шифрования MiniOS. Пароль запрашивается при загрузке. |
| `squashfs` | Сжатый снимок `changes.sb` | Распаковывается в RAM для использования; при сохранении пересобирается и заменяет снимок атомарно. Файловая система постоянства должна сохранять метаданные Linux при сохранении. |

Активная сессия, выбранная для будущего возобновления, и слой записи, разрешённый для текущей загрузки — это связанные, но разные состояния. Изменение будущего выбора не заменяет работающий слой записи.

См. [Управление сессиями](/configuration/Session-Management.md) для команд создания,
выбора, изменения размера, шифрования, конвертации, экспорта и восстановления.

## Приоритет конфигурации

Медиа-конфигурация находится в `minios/config.conf`, с дополнительными фрагментами в
`minios/config.conf.d/`. Рабочие копии — это `/etc/live/config.conf` и
`/etc/live/config.conf.d/` в составленном корне.

При загрузке MiniOS сравнивает время изменения файлов и копирует более новую версию медиа-файла
в рабочий корень. Если носитель доступен для записи и рабочая копия новее, она
копируется обратно на носитель. Фрагментированные файлы синхронизируются по имени файла в обоих направлениях. Если часы были переведены назад после предыдущей синхронизации,
MiniOS избегает замены временных меток и только дополняет отсутствующие назначения.

Параметры командной строки ядра перекрывают соответствующие значения, считанные из рабочей
конфигурации для этой загрузки. Это означает, что фактический порядок для явно
поддерживаемой настройки: сначала параметр загрузки, затем синхронизированная рабочая/медиа-конфигурация,
затем встроенное значение по умолчанию. Постоянные изменения в рабочей конфигурации могут стать
медиа-конфигурацией, если источник доступен для записи; для ISO-носителей только для чтения
это обновление невозможно.

См. [Файл конфигурации](/configuration/Configuration-File.md) и
[live-config](/configuration/live-config.md) для поддерживаемых настроек.

## Завершение работы и жизненный цикл сохранения

При обычном завершении работы системе сначала предоставляется возможность сбросить сервисы и
данные сессии. Сессия SquashFS с включённым сохранением при завершении работы пересобирается и
проверяется до отключения файловой системы. Бэкенд сохранения записывает маркер завершения
именно для текущей сессии; initramfs завершения работы проверяет этот маркер и помечает сессию как «грязную», если требуемое сохранение не удалось.

Далее initramfs завершения работы отсоединяет неиспользуемые loop-устройства, отмонтирует старый корень
и слой для записи, отмечает успешную сессию как чистую, отмонтирует носитель
и закрывает LUKS-мэппинг, принадлежащий MiniOS. После этого оптический носитель можно извлечь до
выключения питания или перезагрузки. Ручное и периодическое сохранение SquashFS используют тот же механизм создания снимков, но только настроенная политика завершения работы блокирует финализацию как чистую при отсутствии сохранения на этапе завершения работы.

## Дерево носителя

Актуальный образ организован следующим образом. Необязательные каталоги появляются только при наличии
контента, созданного соответствующей функцией.

```text
/
|-- .disk/                         ISO metadata
|-- EFI/                           UEFI boot files
`-- minios/
    |-- 00-core-<arch>.sb          base userspace
    |-- 01-kernel-<version>-<arch>.sb
    |-- 02-firmware-<arch>.sb
    |-- NN-<name>-<arch>.sb        ordered system modules
    |-- boot/                      kernels, initramfs, GRUB, and Syslinux data
    |-- changes/                   session metadata and numbered sessions
    |-- modules/                   additional next-boot modules
    |-- config.conf                main media configuration
    |-- config.conf.d/             optional configuration fragments
    |-- kernels/                   optional inactive kernel repository
    |-- userdata/                  optional linked or bound user directories
    `-- log/                       optional exported boot logs
```

Загруженные пути под `/run/initramfs/memory/` являются монтированиями реализации, а не
второй постоянной копией этого дерева.
