# Восстановление DynFileFS и dynblk-хранилища

DynFileFS и `dynblk` предоставляют динамически выделяемый образ блока `virtual.dat`,
данные которого хранятся в наборе файлов `changes.dat`. MiniOS форматирует
`virtual.dat` в ext4 и использует его для сохранения постоянных изменений. `dynblk` —
это поддерживаемая реализация того же формата хранения; MiniOS сохраняет
название режима постоянства `dynfilefs` и команду совместимости `@mount.dynfilefs`, где это требуется.

В этом руководстве рассматриваются проверка, миграция, восстановление файловой системы,
восстановление сессии и извлечение файлов. Оно применяется после некорректного завершения работы,
переполнения устройства хранения, прерванного копирования или сбоя метаданных сессии.

Типичные симптомы:

- MiniOS создает новую сессию с номером при каждом запуске.
- `resume` не загружает предыдущий рабочий стол и файлы.
- Выбор старой сессии в загрузочном меню не дает результата.
- Каталоги сессий по-прежнему содержат файлы `changes.dat`, но не активируются.

Причиной может быть неполный сегмент хранилища, поврежденные метаданные контейнера,
«грязная» файловая система ext4 внутри `virtual.dat` или некорректный `session.conf`.

## Правила безопасности

1. Не выполняйте восстановление единственной копии контейнера хранения.
2. Не копируйте исходные сессии поверх работающего или смонтированного хранилища `minios/changes`.
3. Перед попыткой восстановления скопируйте весь каталог `changes`.
4. Запускайте `e2fsck -y` только на дополнительной копии сессии.
5. Не создавайте отсутствующий файл `changes.dat.N` вручную.

Не делайте первоначальную копию, пока исходная сессия запущена или её контейнер DynFileFS смонтирован. Метаданные и сегментные файлы могут изменяться независимо и привести к неконсистентной копии. Загружайтесь без постоянства или используйте другую систему Linux. Держите представление DynFileFS/FUSE, loop-устройство `virtual.dat` и внутреннюю файловую систему ext4 неактивными. Монтируйте только внешнюю файловую систему хранения, желательно в режиме только для чтения, чтобы можно было последовательно скопировать сегментные файлы.

## 1. Найдите источник и место для восстановления

Посмотрите файловые системы и точки монтирования:

```bash
lsblk -f
findmnt -rn -o SOURCE,TARGET,FSTYPE,OPTIONS
```

Задайте путь к исходному каталогу `changes` и отдельному recovery-каталогу на
диске с достаточным свободным местом:

```bash
SOURCE_CHANGES="/media/user/SOURCE/minios/changes"
TARGET_MINIOS="/media/user/TARGET/minios"
RECOVERY="$TARGET_MINIOS/recovery-changes"
```

Убедитесь, что на целевом диске достаточно места:

```bash
du -sh "$SOURCE_CHANGES"
df -h "$TARGET_MINIOS"
```

## 2. Скопируйте все файлы сессий

Если установлен `rsync`:

```bash
mkdir -p "$RECOVERY"
rsync -aH --sparse --info=progress2 "$SOURCE_CHANGES/" "$RECOVERY/"
sync
```

Альтернативный вариант:

```bash
mkdir -p "$RECOVERY"
cp -a "$SOURCE_CHANGES/." "$RECOVERY/"
sync
```

Нельзя копировать только основной `changes.dat`. Сессия DynFileFS обычно
содержит полную последовательность:

```text
changes.dat
changes.dat.0
changes.dat.1
changes.dat.2
...
```

Все сегменты являются частями одного контейнера.

## 3. Найдите подходящую сессию

Сравните размеры и даты изменения:

```bash
du -sh "$RECOVERY"/[0-9]* 2>/dev/null
ls -ld --time-style=long-iso "$RECOVERY"/[0-9]* 2>/dev/null
ls -lah "$RECOVERY"/[0-9]*/changes.dat* 2>/dev/null
```

Пустые или неудачно созданные сессии обычно имеют небольшой размер. Сессия с
реальными сохранёнными данными, как правило, занимает заметно больше места.

Проверьте сохранённые метаданные:

```bash
cat "$RECOVERY/session.conf" 2>/dev/null
```

MiniOS использует `session.conf` для выбора и описания сессий сохранения.

## 4. Монтирование контейнера DynFileFS или dynblk

Найдите установленный вспомогательный скрипт. В зависимости от образа MiniOS каноническое имя может быть `dynblk` или совместимое имя `@mount.dynfilefs`:

```bash
DYN=""
for candidate in \
    /run/initramfs/bin/dynblk \
    /run/initramfs/bin/@mount.dynfilefs \
    /bin/dynblk \
    /bin/@mount.dynfilefs; do
    if [ -x "$candidate" ]; then
        DYN="$candidate"
        break
    fi
done

[ -n "$DYN" ] || { echo "DynFileFS/dynblk helper not found" >&2; exit 1; }

E2FSCK=/run/initramfs/bin/e2fsck
[ -x "$E2FSCK" ] || E2FSCK=$(command -v e2fsck)

ls -l "$DYN" "$E2FSCK"
```

Выберите подходящую сессию, например, сессию 3:

```bash
SESSION=3
mkdir -p /tmp/dynfilefs-recovery /tmp/old-session

"$DYN" \
    -f "$RECOVERY/$SESSION/changes.dat" \
    -m /tmp/dynfilefs-recovery \
    -p 4000
```

Не указывайте `-s` или `perchsize` при этом ручном монтировании для восстановления. Обычный путь загрузки может передавать `-s` для запрошенного или записанного логического размера, но при восстановлении намеренно избегается запрос изменения размера и используется существующий размер из метаданных DynFileFS/dynblk.

Успешное монтирование открывает доступ к `virtual.dat`:

```bash
ls -lh /tmp/dynfilefs-recovery/virtual.dat
```

Проверьте файловую систему ext4 без внесения изменений:

```bash
"$E2FSCK" -f -n /tmp/dynfilefs-recovery/virtual.dat
```

Затем смонтируйте её в режиме только для чтения:

```bash
mount -o ro,loop /tmp/dynfilefs-recovery/virtual.dat /tmp/old-session
ls -la /tmp/old-session
ls -la /tmp/old-session/home
```

Если ожидаемые файлы видны, сессию можно восстановить.

Отмонтируйте в обратном порядке:

```bash
umount /tmp/old-session
fusermount -u /tmp/dynfilefs-recovery
```

## 5. Исправьте внутреннюю ext4

Если контейнер подключается, но `e2fsck -n` сообщает об ошибках ext4, сначала
сделайте ещё одну копию сессии:

```bash
cp -a "$RECOVERY/$SESSION" "$RECOVERY/${SESSION}-repair"
REPAIR="$RECOVERY/${SESSION}-repair"
```

Подключите и исправьте только эту копию:

```bash
mkdir -p /tmp/dynfilefs-repair

"$DYN" \
    -f "$REPAIR/changes.dat" \
    -m /tmp/dynfilefs-repair \
    -p 4000

"$E2FSCK" -f -y /tmp/dynfilefs-repair/virtual.dat
fusermount -u /tmp/dynfilefs-repair
```

После исправления повторите проверку с подключением только для чтения.

## 6. Восстановление в новую совместимую сессию

Предпочитайте восстановление в заново созданную сессию, а не восстановление метаданных повреждённой. Если существует валидный экспорт `.tar.zst`, загрузитесь в обычном режиме и импортируйте его с автоматическим преобразованием для целевой файловой системы:

```bash
sudo minios-session import /path/to/session.tar.zst --auto-convert
```

Импорт создаёт новую сессию с номером. Проверьте её, затем активируйте явно.

Если доступен только смонтированный контейнер, создайте и загрузите новую сессию в режиме, совместимом с целевой файловой системой. Смонтируйте восстановленную копию в режиме только для чтения, как в разделе 4, затем скопируйте необходимые файлы в эту работающую сессию. Например, для восстановления домашних каталогов:

```bash
sudo rsync -aHAX --info=progress2 \
    /tmp/old-session/home/ \
    /home/
sync
```

Копируйте только те данные и настройки, которые действительно нужны. Это позволит избежать использования неизвестных или неполных метаданных совместимости как определение загрузочной сессии.

## 7. Не восстанавливайте метаданные сессии на месте

Не заменяйте `session.conf` минимальным файлом и не добавляйте восстановленный каталог в существующее хранилище вручную. Метаданные описывают каждую сессию в этом хранилище; их замена может привести к потере доступа к рабочим сессиям, удалению полей совместимости и политики сохранения, а также изменению выбора следующей загрузки.

Если контейнер можно смонтировать в режиме только для чтения, восстановите его файлы в новую совместимую сессию, как описано выше. Если смонтировать не удаётся, сохраните полную офлайн-копию для дальнейшего восстановления файловой системы или экспертизы. Контейнер без надёжных метаданных хранилища — это исходный материал для восстановления, а не определение загрузочной сессии.

## Справочник ошибок

- `cannot open ... changes.dat.N`: отсутствует зафиксированный сегмент. Скопируйте его заново с исходного устройства или попробуйте другую сессию. Не создавайте пустой сегмент.
- `cannot read header`: повреждён заголовок DynFileFS/dynblk.
- `incompatible data format`: несовпадение формата контейнера и вспомогательной утилиты.
- `virtual.dat` существует, но ext4 не монтируется: проверьте копию с помощью `e2fsck`.

## Предотвращение повторения

Большинство инцидентов начинается, когда устройство для постоянного хранения заполняется во время работы. Снизьте риск с помощью следующих мер:

- Оставляйте резерв свободного места с помощью параметра загрузки `perchreserve` (по умолчанию 256 МБ). Новые и увеличивающиеся контейнеры не используют этот резерв, а MiniOS предупреждает при загрузке, если свободное место приближается к резерву. Увеличьте его на небольших или интенсивно используемых устройствах, например `perchreserve=1024`.
- Удаляйте старые или неиспользуемые сессии до того, как устройство заполнится полностью.
- Используйте сессии фиксированного размера `raw`, если требуется предсказуемое использование диска, чтобы рост не мог неожиданно заполнить устройство.
- Завершайте работу корректно. Резкое отключение питания при полном устройстве — самая частая причина контейнера, который впоследствии не удаётся смонтировать.
