# Загрузка модулей в initrd

MiniOS выбирает и монтирует свой набор модулей в initrd до передачи объединённого корня установленной системе инициализации. На этой странице описывается текущее поведение initrd. Это полезно, если модуль, отображаемый на загрузочном носителе, не появляется в `noload=`, `bext=` или `toram=trim`, либо неожиданно меняет процесс загрузки.

## Кандидатные уровни

После обнаружения каталога данных MiniOS, обычно `minios/`, initrd сканирует кандидаты на модули в следующем порядке:

1. Записи непосредственно внутри `minios/`. Этот скан не рекурсивный.
2. Записи рекурсивно ниже `minios/modules/`.
3. Записи рекурсивно ниже `minios/modules/` на источнике для записи, который был зафиксирован initrd.

Третий уровень отделён от каталога `minios/modules/` в выбранном дереве данных только для чтения. Это позволяет долговечным пользовательским модулям переопределять файлы из ISO или другого источника только для чтения. Он доступен только тогда, когда обнаружение постоянства опубликовало корень с возможностью записи, содержащий этот каталог.

Пути кандидатов при монтировании уплощаются до их точного базового имени. Например, `modules/work/50-extra.sb` и `modules/test/50-extra.sb` оба используют точку монтирования с именем `50-extra.sb`. Они не становятся двумя независимыми слоями. Кандидат на более позднем уровне с тем же базовым именем монтируется в ту же точку и заменяет предыдущего кандидата, видимого для сборки union. Поэтому одно и то же базовое имя следует рассматривать как одну ячейку замещения, а не как способ загрузить несколько модулей из разных каталогов.

Обычный формат модуля — это регулярный образ файловой системы SquashFS. Сам сканер initrd ориентируется на имя файла: он выбирает пути, заканчивающиеся на настроенное расширение, и не проверяет заранее, что каждый путь — это обычный файл или корректный SquashFS. Поэтому рекурсивные сканирования могут встретить другой объект файловой системы с подходящим именем. Неудачная попытка монтирования через loop или SquashFS будет зафиксирована в `mount`, но сам по себе этот сбой не приводит к фатальной ошибке, и загрузка может продолжиться с отсутствующим слоем. Проверяйте сомнительные файлы с помощью процедуры инспекции, описанной в разделе [Создание модулей](/development/Creating-Modules.md).

## Порядок и приоритеты

В процессе обнаружения пути сортируются по числовому значению базового имени. Ведущее число в именах, таких как `00-core.sb`, `01-kernel-VERSION.sb` и `50-extra.sb`, определяет порядок модуля. Базовое имя без ведущего числа сортируется как ноль. Используйте явные, уникальные числовые префиксы, а не полагайтесь на порядок при совпадении.

В итоговом union более поздние, с большим номером, модули имеют приоритет над более ранними с меньшим номером. Если два выбранных модуля содержат один и тот же путь относительно корня, будет виден файл из модуля с более высоким приоритетом. Слой изменений с возможностью записи имеет приоритет над всеми модулями только для чтения.

Замещение между уровнями происходит до итогового порядка модулей. Кандидат `50-extra.sb` с более позднего уровня заменяет файл с тем же базовым именем с предыдущего уровня, затем его префикс `50` определяет, где этот оставшийся монтируемый модуль окажется в union.

## Расширение пакета

Параметр загрузки `bext=` определяет расширение имени файла, используемое для поиска данных, фильтрации кандидатов и монтирования модулей. По умолчанию это `sb`, поэтому обычно используется суффикс `.sb`:

```text
bext=sb
```

Изменение `bext` меняет только выбранный суффикс имени файла; оно не конвертирует файл и не проверяет его файловую систему. Координация с ядром — это сознательное текущее ограничение: оно всё ещё использует буквальные имена `.sb` для `01-kernel-VERSION.sb`. Пользовательское значение `bext` не переименовывает и не координирует тот факт, что сканирование кандидатов с отличным от `sb` расширением не выберет такие файлы.

## Фильтры load и noload

`load=` и `noload=` — это неякорные расширенные регулярные выражения, применяемые к строкам путей кандидатов, полученным на каждом уровне. Это не списки точных имён. Простое значение, например `kernel`, совпадает с этим текстом в любом месте пути, а якоря должны быть указаны явно, если требуется точное положение. Пути различаются по уровню: кандидаты верхнего уровня — это базовые имена, кандидаты из рекурсивных данных включают `modules/`, а кандидаты из постоянного хранилища — абсолютные пути.

Запятые преобразуются в оператор альтернативы регулярного выражения. Например:

```text
load=core,kernel,firmware
```

интерпретируется как `core|kernel|firmware`. Другие специальные символы регулярных выражений не экранируются.

Числовой диапазон разворачивается только если весь фильтр — это один возрастающий диапазон, совпадающий с `^[0-9]+-[0-9]+$`. Например, `load=04-06` превращается в альтернативы `04|05|06`, при этом каждое сгенерированное значение дополняется до как минимум двух цифр. Диапазон, встроенный в список через запятую или другое выражение, не разворачивается и сохраняет обычное значение ERE.

Если заданы оба параметра, initrd сначала применяет `load=`, а затем исключает совпадения по `noload=`. Таким образом, `noload=` имеет приоритет. Нет защищённого набора основных или модулей ядра: фильтры могут исключать `00-core`, согласованные `01-kernel` или любой другой кандидат. Такой выбор может привести к неполному корню или невозможности загрузки.

## Координация с работающим ядром

Текущая версия ядра берётся из токена `vmlinuz-VERSION` в командной строке ядра, если он доступен, или используется `uname -r` по умолчанию. Перед монтированием модулей initrd координирует этот верхнеуровневый триплет:

```text
minios/01-kernel-VERSION.sb
minios/boot/vmlinuz-VERSION
minios/boot/initrfs-VERSION.img
```

Если какой-либо из элементов отсутствует, initrd ищет все три файла в:

```text
minios/kernels/VERSION/
```

Когда триплет из репозитория найден полностью, модуль копируется в `minios/`, а загрузочные файлы — в `minios/boot/`. Частичная копия удаляется. Если триплет не полный, настройка ядра возвращает ошибку, но процесс продолжается к обычному этапу монтирования модулей; итоговая система может позже завершиться сбоем из-за отсутствия пользовательских модулей для работающего ядра.

Другие верхнеуровневые файлы, совпадающие с `01-kernel-*.sb`, считаются неактивными. Initrd пытается переместить каждый неактивный модуль и соответствующие ему файлы `vmlinuz` и `initrfs` в `minios/kernels/VERSION/`. Для этих операций с резервными копиями и перемещениями репозитория требуется дерево данных с возможностью записи; отдельные сбои перемещения не считаются фатальными. Всегда используется `.sb`, независимо от `bext=`. Подробнее о поддерживаемых сценариях установки и активации ядра см. в разделе [Управление ядром](/administration/Kernel-Management.md).

## Сборка union

MiniOS выбирает `AUFS`, если работающее ядро поддерживает его, иначе используется OverlayFS. `union=overlayfs` выбирает OverlayFS. `union=aufs` запрашивает `AUFS`, но при отсутствии `AUFS` возвращается к OverlayFS.

С `AUFS` initrd сначала монтирует пустой union с веткой изменений для записи, затем добавляет каждый смонтированный модуль как ветку только для чтения. Ошибка при создании union является фатальной. Ошибка при добавлении отдельной ветки `AUFS` — это попытка по возможности продолжить: загрузка продолжается с уже добавленными ветками, но полномочия на постоянство не публикуются для неполного union.

В случае OverlayFS полный набор модулей подаётся как один обратный список `lowerdir` при монтировании union. Слой для записи предоставляет свои `upperdir` и `workdir`. Ошибка монтирования этого union фатальна. Левосторонний порядок нижних слоёв и порядок добавления `AUFS` реализуют одно и то же правило: более поздние, с большим номером, модули скрывают конфликтующие пути от более ранних модулей.

Эта композиция во время загрузки отличается от активации во время работы. После запуска `sb activate` и `sb deactivate` могут изменять только корень, который в данный момент смонтирован как `AUFS`. Нижние слои OverlayFS нельзя изменить на лету. Активация во время работы не влияет на выбор для следующей загрузки, а добавление модуля для следующей загрузки не активирует его в текущем корне. Подробнее см. в разделе [Менеджер модулей](/administration/Module-Manager.md).

## Обрезка toram

`toram=trim` создаёт дерево данных в RAM до этапа постоянства и координации ядра. Копируются только следующие элементы из выбранного дерева данных MiniOS:

- `config.conf`, который требуется этим путём копирования.
- `authorized_keys`, если он существует как обычный файл.
- Кандидаты верхнего уровня с подходящим расширением, выбранные по `load=` и `noload=`.
- Выбранные кандидаты с подходящим расширением рекурсивно ниже `modules/`, с сохранением их относительных каталогов.
- Полное дерево `changes/`, если командная строка запрашивает постоянство.

Не копируются `boot/`, `kernels/`, `rootcopy/`, `config.conf.d/`, логи, другие данные, не являющиеся модулями, невыбранные модули или отдельный уровень модуля для записи-постоянства. В частности, резервный репозиторий не может использовать каталог `kernels/`, если он был исключён из обрезанного дерева RAM. Копируемый набор модулей фильтруется до обнаружения уровня модуля постоянства.

Проверка достаточности RAM не выполняется заранее. Ошибка копирования `config.conf` или запрошенного `changes/` приводит к выходу из контекста выполнения функции копирования, но вызывающие её функции не всегда корректно останавливают загрузку. Ошибка копирования `authorized_keys` фиксируется, но не останавливает копирование. Выбранные модули копируются через конвейер; ошибка копирования отдельного модуля фиксируется, но её статус не всегда передаётся для остановки внешнего процесса загрузки. Откат транзакции при частично заполненном дереве RAM не реализован.

После копирования initrd пытается размонтировать исходную точку, удалить старый путь данных и переместить дерево RAM в этот путь. Только успех всей цепочки означает отсоединение источника. Если цепочка не удалась, загрузка продолжается с использованием временного пути RAM. Связанные операции отсоединения ISO и Ventoy выполняются по возможности. Поэтому `toram=trim` не является доказательством того, что загрузочное устройство можно извлечь. Не отключайте его, пока диагностика не подтвердит, что его файловая система, loop-устройство и device-mapper больше не смонтированы и не используются.

## Rootcopy и передача корня

После монтирования модулей и сборки union initrd копирует видимое содержимое `minios/rootcopy/` непосредственно в собранный union. Глоб `*` в оболочке пропускает записи с точкой в начале, находящиеся непосредственно в `rootcopy/`, хотя скрытые файлы внутри скопированной директории остаются частью этой копии. Это копирование файлов во внешний вид с возможностью записи, а не ещё один слой модуля только для чтения, поэтому оно может переопределять пути, предоставленные модулями. Ошибки копирования не считаются фатальными для этой функции.

MiniOS затем выполняет раннюю настройку, записывает `fstab` нового корня и, если присутствует, запускает `rootcopy/run/preinit.sh`, передавая путь union в качестве первого аргумента. Этот скрипт выполняется в окружении initrd до передачи корня и должен рассматриваться как привилегированный загрузочный код.

На финальной границе initrd LiveKit переключает собранный union на `/`, оставляет старый initrd под `/run/initramfs` для завершения работы и запускает `init` нового корня. Путь Dracut готовит тот же union и позволяет Dracut выполнить финальный `switch_root`. После пересечения этой границы обычная загрузка продолжается внутри собранного корня; изменение файлов на загрузочном носителе больше не пересобирает выбранный набор нижних слоёв для этой загрузки.

## Безопасная диагностика

Предпочитайте просмотр в режиме только для чтения и сохраняйте исходную командную строку перед изменением фильтров:

```bash
cat /proc/cmdline
sb next-boot
sb list
findmnt -no FSTYPE,OPTIONS /
findmnt -R /run/initramfs 2>/dev/null
```

`sb next-boot` показывает текущий выбор на основе правил, а `sb list` — слои, фактически составляющие работающий корень. Различие может указывать на ошибку монтирования, замену по базовому имени, изменение во время работы `AUFS` или источник выбора, который изменился после загрузки.

Для ранней диагностики добавьте `debug` для вывода трассировки оболочки, `timing` для замеров времени этапов или `rd.break` для открытия оболочки после настройки initrd и до финальной передачи корня. В этой оболочке проверьте `/memory/data`, `/memory/bundles`, точки монтирования и `/proc/cmdline`; не исправляйте файловые системы и не извлекайте носители, пока они смонтированы. Зафиксируйте первую ошибку монтирования или копирования, а не только последующий симптом. Более подробный безопасный диагностический процесс смотрите в разделе [Устранение неполадок](/administration/Troubleshooting.md).
