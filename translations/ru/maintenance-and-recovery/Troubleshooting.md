# Устранение неполадок

Начните с наблюдения и обратимых тестов. Не изменяйте разметку, не форматируйте, не восстанавливайте файловую систему, не удаляйте сессию и не заменяйте загрузочные файлы только ради проверки. Сначала сохраните важные данные.

## Первичные проверки

1. [Проверьте загруженный образ](/installing-minios/Verifying-Downloads).
2. Загрузите **Запустить без сохранения**. Если проблема исчезает, проверьте постоянную сессию или её настройки, а не базовый образ.
3. Удалите пользовательские параметры загрузки и фильтры модулей, если они не нужны для воспроизведения проблемы.
4. Попробуйте другой USB-порт и, если возможно, другое проверенное устройство или компьютер.
5. Запишите первую ошибку и точный пункт загрузочного меню, а не только последнее сообщение на экране.
6. Проверьте [Совместимость оборудования](/getting-started/Hardware-Compatibility) если тот же проверенный образ не работает на одном компьютере, но работает на другом.

## Устройство не доходит до меню загрузки MiniOS

Сначала определите, как был создан загрузочный носитель MiniOS.

- Если образ был записан напрямую (`dd`, Etcher, Rufus режим DD или запись образом через Дисковая утилита), не восстанавливайте отдельные загрузочные файлы. Если копия повреждена, полностью перезапишите устройство из проверенного образа.
- Для установки на основе файловой MiniOS структуры пересоздайте загрузочную разметку тем же документированным способом, а не копируйте файлы GRUB, Syslinux или EFI из другого выпуска.
- Ventoy использует собственный загрузчик и структуру. Не устанавливайте загрузчик MiniOS поверх устройства Ventoy; используйте [процедуру Ventoy](/installing-minios/installation-tools/Ventoy) вместо этого.
- После нативного преобразования целевая система использует стандартный загрузчик Debian и структуру файловой системы. Внешний вид рабочего стола MiniOS может сохраниться, но инфраструктура live и специфические для live-инструменты MiniOS больше не доступны. Перед восстановлением или переустановкой загрузчика Debian, подходящей для его BIOS/UEFI и разметки, сделайте резервную копию данных.

Если заново созданное устройство по-прежнему не отображается в меню загрузки прошивки, проверьте режим прошивки, поддержку Secure Boot выбранной архитектуры, USB-порт/устройство и [совместимость оборудования](/getting-started/Hardware-Compatibility).

## Меню загрузки MiniOS появляется, но запуск не удаётся

Сначала уберите необязательные параметры. Используйте `debug` и `timing` для получения дополнительного вывода на ранних этапах загрузки. `rd.break` предназначен для продвинутого анализа initramfs, а не для восстановления.

Если MiniOS не может найти свой источник, см. [Обнаружение системы](/reference/boot-process/System-Discovery). В оболочке initramfs полезную информацию можно получить только для чтения:

```sh
cat /proc/cmdline
blkid
cat /proc/net/dev
findmnt
cat /var/log/livedbg
```

Временный `from=askdisk` может помочь определить устройство, на котором действительно находятся данные MiniOS. После этого используйте документированный синтаксис `from=` вместо угадывания имён устройств.

Для загрузки по PXE или HTTP ISO см. [Сетевой загрузчик](/reference/boot-process/Network-Boot). Сетевая загрузка на ранних этапах не связана с NetworkManager в рабочей сессии.

### Сбои модулей или root-union

См. [Загрузка модулей](/reference/boot-process/Module-Loading) для правил выбора и порядка загрузки модулей. В частности:

- `load=` и `noload=` могут исключить базовые или критически важные модули ядра; `noload=`побеждает, если совпадают оба;
- кандидаты с одинаковым базовым именем занимают одну и ту же позицию для замены;
- файл `.sb` не гарантирует, что это валидный образ SquashFS;
- запущенное ядро должно совпадать с согласованным модулем ядра MiniOS и загрузочными файлами.

После успешной загрузки проверьте текущее состояние без внесения изменений:

```bash
cat /proc/cmdline
sb list
sb next-boot
findmnt -no FSTYPE,OPTIONS /
findmnt -R /run/initramfs 2>/dev/null
```

## Проблемы с отображением

Если у вас чёрный экран, неподходящее разрешение или цикл входа в дисплей-менеджер:

1. Попробуйте параметр загрузки `text`. Рабочая консоль позволяет отличить проблему с графикой/рабочим столом от сбоя на этапе загрузки.
2. Удалите вручную указанные параметры `xorg-driver` или `xorg-resolution`.
3. Проверьте **Запустить без сохранения**, чтобы исключить сохранённую конфигурацию экрана.
4. Запишите данные о GPU и драйвере с помощью `lspci -nnk`.
5. Проверьте `journalctl -b -p warning` и `dmesg --level=err,warn`.

Для виртуальных машин смотрите раздел [Виртуализация](/maintenance-and-recovery/Virtualization).

В образах Debian 13 / Devuan Excalibur с XFCE **Параметры экрана** содержит элемент управления **Масштаб интерфейса**, где можно выбрать автоматический или ручной процент. Автоматический режим следует за основным экраном; сохранённое явное значение процента имеет приоритет. Используйте предварительный просмотр с таймером и подтверждением, не приравнивайте разрешение экрана и масштаб интерфейса к одной настройке. Эффекты окон и рендерер настраиваются отдельно в **Настройки оконного менеджера → Композитор**.`xfwm4-gl` При невозможности использования OpenGL происходит переход на XRender; размытие и Magic Lamp требуют OpenGL, а затухание/масштабирование и Peek работают и с XRender.

## Проблемы с сетью

Обычные проводные и Wi-Fi-соединения управляются через NetworkManager; см. [Сетевые подключения](/using-minios/Networking).

Сначала определите, существует ли интерфейс:

```bash
ip link
ip address
ip route
nmcli device status
nmcli connection show
```

- Если интерфейс отсутствует, зафиксируйте вывод `lspci -nnk` или `lsusb` и проверьте наличие ошибок прошивки или драйвера в `dmesg`.
- Если интерфейс есть, но адреса нет, различайте проблемы подключения/DHCP и отсутствие поддержки оборудования.
- Если адрес есть, проверьте сначала шлюз, затем IP-адрес, затем DNS-имя, чтобы разделить ошибки канала, маршрутизации и DNS.
- Параметр загрузки `ip=` относится только к ранней сетевой загрузке и не настраивает постоянное соединение через NetworkManager. См. [Сетевой загрузчик](/reference/boot-process/Network-Boot).

## Проблемы с постоянством

Загрузите **Запустить без сохранения** перед изменением подозрительного хранилища постоянных данных. Не восстанавливайте и не удаляйте единственную копию сессии, пока она активна.

Проверьте, что сейчас видит MiniOS:

```bash
sudo minios-session list
sudo minios-session running
sudo minios-session active
sudo minios-session status
sudo minios-session info
```

Проверьте выбранный режим загрузки, доступное место для записи, совместимость файловой системы и совместимость сессии. Подробные правила выбора описаны в [Сессии и постоянство](/using-minios/Sessions-and-Persistence) и [Внутреннее устройство постоянства](/reference/boot-process/Persistence-Internals).

Если важная неактивная сессия `native`, `dynfilefs`, `dynblk`, `vmdk` или `raw` всё ещё доступна для чтения, включая зашифрованную, которую можно разблокировать, экспортируйте её **до** экспериментов с хранилищем:

```bash
sudo minios-session export <id> /path/to/session.tar.zst
```

Если Session Manager не может прочитать или экспортировать сессию, прекратите запись на исходный носитель и сохраните офлайн-копию затронутого хранилища до дальнейших действий. Для отсоединённой сессии DynBlk `dynblk inspect /path/to/volume000.db --metadata-only` и `dynblk check /path/to/volume000.db` предоставляют диагностику формата только для чтения; не запускайте их на томе, который всё ещё подключён. MiniOS не определяет универсальную ручную процедуру для восстановления сегментов DynFileFS, реконструкции базовых частей DynBlk, восстановления внутренней файловой системы или метаданных сессии. Такое восстановление зависит от файловой системы/контейнера и должно выполняться только на копии, если ценность данных это оправдывает.

См. [Резервное копирование MiniOS](/maintenance-and-recovery/Backing-Up-MiniOS) для поддерживаемых сценариев резервного копирования и импорта сессий.

### Ventoy Persistence Plugin

Если Session Manager сообщает, что он недоступен с Ventoy Persistence Plugin, это ожидаемое поведение для однобразного режима, а не отсутствие метаданных сессии. Выберите другой backend в Ventoy или загрузитесь без выбранного образа плагина, чтобы использовать сессии с номерами MiniOS. Недоступный или не-ext4 backend, другой формат объединения или ошибка активации на запись приведут к тому, что MiniOS выдаст предупреждение и продолжит работу в RAM. Проверьте `/run/initramfs/minios-persistence/boot-state` предупреждения при запуске; не создавайте `session.conf` вручную внутри образа плагина. Подробнее см. [Ventoy](/installing-minios/installation-tools/Ventoy).

## Проблемы с хранилищем и свободным местом

Проверьте устройства и точки монтирования без внесения изменений:

```bash
lsblk -o NAME,SIZE,TYPE,FSTYPE,LABEL,UUID,MOUNTPOINTS,MODEL
findmnt
df -hT
df -ih
```

Переполненная файловая система может привести к сбоям при работе с пакетами, неполному сохранению сессий и другим вторичным ошибкам. Освобождайте место, перемещая или удаляя известные данные только после того, как убедитесь, что выбрана правильная файловая система. Для удаления сессий используйте Менеджер сессий MiniOS вместо ручного удаления каталогов сессий с номерами.

Если `LIVE_APT_CACHE=volatile`, также проверьте `findmnt -T /var/cache/apt/archives` и `df -h /var/cache/apt/archives`: область архива — это ограниченная файловая система RAM, и крупная загрузка может её заполнить, даже если на USB-устройстве есть свободное место. При использовании `LIVE_LOG_STORAGE=volatile`, обычный `/var/log` имеет отдельное ограничение в 32 МиБ на RAM. Заполнение любой из этих областей не приводит к тому, что MiniOS автоматически начнёт записывать эти файлы на USB-устройство. Подробнее см. [Производительность](/maintenance-and-recovery/Performance#reduce-cache-and-log-writes-with-perch).

Восстановление файловой системы — это не универсальная операция MiniOS. Если сама файловая система повреждена, сначала размонтируйте её, сохраните важные данные или образ, а затем используйте процедуру восстановления, подходящую для этой файловой системы и устройства хранения.

## Изменения пакетов и обновления системы

Если проблемы возникли после изменений пакетов APT, помните, что в живой сессии с сохранением данные могут перекрывать файлы из модулей только для чтения MiniOS. Проверьте **Запустить без сохранения** чтобы сравнить с исходным набором модулей. Подробнее см. [Обновление MiniOS](/maintenance-and-recovery/Updating-MiniOS) о различии между обслуживанием через APT и сменой релизов MiniOS.

## Сбор журналов

Полезная информация включает:

```bash
uname -a
cat /etc/os-release
journalctl -b
journalctl -b -p warning
dmesg
lsblk -f
lspci -nnk
lsusb
```

При повторных сбоях загрузки на записываемых носителях MiniOS, `EXPORT_LOGS=true` в `config.conf` экспортирует журналы загрузки в `minios/log/`. См. [config.conf](/reference/configuration/config.conf).

В исправной и устойчивой `perch` сессии два обязательных журнала запуска сохраняются независимо от `LIVE_LOG_STORAGE`:

```bash
sudo ls -l /var/log/minios/minios-boot.log*
sudo ls -l /var/log/live/config.log*
sudo cat /run/initramfs/minios-persistence/boot-state
findmnt -T /var/log
findmnt -T /var/log/minios
```

Версии `.1`, `.2` и `.3` — это предыдущие загрузки. Обычный `/var/log` том можно `tmpfs` пока `/var/log/minios` и `/var/log/live` остаются на хранилище данных. Для SquashFS эти журналы также находятся в `minios/changes/<session-id>/boot-logs/`, вне `changes.sb`; они сохраняются даже при сбое создания снимка при завершении работы. При сбое или отсутствии устойчивости `perch` активации нет гарантированного места для хранения журналов. С `LIVE_LOG_STORAGE=volatile`, `journalctl -b` и другие обычные журналы доступны только для **текущей** загрузки. Для подробных `minios-update-*` трассировок включайте `LIVE_CONFIG_DEBUG=true` только при необходимости; стандартные ошибки фиксируются и без этого.

Перед отправкой журналов удалите учетные данные, приватные ключи, пароли Wi-Fi и другую конфиденциальную информацию. Для воспроизводимой ошибки приложите соответствующие фрагменты и создайте обращение в [трекере задач MiniOS](https://github.com/minios-linux/minios-live/issues).

### Сессии VMDK не поддерживаются

Обновите драйвер/CLI DynBlk и инструменты для работы с сессиями одновременно, затем пересоберите
initrd загрузки. Запущенный initrd должен объявлять `vmdk-session-v1`; установщик также
проверяет каждый исходный initrd, который будет скопирован. Старый пустой маркер DynBlk только
указывает на поддержку нативных блочных устройств и не гарантирует поддержку загрузки сессий VMDK.
Не изменяйте режим существующей сессии вручную: используйте явное копирование или
конвертацию в другой формат.

### Освобождение места в DynFileFS, DynBlk или сессиях VMDK

Используйте контекстное меню Диспетчера сессий **Освободить место...**, или
`minios-session reclaim ID --json`. Для сессий в открытом виде эта операция обрезает
внутренний ext4 и затем запрашивает у управляющего backend освобождение хранилища без
перемещения активных данных. Для этого требуется версия DynFileFS 4.6.0 или новее.
На файловых системах, таких как exFAT, внутренние фрагменты могут оставаться выделенными для файла-хоста
но быть доступны контейнеру повторно; `--compact` — это отдельный ручной выбор, который может
переместить активные данные и увеличить количество записей на флеш-устройство. Ничто не включает
компактацию или автоматическое освобождение LUKS. Для зашифрованной сессии можно освободить только
место, уже известное базовому backend через эту команду.
