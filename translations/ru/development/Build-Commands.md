# Команды сборки

MiniOS предоставляет два интерфейса командной строки для сборки. Запускайте команды из исходного каталога `minios-live`, если не используете установленную копию.

- `minios-cmd` — это фронтенд. Он принимает стандартные параметры цели, генерирует рабочую конфигурацию и запускает полную сборку.
- `minios-live` — это поэтапный бэкенд. Он читает конфигурацию сборки и выполняет один этап, диапазон этапов или весь конвейер целиком.

Для установленной версии используйте `./minios-cmd --help`, `./minios-live --help` и активный `build.conf`. Они считаются приоритетными, если примеры или устаревшая документация расходятся. Поддерживаемые значения целей могут меняться, поэтому на этой странице не приводится матрица поддержки.

## Требования root

Для отображения справки root-права не требуются:

```bash
./minios-cmd --help
./minios-live --help
```

Операции сборки требуют root, так как используются debootstrap, chroot, монтирования и инструменты создания образов. Текущий фронтенд также проверяет наличие root до записи конфигурации с помощью `--config-only`.

```bash
sudo ./minios-cmd -d trixie -a amd64 -de xfce -pv standard
```

Бэкенд проверяет и устанавливает необходимые зависимости хоста, перечисленные в `linux-live/prerequisites.list`, если только в конфигурации не установлен `SKIP_SETUP_HOST=true`.

## Сборки фронтенда

Обычный вызов `minios-cmd` требует указания всех четырёх опций выбора цели:

- `-d`, `--distribution`
- `-a`, `--architecture`
- `-de`, `--desktop-environment`
- `-pv`, `--package-variant`

Например:

```bash
sudo ./minios-cmd -d trixie -a amd64 -de xfce -pv standard
```

К распространённым дополнительным параметрам относятся сжатие, поведение ядра, локаль, часовой пояс, сборщик initramfs, язык меню загрузки и директория для сборки. Проверяйте наличие опции через `./minios-cmd --help`, а не предполагая её существование.

### Выбор ядра

Фронтенд напрямую предоставляет текущие настройки ядра:

| Опция | Эффект |
| --- | --- |
| `-kp`, `--kernel-provider` | Выбрать `distribution` или `minios` |
| `-mk`, `--minios-kernel` | Выбрать ядро MiniOS с поддержкой AUFS и автоматическим выбором серии |
| `-mks`, `--minios-kernel-series` | Выбрать `auto`, `6.1` или `6.12` и задать провайдера MiniOS |
| `-kpm`, `--kernel-payload-mode` | Выбрать полезную нагрузку с модулем ядра `runtime` или `full` |
| `-dkms`, `--kernel-build-dkms` | Собрать дополнительные драйверы DKMS для выбранного ядра |

Например:

```bash
sudo ./minios-cmd -d bookworm -a amd64 -de xfce -pv standard \
  -mks 6.1 -kpm runtime -dkms
```

Провайдер `distribution` разрешает подписанный пакет ядра в изолированном состоянии APT. Если включён DKMS, этот пакет также содержит заголовки, соответствующие выбранному ядру; на этапе DKMS они не заменяются на универсальный метапакет заголовков дистрибутива пользовательского пространства. Обычные архивы ядра используют HTTP, чтобы apt-cacher-ng мог кэшировать содержимое пакетов. APT всё равно проверяет подписанные метаданные `InRelease` и хэши пакетов.

Провайдер `minios` устанавливает `linux-image-SERIES-mos-ARCH`, проверяет поддержку AUFS в ядре и использует `linux-headers-SERIES-mos-ARCH` для DKMS. `KERNEL_FLAVOUR` должен быть `none`, архитектуры пользовательского пространства и пакета ядра должны совпадать, а политика обновлений — быть замороженной. Автоматический выбор серии использует 6.1 для i386, Buster, Bullseye, Bookworm и Jammy; для других поддерживаемых целей используется 6.12. Ядра MiniOS i386 поддерживают только серию 6.1.

`KERNEL_PAYLOAD_MODE=runtime` публикует дерево модулей ядра, конфигурацию ядра, System.map, метаданные для развёртывания и файлы интеграции для выполнения в каталогах `modprobe.d`, `modules-load.d` и `udev/rules.d`. Исключаются рабочая база данных dpkg, заголовки, ссылки на сборку, исходники DKMS, инструменты компилятора, пакеты initramfs и прошивки. Прошивки относятся к `02-firmware`. Режим `full` сохраняет расширенный диагностический набор пакетов.

Фронтенд копирует шаблон конфигурации, записывает в копию переданные значения и вызывает `minios-live -`. По умолчанию рабочая копия для этого примера:

```text
build/trixie-standard-amd64/build.conf
```

Сгенерировать конфигурацию без запуска сборки:

```bash
sudo ./minios-cmd --config-only \
  -d trixie -a amd64 -de xfce -pv standard
```

Если не указан другой путь, результат будет записан в `build/build.conf`.

`--config-file FILE` выбирает файл конфигурации. В справке к команде указано, что в этом режиме все остальные опции игнорируются, поэтому не комбинируйте его с опциями цели или оптимизации:

```bash
sudo ./minios-cmd --config-file /absolute/path/build-trixie.conf
```

В режиме опций фронтенда явно указанные значения командной строки перезаписывают соответствующие значения шаблона. В режиме файла конфигурации выбранный файл используется как входная конфигурация, а не для переопределения другими параметрами фронтенда.

## Конфигурация бэкенда

В исходной копии по умолчанию `minios-live` читает `linux-live/build.conf`. В установленной версии используется `/etc/minios-live/build.conf`. Бэкенд подключает выбранный файл перед вычислением целевых путей и не поддерживает флаги командной строки для переопределения отдельных настроек конфигурации.

Выберите другой файл через `BUILD_CONF`. Используйте абсолютный путь при переходе через границу `sudo`:

```bash
sudo env BUILD_CONF=/absolute/path/build-trixie.conf ./minios-live -
```

`BUILD_DIR` выбирает другой корень для вывода сборки:

```bash
sudo env \
  BUILD_CONF=/absolute/path/build-trixie.conf \
  BUILD_DIR=/absolute/path/minios-build \
  ./minios-live -
```

Не редактируйте сгенерированные файлы в рабочей директории цели вместо поддержки выбранной конфигурации. См. `linux-live/build.conf` для расширенных настроек ядра, загрузчика, локали, кэша, снимков, модулей, очистки и публикации.

## Этапы бэкенда

Этапы выполняются в следующем порядке:

1. `build-bootstrap`
2. `build-chroot`
3. `build-live`
4. `build-modules`
5. `build-boot`
6. `build-config`
7. `build-iso`
8. `remove-sources`

Скрипт принимает имена этапов с дефисами, отображаемые в справке.

Выполнить полный конвейер:

```bash
sudo ./minios-live -
```

Выполнить только один этап:

```bash
sudo ./minios-live build-iso
```

Выполнить диапазон этапов:

```bash
sudo ./minios-live build-chroot - build-live
```

Выполнить с первого этапа до выбранного:

```bash
sudo ./minios-live - build-live
```

Выполнить с выбранного этапа до последнего:

```bash
sudo ./minios-live build-modules -
```

В этих примерах бэкенда используется цель, выбранная в активной конфигурации. Для примеров на этой странице сначала задайте `DISTRIBUTION="trixie"`, `DISTRIBUTION_ARCH="amd64"`, `DESKTOP_ENVIRONMENT="xfce"` и `PACKAGE_VARIANT="standard"`.

## Зависимости этапов

Частичная команда не пересоздаёт выходные данные, получаемые на пропущенных ранних этапах. Поздние этапы используют корневую файловую систему, модули SquashFS, загрузочные файлы и конфигурацию, созданные на предыдущих этапах.

Пересборка раннего этапа может сделать все зависящие от него выходные данные устаревшими. Пересобирайте до последнего затронутого этапа и не сохраняйте модули с более высоким номером после изменения нижележащего модуля, на котором они основаны. В частности, `build-iso` только упаковывает ранее подготовленные данные образа; он не пересобирает эти данные.

Выполните полную сборку для новой цели или если необходимые ранние выходные данные отсутствуют:

```bash
sudo ./minios-cmd -d trixie -a amd64 -de xfce -pv standard
```

## Выходные файлы и логи

В конфигурации и корне сборки по умолчанию пример trixie использует следующие проверенные пути:

- `build/trixie-standard-amd64/core/` — изменяемая основная файловая система
- `build/trixie-standard-amd64/image/` — подготовленное дерево ISO
- `build/trixie-standard-amd64/image/minios/` — сгенерированные модули и полезная нагрузка MiniOS
- `build/iso/` — ISO-файлы и их побочные файлы `.iso.sha256`
- `build/log/build-YYYYMMDD-HHMMSS.log` — сохранённый лог сборки

Все пути указываются относительно `BUILD_DIR`. Имя файла ISO включает параметры сборки и, для нерелизных сборок, временную метку; используйте путь, выведенный после успешной сборки, а не пытайтесь предсказать полное имя файла.

## Токены Ubuntu Pro

`--ubuntu-pro-token` включает использование Ubuntu Pro при сборке фронтенда. Код сборки подключает токен внутри chroot, затем отключает и удаляет состояние Pro, аутентификацию репозиториев, настройки и следы ключей перед созданием образа. Эта очистка не делает токен безопасным для использования на хосте.

Не размещайте реальный токен в документации, системе контроля версий, истории команд оболочки, выводе CI или в общей командной строке. Лучше используйте приватный конфигурационный файл вне репозитория, ограничьте к нему доступ только владельцу и передавайте только путь к файлу:

```bash
install -m 600 linux-live/build.conf /private/path/build-trixie.conf
sudo env BUILD_CONF=/private/path/build-trixie.conf ./minios-live -
```

Укажите `USE_UBUNTU_PRO="true"` и `UBUNTU_PRO_TOKEN="..."` в этом приватном файле. Защитите и удалите любую рабочую конфигурацию на стороне хоста, содержащую токен, когда она больше не нужна, и убедитесь, что ни токен, ни данные аутентификации Pro не попали в опубликованные артефакты.
