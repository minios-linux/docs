# Сборка MiniOS

MiniOS собирается из базового образа SquashFS, выбранных модулей-расширений, файлов ядра и загрузки, а также сгенерированной конфигурации. На этой странице описаны текущие интерфейсы сборки исходного дерева и зависимости между их результатами.

Выполните `./minios-cmd --help`, `./minios-live --help`, и проверьте выбранные `build.conf` перед сборкой. Эти файлы являются эталонными для выбранной версии.

## Требования

Сборка выполняется на Debian или Ubuntu при наличии свободного места не менее `BUILD_DIR` и `/tmp`.
Для типовой рабочей станции требуется не менее 20 ГиБ. Для операций сборки необходимы права root для debootstrap, chroot, монтирования, loop-устройств и создания образов; для вывода справки права root не требуются.

Актуальный список необходимых пакетов для хоста находится в `linux-live/prerequisites.list`. Для текущей версии его можно установить командой:

```bash
sudo apt-get update
sudo apt-get install \
  sudo binutils debootstrap squashfs-tools xorriso mtools rsync \
  grub-common gpg curl openssl sbsigntool
```

В рабочем каталоге исходников `minios-live` проверяет этот список перед сборкой, если не задано `SKIP_SETUP_HOST=true`. На обычном хосте программа сообщает о недостающих пакетах и завершает работу; автоматическая установка используется только при сборке в контейнере.

Стандартная конфигурация проверяет доступ к Интернету. Проверку можно отключить с помощью `CHECK_INTERNET_CONNECTION=false` и она пропускается при использовании подготовленного репозитория кэша APT, однако все необходимые пакеты и загрузочные файлы должны быть доступны из настроенных репозиториев или кэшей.

Если `USE_APT_CACHER=true`, должен быть заранее настроен доступный сервис apt-cacher-ng по адресу `APT_CACHER_ADDRESS`; иначе установите опцию в `false` перед сборкой.

::: danger Доверие к bootstrap
Текущий путь bootstrap вызывает debootstrap с `--no-check-gpg` и загружает ключ архива MiniOS по неаутентифицированному HTTP. Не используйте полученный образ как доверенный релиз до тех пор, пока эти исходные пути не будут обеспечивать проверку ключа и bootstrap-аутентификацию.
:::

## Быстрая сборка

Клонируйте репозиторий и запустите frontend из его корня:

```bash
git clone https://github.com/minios-linux/minios-live.git
cd minios-live
sudo ./minios-cmd -d trixie -a amd64 -de xfce -pv standard
```

Четыре параметра цели обязательны, если не выбран файл конфигурации:

| Параметр | Значение |
| --- | --- |
| `-d`, `--distribution` | Целевая версия дистрибутива |
| `-a`, `--architecture` | Целевая архитектура |
| `-de`, `--desktop-environment` | Окружение модулей |
| `-pv`, `--package-variant` | `minimum`, `standard`, `toolbox`, или `ultra` |

Текущие поддерживаемые значения для дистрибутива, архитектуры, рабочего стола, сжатия и варианта приведены в `linux-live/build.conf`. Не делайте выводы о поддержке на основе устаревших примеров команд.

## Интерфейсы сборки

### `minios-cmd`

`minios-cmd` копирует шаблон конфигурации в рабочий каталог цели, записывает настройки frontend в эту копию и запускает полный `minios-live -` конвейер. Часто используемые параметры:

| Параметр | Эффект |
| --- | --- |
| `-b`, `--build-dir` | Выбор корня для вывода сборки |
| `-c`, `--compression-type` | Выбор сжатия SquashFS |
| `-kp`, `--kernel-provider` | Выбор `distribution` или `minios` |
| `-kf`, `--kernel-flavour` | Выбор варианта ядра дистрибутива |
| `-mk`, `--minios-kernel` | Выбор поставщика ядра MiniOS |
| `-mks`, `--minios-kernel-series` | Выбор `auto`, `6.1`, или `6.12` и подразумевает поставщика MiniOS |
| `-kpm`, `--kernel-payload-mode` | Выбор `runtime` или `full` |
| `-dkms`, `--kernel-build-dkms` | Сборка дополнительных драйверов для выбранного ядра |
| `-l`, `--locale` | Установка системной локали |
| `-ml`, `--multilingual` | Генерация нескольких локалей |
| `-kl`, `--keep-locales` | Сохранить доступные локали |
| `-tz`, `--timezone` | Установка часового пояса live-системы |
| `-ib`, `--initramfs-builder` | Выбор `livekit` или `dracut` |
| `-mln`, `--menu-language` | Выбор языка загрузочного меню |

Например:

```bash
sudo ./minios-cmd -d bookworm -a amd64 -de xfce -pv toolbox \
  -c zstd -mks 6.1 -kpm runtime -dkms
```

Создать конфигурацию без запуска сборки:

```bash
sudo ./minios-cmd --config-only \
  -d trixie -a amd64 -de xfce -pv standard
```

Без указания другого пути результат будет записан в `build/build.conf`. В этом режиме frontend также требует права root.

`--config-file FILE` выбирает конфигурацию для копирования. Текущая реализация затем записывает разобранные значения командной строки и непустые значения frontend по умолчанию в рабочую копию, несмотря на более краткое описание в `--help`. Для точной, вручную поддерживаемой конфигурации используйте `minios-live` напрямую и проверяйте активный файл, а не полагайтесь на объединение frontend.

Не используйте одновременно `--config-only` с `--config-file` указывающим на существующую конфигурацию: режим только-конфигурации перезапишет этот путь шаблоном по умолчанию.
Используйте `-b DIR --config-only` чтобы выбрать отдельный путь для сгенерированного файла.

### `minios-live`

`minios-live` — это подготовленный backend. В рабочем каталоге исходников он читает `linux-live/build.conf` по умолчанию; установленная копия использует `/etc/minios-live/build.conf`. Для выбора другого файла и корня вывода используйте переменные окружения:

```bash
sudo env \
  BUILD_CONF=/absolute/path/build-trixie.conf \
  BUILD_DIR=/absolute/path/minios-build \
  ./minios-live -
```

Используйте абсолютный путь к `BUILD_CONF` через `sudo`. Конфигурационные файлы интерпретируются как Bash, поэтому используйте только доверенные файлы. В backend нет параметров для переопределения отдельных переменных конфигурации.

## Этапы сборки

Конвейер выполняется в следующем порядке:

1. `build-bootstrap` создает минимальный корень цели с помощью debootstrap.
2. `build-chroot` устанавливает и настраивает базовую систему.
3. `build-live` создает `00-core` модуль SquashFS.
4. `build-modules` собирает выбранные модули среды в заданном порядке.
5. `build-boot` генерирует initramfs, ядро, EFI и загрузочные файлы.
6. `build-config` генерирует MiniOS и конфигурацию загрузки.
7. `build-iso` публикует загрузочный ISO и контрольную сумму.
8. `remove-sources` удаляет выбранный рабочий каталог, если это настроено.

Допускаются как имена с дефисами, так и формы с подчеркиванием.

```bash
# Complete pipeline
sudo ./minios-live -

# One stage only
sudo ./minios-live build-iso

# Inclusive range
sudo ./minios-live build-chroot - build-live

# First stage through build-live
sudo ./minios-live - build-live

# build-modules through remove-sources
sudo ./minios-live build-modules -
```

Частично выполненная команда не пересобирает пропущенные входные данные. `build-iso` только упаковывает подготовленное дерево образа, а `build-modules` не может пересоздать `00-core`. После изменения предыдущего этапа пересоберите все последующие, от которых он зависит.

Полный конвейер начинается с `build-bootstrap`, который удаляет существующие каталоги `core/` и `image/` цели. Сохраните все важные данные перед запуском; сгенерированные деревья цели — это выходные данные сборки, а не постоянное хранилище исходников.

Если `REMOVE_SOURCES=true`, финальный этап `remove-sources` удаляет и пересоздаёт весь рабочий каталог `build/<distribution>-<variant>-<architecture>/`, а не только загруженные исходные архивы. Опубликованные ISO, общие кэши и логи вне этого каталога сохраняются.

## Конфигурация

`linux-live/build.conf` управляет идентификатором цели, ядром, локалью, загрузчиком, live-пользователем, службами, кэшами, снимками, очисткой и публикацией. Важные группы:

- `DISTRIBUTION`, `DISTRIBUTION_ARCH`, `DESKTOP_ENVIRONMENT`, и `PACKAGE_VARIANT` выбирают цель и цепочку модулей.
- `COMP_TYPE` управляет сжатием SquashFS.
- `KERNEL_*` и `MINIOS_KERNEL_SERIES` управляют получением ядра и его содержимым.
- `INITRAMFS_BUILDER`, `INITRAMFS_CRYPT`, `BOOTLOADER`, `MENU_LANG`, и `SERIAL_CONSOLE` управляют загрузочными артефактами.
- `USE_ROOTFS`, `USE_APT_CACHE`, `USE_SHARED_APT_CACHE`, `USE_APT_CACHE_REPO`, и `USE_APT_CACHER` управляют повторно используемыми входными данными.
- `VERBOSITY_LEVEL` принимает `0`, `1`, или `2`.
- `REMOVE_OLD_ISO`, `REMOVE_SOURCES`, и `BUILD_TEST_ISO` управляют публикацией и очисткой.

Не редактируйте сгенерированный `build/<target>/build.conf` вместо поддержки выбранной исходной конфигурации.

### Выбор ядра

Провайдер `distribution` определяет выбранное ядро Debian или Ubuntu и, если включён DKMS, соответствующие заголовки в изолированном подписанном состоянии APT.
`KERNEL_AUTO_SELECT=true` получает исходную версию и архитектуру из целевого пользовательского пространства. Для ручного выбора используйте `false` и настройте поля дистрибутива, архитектуры, версии, снимка и политики обновлений в `build.conf`.

Провайдер `minios` устанавливает `linux-image-SERIES-mos-ARCH`, проверяет поддержку AUFS и использует соответствующие заголовки MiniOS для DKMS. Требуются `KERNEL_FLAVOUR=none` и совпадающие архитектуры пакетов пользовательского пространства и ядра.
В текущей реализации `MINIOS_KERNEL_SERIES=auto` соответствует `6.12`; используйте `6.1` явно, если требуется именно эта серия.

`KERNEL_PAYLOAD_MODE=runtime` сохраняет дерево модулей ядра, конфигурацию ядра, `System.map`, метаданные развертывания и интеграцию во время выполнения в `modprobe.d`, `modules-load.d`, и `udev/rules.d`. Удаляется состояние пакетов, используемых только для сборки, заголовки, исходники DKMS, компиляторы и пакеты initramfs. Прошивка по-прежнему управляется `02-firmware`. `full` сохраняет расширенный диагностический набор.

## Система модулей

Исходники модулей размещаются в `linux-live/scripts/`. Окружение в `linux-live/environments/<desktop>/` содержит упорядоченные симлинки на используемые исходники. Имя в локальном окружении определяет порядок сборки и может перенумеровать общий исходник, например:

```text
linux-live/environments/xfce/06-firefox -> ../../scripts/10-firefox
```

`00-core` создаётся с помощью `build-live` и не является обычной ссылкой окружения.
Модули с `01` и выше являются накопительными: каждый строится поверх всех предыдущих. `skip_conditions.conf` может не содержать некоторые записи для цели, поэтому проверяйте выбранное окружение, а не предполагаемую универсальную цепочку.

Используйте `linux-live/scripts/10-example/` как текущий шаблон для разработки. Модуль может содержать:

```text
NN-module-name/
├── packages.list
├── install
├── build
├── postinstall
├── skip_conditions.conf
├── patches/
├── rootcopy-install/
└── rootcopy-postinstall/
```

Требуются только необходимые для модуля файлы. `build`, `postinstall`, условия пропуска, патчи и деревья rootcopy не обязательны. `build` и `patches/` недоступны для `00-core`.

В деревьях rootcopy владельцы файлов с хоста не сохраняются; скопированные файлы обычно становятся `root:root`. В `.minios-ownership` манифесте внутри дерева rootcopy используются:

```text
owner:group relative/path
```

Пути должны оставаться внутри дерева. Хост применяет манифест сразу и разрешает имена через свою базу пользователей. Для аккаунтов, которых нет на хосте, используйте числовые значения `UID:GID` или задайте владельца через `install` или `postinstall` внутри chroot. Перемещение манифеста в `rootcopy-postinstall/` не влияет на разрешение имён.

Поскольку текущая проверка вложенности не приводит путь к каноническому виду, никогда не используйте в путях манифеста компоненты `..` или симлинки. Проверьте деревья rootcopy перед привилегированной сборкой: специально созданный путь может позволить `chown` выйти за пределы копируемого дерева.

Для пакетов обычные install-скрипты модуля используют файлы, скопированные в chroot с помощью `build-modules`:

```bash
#!/bin/bash
set -e
set -o pipefail
set -u

. /minioslib || exit 1
. /minios_build.conf || exit 1

SCRIPT_DIR="$(dirname "$(readlink -f "$0")")"
/condinapt \
  -l "${SCRIPT_DIR}/packages.list" \
  -c "${SCRIPT_DIR}/minios_build.conf" \
  -m "${SCRIPT_DIR}/condinapt.map"
```

См. [CondinAPT](/development/CondinAPT) для синтаксиса списков пакетов и актуальной карты фильтров MiniOS.

### Добавление модуля

Скопируйте шаблон и добавьте ссылку на него в каждое нужное окружение с нужной позицией в локальном порядке:

```bash
cp -a linux-live/scripts/10-example linux-live/scripts/10-my-module
ln -s ../../scripts/10-my-module \
  linux-live/environments/xfce/07-my-module
```

Адаптируйте `packages.list`, скрипты, метаданные и содержимое rootcopy перед сборкой.
Проверьте корректность всех указанных рабочих столов, вариантов, дистрибутивов и архитектур.

## Безопасная пересборка

Существующие артефакты модулей пропускаются. Если изменился нижележащий накопительный модуль, удалите его артефакт и все артефакты последующих модулей, затем запустите `build-modules`; если оставить более высокие модули, их содержимое будет собрано на основе устаревшего нижнего слоя. Определяйте артефакты по порядку окружения и имени модуля, так как условия пропуска могут создавать пропуски в нумерации.

Ядро — особый случай. Чтобы пересобрать только `01-kernel`, удалите его артефакт для выбранной цели и пересоберите начиная с модулей до публикации:

```bash
rm build/trixie-standard-amd64/image/minios/01-kernel-*.sb
sudo ./minios-live build-modules -
```

Перед удалением убедитесь в правильности пути к цели. Не используйте этот способ для `00-core` и не применяйте его к модулям с `02` и выше.

Для обычного модуля, например `03-gui-base`, удалите его артефакт и все последующие соответствующие артефакты модулей, затем выполните тот же диапазон `build-modules -`. Для изменений только в initramfs, EFI или загрузке оставьте модули SquashFS на месте и выполните:

```bash
sudo ./minios-live build-boot -
```

Выполните полную сборку после изменений в `00-core`, настройке bootstrap/chroot, идентификаторе цели, политике репозиториев или других входных данных, которые нельзя изолировать на более поздних этапах.

## Выходные данные и логи

При стандартном `BUILD_DIR`, важные пути:

- `build/rootfs/<distribution>-<architecture>-rootfs.tar.gz`
- `build/aptcache/<distribution>/`
- `build/<distribution>-<variant>-<architecture>/core/`
- `build/<distribution>-<variant>-<architecture>/image/`
- `build/<distribution>-<variant>-<architecture>/image/minios/`
- `build/<distribution>-<variant>-<architecture>/overlays/`
- `build/cache/kernel/`
- `build/iso/*.iso` и `build/iso/*.iso.sha256`
- `build/log/build-*.log`

Имена ISO зависят от настроек сборки, режима релиза и времени сборки. Используйте путь, выведенный после успешной сборки, а не пытайтесь предсказать полное имя файла.

## Секреты и отладочные артефакты

Не размещайте токен Ubuntu Pro в системе контроля версий, документации, истории команд или общих логах. Используйте приватную конфигурацию вне репозитория:

```bash
install -m 600 linux-live/build.conf /private/path/build-trixie.conf
sudo env BUILD_CONF=/private/path/build-trixie.conf ./minios-live -
```

Установите `USE_UBUNTU_PRO=true` и `UBUNTU_PRO_TOKEN=...` только в этом файле. Сборка удаляет состояние Pro из образа, но файл на хосте по-прежнему содержит секрет.

`DEBUG_SSH_KEYS=true` генерирует приватные ключи для отладки. Такой образ следует считать временным и не публиковать его, не убедившись в отсутствии ключа.

Возврат опции к значению `false` не удаляет уже созданные ключи в `build/<target>/image/minios/debug_ssh_key`, соседних файлах `authorized_keys.*` или `build/<target>/debug_ssh_key`. Используйте чистую цель или удалите эти файлы вручную, затем проверьте дерево ISO перед публикацией.

## Устранение неполадок

- Сбои bootstrap обычно связаны с доступностью репозиториев, поддержкой debootstrap, архитектурой, снимками или отсутствием необходимых пакетов на хосте.
- Сбои ядра и модулей чаще всего вызваны недоступностью пакетов, фильтрами CondinAPT, скриптами сопровождения, содержимым rootcopy или устаревшим нижним модулем.
- Сбои загрузки обычно связаны с выбранным ядром, сборщиком initramfs, получением EFI, генерацией GRUB/SYSLINUX или отсутствием загрузочных файлов.
- Сбои ISO чаще всего связаны с подготовленным деревом образа, xorriso, нехваткой места для вывода или настройками очистки.

После прерванной привилегированной сборки проверьте монтирования в рабочем каталоге цели перед повтором. Ознакомьтесь с соответствующим `build/log/build-*.log`; не исправляйте сгенерированные оверлеи или `.sb` файлы на месте.
