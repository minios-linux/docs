# Создание модулей

Модули MiniOS представляют собой файловые образы SquashFS только для чтения, которые по соглашению имеют расширение `.sb`. При загрузке MiniOS формирует из выбранных модулей слоистую корневую файловую систему. Файлы из слоя с более высоким приоритетом могут дополнять или скрывать файлы из нижележащих слоев.

В этом руководстве описаны текущие командные сценарии работы с инструментами MiniOS Tools. Для графического приложения см. [MiniOS Module Manager](/administration/Module-Manager.md). Полный процесс сборки образа и архитектуру системы см. в разделе [Building MiniOS](/development/Building-MiniOS.md). Списки пакетов, используемые при сборке MiniOS, описаны в [документации CondinAPT](/development/CondinAPT.md).

## Границы безопасности и привилегий

Не все операции с модулями требуют прав суперпользователя:

| Операция | Привилегии |
|---|---|
| Просмотр запущенных сейчас или на следующей загрузке с помощью `sb` | Без root |
| Просмотр модуля с помощью `sb inspect` | Без root |
| Обычное преобразование `dir2sb` и `sb2dir` | Без root |
| Сохранение владельца или разрешение специальных файлов при конвертации | Root |
| Сборка с помощью `apt2sb`, `script2sb` или `chroot2sb` | Root |
| Захват сессии с помощью `savechanges` | Root |
| Активация, деактивация, добавление в следующий запуск или удаление из следующего запуска | Root |

Сборщики используют изолированный union и не устанавливают пакеты или скрипты непосредственно в рабочий root. Создание также не активирует результат и не выбирает его для следующей загрузки.

Текущие конвертеры и сборщики используют публикацию без замены. Уже существующая цель, включая символическую ссылку, не перезаписывается. Выберите новый путь для вывода или вручную удалите старый результат.

Используйте вывод `--help` каждой команды как ссылку на установленную версию. Стандартные варианты сжатия для сборщика: `zstd` (по умолчанию), `gzip`, `lzo` и `xz`; `dir2sb` также поддерживает `lz4`.

## Имена модулей и уровни фильтрации

Имена часто начинаются с числа, например `06-browser.sb`, так как порядок слоев влияет на разрешение конфликтов. Модуль должен содержать пути относительно корня системы, например `usr/bin/example`, а не дополнительную директорию с этим деревом.

Опция `--level LEVEL` для `apt2sb`, `script2sb` и `chroot2sb` ограничивает базовые слои, используемые для построения объединённой файловой системы. С `--level 3` используются слои с номерами до `03`, а более высокие номера фильтруются. Это может сделать модуль менее зависимым от необязательных верхних слоев, но увеличивает количество зависимостей в результате.

## Создание модуля из пакетов

`apt2sb` устанавливает пакеты из репозитория или читаемые локальные файлы `.deb` во временное объединённое окружение и сохраняет результат. Требуется поддерживаемая живая сессия MiniOS и права root.

```bash
sudo apt2sb install chromium chromium-sandbox
sudo apt2sb install -y --level 3 -n 06-browser.sb chromium chromium-sandbox
sudo apt2sb install -y --no-install-recommends ./example_amd64.deb -n 06-example.sb
```

Без указания `--name` имя выходного файла формируется на основе первого пакета. Полезные параметры APT: `--install-recommends`, `--no-install-recommends`, `--install-suggests`, `--no-install-suggests`, `--allow-downgrades` и `--target-release RELEASE`. Опция target-release применяется только к `install`.

Чтобы зафиксировать обновления уже установленных пакетов:

```bash
sudo apt2sb upgrade -y -n upgrades.sb
```

## Создание модуля из скрипта

`script2sb` копирует установочный скрипт во временное chroot-окружение, делает его исполняемым, запускает от root без интерактивного терминала, удаляет его и сохраняет изменения файловой системы. Если скрипт завершился с ошибкой, модуль не создаётся.

```bash
sudo script2sb --script ./install-example.sh -n 06-example.sb
sudo script2sb --script ./install-example.sh --directory ./seed-root --level 3 -n 06-example.sb
```

Необязательный параметр `--directory DIR` копирует все содержимое исходной директории, включая скрытые файлы, в корень модуля до запуска скрипта. Подготовьте директорию-источник как дерево файловой системы:

```text
seed-root/
`-- usr/
    `-- share/
        `-- applications/
            `-- example.desktop
```

Перед запуском обязательно проверьте скрипт. Он выполняется с правами администратора и может запускать любые команды. Если для установки требуются вопросы или ручные действия, используйте вместо этого `chroot2sb`.

## Создание модуля в интерактивном режиме

`chroot2sb` создаёт временное объединённое окружение и открывает в нём root-оболочку. Установите пакеты или измените файлы, затем выйдите из оболочки для сохранения изменений:

```bash
sudo chroot2sb --level 3 -n 06-custom.sb
sudo chroot2sb --directory ./seed-root -c xz -n 06-custom.sb
```

Введённые в оболочке команды не воспроизводятся при загрузке модуля; модуль — это снимок итогового состояния файловой системы. История команд оболочки из результата удаляется. Если имя не указано, оно формируется автоматически по текущей дате и времени.

Разделённый жизненный цикл `prepare`, `shell`, `finish` и `cancel` используется для защищённых графических интерфейсов. Для обычной работы в терминале используйте приведённую выше интерактивную команду.

## Создание модуля из директории

`dir2sb` упаковывает содержимое подготовленной директории в новый модуль. Оба аргумента обязательны:

```bash
dir2sb my-app-root 06-my-app.sb
dir2sb --comp xz my-app-root 06-my-app-xz.sb
```

Обычное преобразование не требует root. Исходные данные не изменяются, внутри модуля все файлы принадлежат root, устройства, сокеты и FIFO-объекты отклоняются, цель никогда не перезаписывается. Используйте `--keep-ownership` или `--allow-special` только при необходимости этих привилегированных режимов.

## Захват изменений текущей сессии

`savechanges` читает основной записываемый слой работающей сессии MiniOS. Требуются права root, так как этот слой может содержать файлы, доступные только root. Местоположение изменений определяется автоматически:

```bash
sudo savechanges session-changes.sb
sudo savechanges --comp xz session-changes-xz.sb
```

Без параметра `--profile` историческая политика MiniOS исключает пустые директории, кэши, логи, загрузочные данные, временные пути, псевдофайловые системы и отдельные файлы сессии и системы. Это удобно для традиционного создания модулей, но не является явной гарантией приватности.

Доступные профили:

- `exact` сохраняет все представимые изменения, включая пользовательские данные, логи, кэши, идентификационные файлы, учётные данные и поддерживаемые метаданные об удалениях. Не поддерживаемые объекты файловой системы отклоняются, а не теряются молча.
- `clean` использует ограниченный список разрешённых путей, ориентированных на ПО. Исключаются домашние и root-директории, логи, кэши, идентификаторы, сетевые настройки, учётные данные, произвольная системная конфигурация и `/usr/local`. Это уменьшает риск раскрытия приватных данных, но не гарантирует, что разрешённый файл не содержит секретов.
- `selected` включает только проверенные относительные пути из файла инвентаризации и выбора. Явные исключения имеют приоритет. Этот профиль подходит, если модуль должен содержать строго контролируемый набор изменений сессии.

Примеры:

```bash
sudo savechanges --profile exact exact-session.sb
sudo savechanges --profile clean --comp xz software-session.sb
sudo savechanges --inventory-json session-inventory.json
sudo savechanges --profile selected --selection selection.json selected-session.sb
```

Файл выбора должен иметь строго следующую JSON-структуру:

```json
{
  "product_kind": "minios-session-selection",
  "schema_version": 1,
  "include_paths": ["etc/default", "opt/my-app"],
  "exclude_paths": ["opt/my-app/private"]
}
```

Пути нормализуются, не могут быть пустыми и указываются относительно корня изменений. Сначала сгенерируйте и проверьте инвентаризацию; каждый включённый путь должен соответствовать данным инвентаря. Инвентаризация записывает метаданные (путь, тип, категорию, чувствительность, размер), но не читает и не выводит содержимое файлов, цели симлинков или секретные значения. Выходные данные и инвентари для явных профилей имеют режим `0600`; модули по старой политике — режим `0644`.

Захват сессии может сохранять поддерживаемые удаления файлов и непрозрачность директорий для активных бэкендов AUFS или OverlayFS. Исключаются временные монтирования, вложенные файловые системы, служебные данные union и сам выходной файл. Существующая цель никогда не заменяется.

## Просмотр и извлечение модулей

Просмотреть модуль без монтирования или извлечения:

```bash
sb inspect 06-example.sb
sb inspect 06-example.sb --json
```

Просмотр не требует root и работает вне сессии MiniOS.

Извлечь модуль в новую директорию:

```bash
sb2dir 06-example.sb example-root
```

Обычное извлечение не требует root и не изменяет исходный модуль. Целевая директория не должна существовать. Специальные файлы отклоняются, если только не указан `--allow-special` с достаточными правами.

Директории, созданные текущей `sb2dir`, являются обычными директориями. `rmsbdir`, `sb rm` и `sb rmdir` — устаревшие команды совместимости, которые всегда отказывают в удалении; они не размонтируют и не удаляют ничего рекурсивно. Перед удалением извлечённого пути и его содержимого используйте стандартные инструменты файловой системы для проверки.

## Управление модулями в текущей и следующей сессии

Текущая сессия (Running Now) и следующая загрузка (Next Boot) — независимые композиции.

Показать модули, фактически составляющие текущий корень AUFS или OverlayFS, в порядке от низшего к высшему приоритету:

```bash
sb list
sb list --json
```

Показать модули, выбранные текущими правилами загрузки, включая `bext`, `load` и `noload`:

```bash
sb next-boot
sb next-boot --json
```

Эти запросы не требуют root. Модуль для следующей загрузки может быть взят из основной директории данных, её каталога `modules/` или отдельного хранилища пользовательских модулей. Поздний источник с тем же именем заменяет более ранний выбор.

Чтобы сделать пользовательский модуль доступным при следующей загрузке:

```bash
sudo sb next-boot add 50-extra.sb
```

MiniOS использует подходящее долговременное хранилище, подготавливает и проверяет копию, публикует её атомарно, не заменяя существующий модуль. Имя файла должно соответствовать текущим фильтрам загрузки. Для удаления выбранного пользовательского модуля используйте его точное имя:

```bash
sudo sb next-boot remove 50-extra.sb
```

Удаление невозможно для базовых модулей и модулей на только для чтения или временных источниках.

Активация в реальном времени — отдельная операция только для текущей сессии:

```bash
sudo sb activate 50-extra.sb
sudo sb deactivate 50-extra.sb
```

Активация и деактивация работают только если `/` сейчас объединён с помощью AUFS. Они недоступны на OverlayFS, и одной поддержки AUFS в ядре недостаточно. Ни одна из команд не меняет Next Boot.

Диспетчер конвертеров совместимости требует оба аргумента:

```bash
sudo sb conv my-app-root 06-my-app.sb
sudo sb conv 06-my-app.sb example-root
```

Рекомендуется использовать прямые `dir2sb` и `sb2dir`, так как обычное преобразование можно выполнять без root.
